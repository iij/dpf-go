# dpf-go Constitution

本プロジェクトは、IIJ DNSプラットフォームサービス (DPF) API を利用するためのGoモジュールである。
他の Go プロジェクトからインポートして利用することを前提とする。

[DPF-API](https://manual.iij.jp/dpf/dpfapi/)のOpenAPI仕様を元に自動生成されるコードを主に含む、低レベルのAPIクライアントである github.com/iij/dpf-goと、高レベルのユーティリティやラッパーを含むモジュールで構成される。

## Core Principles

### I. 生成コードと手書きコードの分離（NON-NEGOTIABLE）

`openapi.json` を単一の入力とし、API クライアントの実装は生成物として扱う。

- `api_*.go` / `model_*.go` / `client.go` / `configuration.go` / `response.go` /
  `utils.go` / `executeall_gen.go` は生成物であり、直接編集してはならない（MUST NOT）。
  変更は `openapi.json`、`templates/`、または `tools/genexecuteall` に対して行い、
  `make generate` で反映する。
- 生成物の先頭には `// Code generated by <使用したツール>. DO NOT EDIT.` を付与しなければ
  ならない（MUST）。
- 手書きファイル・手書きパッケージは `.openapi-generator-ignore` に登録して保護しなければ
  ならない（MUST）。新たに手書きファイルを追加した場合は同時に登録する。
- 再生成は `clean` を経由し、`openapi.json` から消えたスキーマ／API の古いファイルが
  残らない状態を保たなければならない（MUST）。
- `templates/` の独自カスタマイズ（`partial_header.mustache` の SPDX 表記、
  `client.mustache` の OpenTelemetry 計装）は生成物の前提であり、`make templates` で
  公式テンプレートへ戻した場合は再適用してから生成しなければならない（MUST）。

**根拠**: 生成物は再生成で失われる。手書きと生成物の境界を曖昧にすると、API 仕様更新の
たびに実装が消えるか、再生成を諦めて仕様と実装が乖離する。

### II. テストを伴う実装（NON-NEGOTIABLE）

手書きコードは単体テストを伴わなければ完成とみなさない。

- 手書きで追加・変更した公開挙動には単体テストを付与しなければならない（MUST）。
- `make test` は全モジュールに対し `-race -count=1` で実行され、ネットワークアクセスを
  必要としない状態を保たなければならない（MUST）。
- ビルド・テスト・各検査の対象モジュールは、リポジトリ内の `go.mod` の位置から
  導出しなければならない（MUST）。固定の列挙を持ってはならない（MUST NOT）。
  モジュールが増えたときに、対象から静かに漏れることを防ぐため。
  現在の実数は 5 件（本体と `misc/` 配下の 4 つ）である。
- 実際の DPF-API や権威 DNS サーバに依存するテストは `integration` ビルドタグで隔離し、
  `make test` の対象に含めてはならない（MUST NOT）。統合テストは API 呼び出しを直列化する
  （`-parallel 1`、`t.Parallel()` 不使用）。
- 生成物に対する単体テストは生成しない（`apiTests` / `modelTests` は false）。検証は
  手書きコードと統合テストで行う。

**根拠**: 本ライブラリは他者のゾーンとレコードを操作する。ネットワーク不要で常時実行できる
単体テストと、実 API に触れる統合テストを分離することで、日常の変更を安全かつ高速に検証できる。

### III. godoc とドキュメントの同時更新

利用者が godoc だけで使えることを、実装完了の条件とする。

- 公開されたパッケージ・型・関数・メソッド・エラー値には godoc 形式のコメントを
  付与しなければならない（MUST）。
- すべての Go ファイルの先頭には `// SPDX-License-Identifier: Apache-2.0` を
  置かなければならない（MUST）。
- 各パッケージは `doc.go` を持ち、用途・使い方・関連パッケージを記述する（MUST）。
- 利用者に見える挙動を変更した場合は、同じ変更のなかで `CHANGELOG.md`（Keep a Changelog
  形式）と、必要に応じて `README.md` を更新しなければならない（MUST）。
- 記述言語は日本語とする。

**根拠**: DPF-API は日本語の仕様書を持つ国内向けサービスであり、利用者は godoc を
一次情報として参照する。ドキュメントを後回しにすると、生成物の膨大なコードのなかで
手書きの意図が失われる。

### IV. ドメイン名の操作は miekg/dns を用いる

ドメイン名は正規化された FQDN 形式で扱うことを前提とする。

- ドメイン名の比較・結合・親子判定・正規化には `github.com/miekg/dns` の関数を
  用いなければならない（MUST）。`strings` 系の関数による自作処理を用いてはならない
  （MUST NOT）。
- ドメイン名を引数として受け取る公開関数は、内部で miekg/dns により正規化しなければ
  ならない（MUST）。呼び出し側に正規化を要求してはならない。

**根拠**: 末尾ドット、大文字小文字、エスケープ、ラベル長といった DNS 名の規則を
文字列操作で再実装すると、longest match やロック判定が静かに誤る。

### V. ライブラリとしての規律

本リポジトリはアプリケーションではなくライブラリである。呼び出し側の環境を侵さない。

- `unsafe` パッケージおよび unsafe な機能を使用してはならない（MUST NOT）。
- ライブラリ内でログを出力してはならない（MUST NOT）。異常は error として返し、
  観測は OpenTelemetry のトレースに委ねる。
- 挙動の既定値は保守的に定め、変更手段は Option として公開しなければならない（MUST）。
  既定値（レート制限 5 req/s・バースト 10、最大同時実行数 5、リトライ 3 回、
  タイムアウト 30 秒、ロック TTL 15 分、`ExecuteAll` の 1 ページあたり通常 10000 件・
  log 系 100 件）を変更する場合は破壊的変更として扱う。
- 本体（`github.com/iij/dpf-go`）が依存する外部パッケージを増やしてはならない
  （MUST NOT）。他パッケージに依存する optional な機能は `misc/` 配下に独立した
  `go.mod` を持つモジュールとして配置しなければならない（MUST）。

**根拠**: 依存とログと既定値は、ライブラリが利用者のビルドと運用へ漏らす副作用である。
本体を最小に保つことで、シークレット管理サービス連携のような重い依存を必要な利用者だけが
取り込める。

## セキュリティとリリース

- シークレットをリポジトリへ混入させてはならない（MUST NOT）。検査は betterleaks による
  三段構え（`pre-commit` / `pre-push` / CI）で行い、`main` へのマージには CI の
  `betterleaks` の成功を必須とする。
- betterleaks が未インストールの場合、hook は検査を省略して通過させてはならない（MUST NOT）。
  中断する。
- 検出値が本物であった場合は、履歴の書き換えより先にトークンの失効・再発行を
  行わなければならない（MUST）。一度 push された値は漏洩したものとして扱う。
- 誤検知を除外する場合は、シークレットでない理由を記載しなければならない（MUST）。
- CI のログに検出箇所そのものを出力してはならない（MUST NOT）。
- トークンは API リクエストのたびに `TokenProvider` を評価して取得する。別ホストへの
  リダイレクト時にトークンを付与してはならない（MUST NOT）。
- バージョン番号は Semantic Versioning に従う。`v1.0.0` に達するまでは、マイナー
  バージョンの更新に破壊的変更を含めてよい。
- リリースは `main` から行う（MUST）。`main` はマージ前ゲートをすべて満たしているため、
  リリース時点で改めて満たすべき品質ゲートは無い。
- リリースには SBOM（SPDX 2.3）を添付し、SLSA provenance attestation を付与する（MUST）。

## 開発ワークフローと品質ゲート

変更を `main` へ入れる前に、以下をすべて満たさなければならない（MUST）。

| ゲート | コマンド | 対象 |
|---|---|---|
| ビルド | `make build-all` | リポジトリ内のすべてのモジュール |
| 単体テスト | `make test` | リポジトリ内のすべてのモジュール（`-race -count=1`） |
| 整形・静的解析 | `make check-lint` | リポジトリ内のすべてのモジュール（`--build-tags=integration`） |
| ファイル冒頭の規約 | `make check-headers` | すべての Go ファイル（テスト・生成物を含む） |
| 依存ライセンス | `make check-licenses` | リポジトリ内のすべてのモジュールの依存 |
| 到達可能な既知脆弱性 | `make check-vuln` | リポジトリ内のすべてのモジュールの依存 |
| シークレット検査 | `make betterleaks` | 履歴と作業ツリー |

- `make check` は**上表のすべてのゲートをまとめて実行する**（MUST）。ここでいう「上表」とは、
