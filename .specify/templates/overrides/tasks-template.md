# タスク: [機能名]

**入力**: `/specs/[###-feature-name]/` の設計文書

**前提**: plan.md (必須)、spec.md (利用シナリオのため必須)、research.md、data-model.md、contracts/

**テスト**: 以下の例にはテストのタスクを含めている。テストは任意であり、機能仕様で明示的に求められた場合にのみ含めること。

**構成**: タスクは利用シナリオごとにまとめる。シナリオ単位で独立して実装・検証できるようにするためである。

## 書式: `[ID] [P?] [シナリオ] 説明`

- **[P]**: 並行して実行できる (異なるファイル、依存なし)
- **[シナリオ]**: このタスクが属する利用シナリオ (例: US1、US2、US3)
- 説明には正確なファイルパスを含めること

## パスの規約

- **単一プロジェクト**: リポジトリルートの `src/`、`tests/`
- **Web アプリ**: `backend/src/`、`frontend/src/`
- **モバイル**: `api/src/`、`ios/src/` または `android/src/`
- 以下のパスは単一プロジェクトを前提としている。plan.md の構成に合わせて調整すること

## 依存関係と実行順序

### フェーズ間の依存

- **準備 (フェーズ 1)**: 依存なし。ただちに開始できる
- **土台 (フェーズ 2)**: 準備の完了に依存する。すべての利用シナリオを塞ぐ
- **利用シナリオ (フェーズ 3 以降)**: いずれも土台のフェーズの完了に依存する
  - その後、シナリオは並行して進められる (人員がいれば)
  - あるいは優先度の順 (P1 → P2 → P3) に順次進める
- **仕上げ (最終フェーズ)**: 実施すると決めたすべての利用シナリオの完了に依存する

### 利用シナリオ間の依存

- **利用シナリオ 1 (P1)**: 土台 (フェーズ 2) の後に開始できる。他のシナリオに依存しない
- **利用シナリオ 2 (P2)**: 土台 (フェーズ 2) の後に開始できる。US1 と結合してもよいが、独立して検証できること
- **利用シナリオ 3 (P3)**: 土台 (フェーズ 2) の後に開始できる。US1 / US2 と結合してもよいが、独立して検証できること

### 各利用シナリオの内部

- テスト (含める場合) は実装より先に書き、失敗することを確認しなければならない
- モデルはサービスより先
- サービスはエンドポイントより先
- 中核の実装は結合より先
- 次の優先度に移る前に、そのシナリオを完了させる

### 並行できる箇所

- [P] を付けた準備のタスクはすべて並行できる
- [P] を付けた土台のタスクはすべて並行できる (フェーズ 2 の内部で)
- 土台のフェーズが完了すれば、すべての利用シナリオを並行して開始できる (人員が許すなら)
- ある利用シナリオの [P] を付けたテストはすべて並行できる
- あるシナリオ内の [P] を付けたモデルは並行できる
- 異なる利用シナリオは、異なる担当者が並行して進められる

## 実装の進め方

### まず MVP (利用シナリオ 1 のみ)

1. フェーズ 1 (準備) を完了する
2. フェーズ 2 (土台) を完了する (重要 — すべてのシナリオを塞ぐ)
3. フェーズ 3 (利用シナリオ 1) を完了する
4. **いったん止めて確認する**: 利用シナリオ 1 を単独で検証する
5. 準備ができていれば反映 / 提示する

### 増分で届ける

1. 準備 + 土台を完了する → 土台が整う
2. 利用シナリオ 1 を追加 → 単独で検証 → 反映 / 提示 (MVP)
3. 利用シナリオ 2 を追加 → 単独で検証 → 反映 / 提示
4. 利用シナリオ 3 を追加 → 単独で検証 → 反映 / 提示
5. 各シナリオは、それ以前のシナリオを壊さずに価値を足す

### 複数人で並行する場合

担当者が複数いる場合:

1. 準備 + 土台をチームで完了する
2. 土台が終わったら:
   - 担当者 A: 利用シナリオ 1
   - 担当者 B: 利用シナリオ 2
   - 担当者 C: 利用シナリオ 3
3. 各シナリオは独立して完了し、結合する

## 補足

- [P] のタスク = 異なるファイル、依存なし
- [シナリオ] のラベルは、追跡のためにタスクを特定の利用シナリオへ対応づける
- 各利用シナリオは、単独で完了・検証できること
- 実装前にテストが失敗することを確認する
- タスクごと、あるいは論理的なまとまりごとにコミットする
- どの関門でも作業を止めて、シナリオを単独で検証できる
- 避けること: 曖昧なタスク、同一ファイルの競合、独立性を壊すシナリオ間の依存
