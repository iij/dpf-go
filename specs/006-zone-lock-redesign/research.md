# 調査と決定: ゾーン単位の排他の見直し

**機能**: [spec.md](./spec.md) | **計画**: [plan.md](./plan.md) | **日付**: 2026-09-18

仕様に `[要明確化]` は無い。本ファイルは、仕様が実装に委ねた選択について、決定・根拠・
採らなかった案を記録する。D1 と D2 は実 API で確認した事実、D3 以降は設計の決定である。

## D1: 排他の根拠となる DPF-API の性質（実測）

**決定**: 一時レコード追加ロックは、レコードの新規追加に対する重複拒否を排他の根拠とする。
公開されてしまった専用レコードからの回復は、削除予定が重複判定に影響しないことを根拠とする。

**根拠**: 2026-09-18 に `internal/integration` の `TestLockRecordPremises` で実測した
（所要 65 秒、対象ゾーン `sub.sub.dns-tool-test.jp.`）。

| 状態 | 同名同 RRTYPE の POST | 応答 |
|---|---|---|
| 追加予定 (state=1) が存在 | 拒否 | 400 `duplicated` / `record` |
| 反映済み (state=0) が存在 | 拒否 | 400 `duplicated` / `record` |
| 削除予定 (state=2) が存在 | **成功** | 202 |

拒否は**同期の 400** で返り、`error_details` に `code=duplicated, attribute=record` が入る。
非同期 JOB の失敗として返るのではないため、重複と他の 400 を呼び出し側で判別できる。

追加予定の取り消し（`DELETE /records/{id}/changes`）ではレコードが消え、未反映件数が 0 に
戻ることも確認した。**一時ロックの解放にゾーン反映は要らない。** 削除予定にしてから追加
予定を入れると、同じ名前と RRTYPE で state=2 と state=1 の 2 件が別 ID で並存し、追加予定を
取り消して反映すると公開済みのレコードが消えることも確認した（FR-008 の回復経路）。

**採らなかった案**: SOA レコードのラベルだけで排他する現行方式。`PATCH` は同一ユーザからの
編集を拒否されないため、ラベルの読み取りから書き込みまでの間に競合すると両者が成功する。
D2 のとおり、この性質は方式の前提ではなく既知の欠陥である。

## D2: 同一ユーザ間で現行方式が成立しない理由（既知）

**決定**: 排他の強さを競合相手ごとに区別し、同一ユーザ間は本方式の手順で成立させる。

**根拠**: DPF-API は編集中のレコードへの**他ユーザ**からの編集を拒否するが、**同一ユーザ**
からの編集は拒否しない。003-utils-highlevel-api はこの区別を置かず「編集中のレコードは
重ねて編集できない」と記したため、1 つのアクセストークンで複数のプログラムを動かす最も
一般的な構成で排他が成立しない状態になっていた。加えて現行の `lockable` は「owner が
自分自身ならロック可能」と判定するため、既定 owner（ホスト名）が一致するプログラム同士は
互いをまったく排他しない。

**未確認**: 「他ユーザからの編集が拒否されること」は別ユーザのトークンを必要とするため
実測していない（FR-028 の (3)）。これは**現行の実装が既に依拠している性質**であり、本方式で
新たに依存を増やすものではない。「同一ユーザからの編集は拒否されない」は、既存の
`TestZoneMutex` が同一 owner でのロック再取得を通していることが示している。

## D3: 専用レコードの名前は最左ラベルのみを受け取る

**決定**: 専用レコードの名前は「最左ラベル + ゾーン名」で組み立てる。Option
（`WithLockRecordLabel`）で変更できるのは**最左ラベルのみ**とし、FQDN は受け取らない。
既定の最左ラベルは `_dpf-go-lock`。

**根拠**: FQDN を受け取ると、ゾーンの範囲外の名前を渡せてしまい `out_of_zone` で失敗する。
最左ラベルだけを受け取れば、範囲外の名前が**構造的に作れない**。名前の結合と正規化は
`miekg/dns`（`dns.Fqdn` / `dns.CanonicalName`）で行う（憲章 原則 IV）。

既定値を `_dpf-go-lock` とするのは、アンダースコアで始まる名前が通常のホスト名と衝突せず、
`_acme-challenge` のような用途別レコードの慣習に沿うためである。`TestLockRecordPremises` で
実際に登録・公開・削除できることを確認した。

**採らなかった案**: ゾーン名を利用者に渡させる（誤りの余地が増える）。ランダムな名前
（同じ名前に収束しないと排他にならないため不可）。

## D4: ゾーン名は SOA レコードから得る

**決定**: 専用レコードの名前に必要なゾーン名は、SOA レコードの `name` から得る。
`dpf.ZonesApi` は受け取らない。得たゾーン名は `Mutex` に保持し、2 回目以降の取得では
問い合わせを省く。

**根拠**: SOA レコードはゾーンの apex に 1 つだけ存在する（DNS の規則であり、仕様の前提でも
ある）。したがって SOA の名前はゾーン名そのものである。`Mutex` は既に SOA を読むため、
新たな API も新たなインターフェースも要らない。`NewMutex` の引数を増やさずに済むことが、
破壊的変更の範囲を最小にする。

ゾーン名の取得は**読み取りのみ**であり、排他が必要な read-modify-write には当たらない。
このため一時ロックの取得より前に行ってよい。判定と書き込み（`lockable` の評価と SOA の
`PATCH`）は必ず一時ロックの保護下で行う（[contracts/lock-record.md](./contracts/lock-record.md)
第 2 節の順序表）。

**採らなかった案**: `NewMutex` に `dpf.ZonesApi` を追加して `GetZone` で引く（引数が増え、
既存の呼び出しがすべて壊れる）。利用者にゾーン名を渡させる（D3 と同じ理由で却下）。

## D5: `dpf.RecordsApi` を 3 メソッド拡張する

**決定**: `interfaces.go` の `RecordsApi` に `PostRecord` / `DeleteRecord` /
`DeleteRecordChanges` を追加する。`NewMutex` のシグネチャは変えない。

**根拠**: 一時レコード追加ロックには追加（POST）、追加予定の取り消し
（DELETE `/changes`）、反映済みレコードの削除（DELETE）の 3 つが必要である。現在の
`RecordsApi` は `GetRecordList` と `PatchRecord` の 2 つしか持たない（`interfaces.go:19-22`）。

`*dpf.RecordsAPIService` は追加後のインターフェースも満たすため、`client.RecordsAPI` を
渡している利用者への影響は無い。影響を受けるのは `dpf.RecordsApi` を**自分で実装している**
利用者（主に試験用の差し替え）であり、これは破壊的変更として `CHANGELOG.md` に記載する。

**採らなかった案**: `*dpf.APIClient` を直接受け取る（テスト時の差し替えができなくなり、
`utils` 全体の作法（部分インターフェースを受け取る）から外れる）。`utils` 内に独自の
インターフェースを定義する（`dpf.ZonesApi` / `dpf.RecordsApi` が `interfaces.go` に
置かれている既存の作法に反する）。

## D6: 非同期の確立は `JobsApi` ではなくポーリングで待つ

**決定**: レコードの更新が反映されたことの確認は、`GetRecordList` のポーリングで行う。
`dpf.JobsApi`（`SyncWait`）は受け取らない。

**根拠**: 3 つの要求が 1 つの仕組みで満たせる。

1. **非同期の確立待ち**: レコードの更新は非同期（202）であり、`Lock` から復帰した時点で
   編集中状態が立っているとは限らない。現行の `patchLabels` は `AsyncResponse` を破棄して
   いるため待てていない（既存の `internal/integration/mutex_test.go` が `waitSOALabel` で
   独自に待っており、この欠落を裏付けている）。
2. **競合の検出**（FR-020）: 書き込んだ owner と奪ってよい時刻がそのまま読み出せるかを
   確認することで、後着に負けた場合を検出できる。
3. **引数を増やさない**: `JobsApi` を受け取ると `NewMutex` のシグネチャが変わる（D5 の
   方針に反する）。

**採らなかった案**: `JobsApi` を追加して `SyncWaitContext` で待つ（JOB の完了は分かるが、
「自分の値が残っているか」は別途読む必要があり、ポーリング 1 つで済む話が 2 つになる）。
`time.Sleep` の固定待ち（環境によって過剰にも不足にもなる）。

## D7: 受理が重なった場合は ID の昇順で勝者を決める

**決定**: 一時ロックの POST が受理された後、専用レコードが 2 件以上見つかった場合は、
レコード ID の昇順で最小の 1 件を勝者とする。自分の追加予定が勝者でなければ、それを
取り消して `ErrStillLock` を返す。

**根拠**: 重複拒否は同期の 400 で返る（D1）が、「受理されてから追加予定が実際に立つまで」の
間に別の POST が受理されるかは実測していない。両方が受理されると、同名同 RRTYPE の追加予定が
2 件並ぶ。このとき双方が譲ると誰も取得できず（ライブロック）、双方が続行すると排他が壊れる。
ID の昇順という**全員が同じ結論に至る規則**で勝者を一意に決めれば、どちらも起きない。
ID は API が発行する不変の値であり、両者が同じ一覧を読めば同じ勝者を選ぶ。

**採らなかった案**: 双方が取り消して再試行する（ライブロックの危険。`LockWait` の間隔が
揃っている場合に収束しない）。先に作られた方を勝者とする（作成時刻を返す項目が無い）。
この状況を異常として扱いエラーにする（回復手段が無くなる）。

## D8: `lockable` から owner 一致の分岐を外す

**決定**: ロック取得の判定は「奪ってよい時刻」だけで行う。owner が自分自身かどうかは見ない。
値が数値として解釈できない場合は保持者不明として取得を許す。保持期間の延長は `Renew` に
分離する。

**根拠**: owner 一致で取得を許す分岐が、同じ owner を持つ呼び出しをすべて通してしまう
（D2）。この分岐が残っている理由は、取得の再呼び出しを保持期間の延長の手段にしていたこと
だけである。延長を別の操作にすれば分岐は不要になる。

解釈できない値を奪取可とするのは、現行の実装では「不正な値 かつ owner が他者」の場合に
判定が恒久的に `false` となり、誰も取得できなくなるためである（FR-019、SC-006）。

**採らなかった案**: owner をインスタンスごとに一意にして分岐を残す（分岐が残る限り、
利用者が `WithOwner` で同じ値を渡した瞬間に排他が壊れる。値の一意性に安全性を依存させない）。

## D9: 保持者はインスタンスごとに一意とする

**決定**: 既定の owner は `<ホスト名の nodename>-<PID>-<ランダム 4 バイト>` とし、
`NewMutex` の呼び出しごとに生成する。ラベル値の上限 63 文字に収まるようホスト名側を
切り詰める。

**根拠**: 延長と解放は「自分が保持者である」ことを確認して行う（FR-023・FR-024）。owner が
プロセス単位だと、同一プロセス内の別インスタンスが互いの排他を延長・解放できてしまう。
インスタンス単位にすれば、ラベルの owner が保持者を一意に指す。ホスト名と PID を含めるのは、
人がラベルを見てどこから取られた排他かを識別できるようにするためである（FR-016）。
ランダム値を加えるのは、PID の再利用で終了したプロセスの排他を引き継がないためである。

排他そのものは「奪ってよい時刻」で成立しており（D8）、owner の一意性は延長・解放の宛先の
正しさにのみ効く。これは `WithOwner` で利用者が任意の値を渡しても排他が壊れないことを
意味する（壊れるのは延長・解放の宛先の判別だけ）。

**採らなかった案**: プロセス単位の owner + プロセス内の記録で重複取得を防ぐ（一時ロックを
導入すると重複の拒否が API 側で行われるため、プロセス内専用の仕組みは不要になる。
仕組みが 2 つあると、どちらが効いているのか分からなくなる）。ホスト名のみ（現行。D2 の欠陥）。

## D10: SOA の行が複数返った場合は state で一意に絞る

**決定**: `GetRecordList` が返す SOA のうち、state が 3（更新予定）の行があればそれを使い、
無ければ state が 0（反映済み）の行を使う。どちらも無い場合、または同じ state が複数ある
場合はエラーを返す。

**根拠**: 現行の `getSOA` は state=0 を**優先する**。ロックを保持している間の SOA は state=3
であり、もし一覧に state=0 または state=5（更新前の状態）の行も同時に現れるなら、現行の
実装は**ロックのラベルが付いていない古い行を掴む**。その結果 `lockable` が真となり、
保持中の排他を他者へ渡してしまう。ロックの判定材料は「いま編集中の行」でなければならない。

**実測（2026-09-18、`TestZoneMutex`）**: ロック前は state=0 の 1 行、ロック後は同じ ID の
state=3 の 1 行のみであった。state=5（更新前の状態）の行は `GetRecordList` には現れない。
したがって「反映済みの古い行を掴んで保持中の排他を他者へ渡す」事象は、現行の DPF-API では
発生しない。本決定は**将来 API の応答が変わった場合に備えた予防**であり、既存の欠陥の
修正ではない。判定は両方の応答に耐える形を維持する。

**採らなかった案**: 最初に見つかった行を使う（順序が保証されない）。1 行でなければ常に
エラー（state=5 が返る仕様だった場合にロックが機能しなくなる）。

## D11: 延長と解放は一時ロックを取らない

**決定**: 一時レコード追加ロックを取るのは取得（`Lock`）のときだけとする。`Renew` と
`Unlock` は、自分が保持者であることを確認したうえで奪ってよい時刻を書き換える。

**根拠**: 一時ロックが守るのは「ロックが空いているかを判定して書き込む」区間である。
`Renew` と `Unlock` は判定の対象が「自分が保持者か」であり、競合しうる相手は
「奪ってよい時刻を過ぎたと判断して奪った者」だけである。それは `Renew` が
`ErrNotLockHolder` を返すべき場合そのものであり、`verify` で検出できる。ここに一時ロックを
被せると API 呼び出しが 3 回増えるだけで、防げる誤りが増えない。

**採らなかった案**: すべての操作を一時ロックで囲む（費用に対して得るものが無い）。

## D12: 事前判定で一時レコード追加ロックの取得を省く

**決定**: 一時レコード追加ロックを取得する前に SOA レコードのラベルを読み、取得できないことが
既に分かっている場合はその時点で `ErrStillLock` を返す。専用レコードは作らない。取得できると
判断した場合のみ一時ロックへ進み、**取得後に改めて判定して**その結果で書き込みの可否を決める
（FR-001〜FR-003）。ラベル数の上限（FR-014）も事前判定で見る。

**根拠**: 専用レコードの追加は高価である。追加そのものに加えて、確立の確認、取り消し、
取り消しの確認が付いて回り、1 回の試行で 4 回の呼び出しになる。ところが**取得できない場合が
最も頻繁に起こる**。`LockWait` は取得できるまで試行を繰り返すため、他者が 15 分保持している
間の試行はすべて無駄な追加と取り消しになる。事前に読めば 1 回の問い合わせで終わる。

| 場面 | 事前判定なし | 事前判定あり |
|---|---|---|
| 取得できる（競合なし） | 7 回 | 8 回 |
| 他者が保持中 | 7 回 | **1 回** |
| `LockWait` の 1 試行あたり（保持中） | 7 回 | **1 回** |

取得できる場合は 1 回増える。競合していないときの 1 回と、待ち続けるときの毎回 6 回を
交換する取引であり、後者の方が重い。加えて、専用レコードを作らずに済むことは
**他者のゾーンの編集差分を汚さない**ことでもある（保持中の他者がゾーン反映を行う瞬間に
自分の専用レコードが公開される危険を、試行のたびに作らない）。

**安全性**: 事前判定は**取得を早く諦めるためだけ**に使う。判定が「取得できる」であっても、
一時ロックの取得後に改めて読んだ結果が「取得できない」であれば取得は失敗する（FR-003）。
事前判定と本判定の間に他者が取得しても、本判定が正しく弾く。逆方向の誤り（事前判定が
「取得できない」と言ったが実際には空いていた）は、その試行が失敗するだけであり、
`LockWait` の次の試行で取得できる。**取りこぼしは起きるが、二重取得は起きない。**

**採らなかった案**: 事前判定の結果で書き込みまで進む（読み取りから書き込みまでが保護されて
おらず、現行方式と同じ欠陥になる）。事前判定を行わない（`LockWait` の費用が 7 倍になる）。
専用レコードの有無も事前に読む（呼び出しが 1 回増えるが、重複拒否で分かることを先に
読み直すだけで得るものが無い）。

`README.md`（88 行目の「ゾーン単位ロック」という記述は本機能でも変わらない）、
`.github/workflows/`（ゲートの構成は変えない）。

**CI の owner 固定について**: `internal/integration/mutex_test.go` は owner を
`dpf-go-ci` に固定し、「owner が自分自身ならロック可能」という判定で中断からの自己回復を
得ている。D8 でこの判定を外すため、自己回復は次のいずれかに置き換わる。

1. ロックの TTL（テストでは 2 分）の経過を待つ
2. 一時ロックが残っていた場合は、その失効（既定 1 分）の経過で次の実行が取り消して進む
3. テストの後始末（`discardSOAChanges`）が SOA の未反映編集を破棄する。これは中断されない
   限り毎回走る

3 が働く限り 1 は発生しない。中断時は 1 または 2 を待つことになるため、README の説明を
書き換える。テストの TTL を短くすることは、ロックの有効期間そのものの検証を弱めるため
行わない。
