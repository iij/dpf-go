# データモデル: ゾーン単位の排他の見直し

**機能**: [spec.md](./spec.md) | **計画**: [plan.md](./plan.md) | **日付**: 2026-09-18

排他の状態は DPF-API 上のレコードとラベルとしてのみ保持する。プロセス内に状態を持たない。

## 1. ゾーンの排他 (SOA レコードのラベル)

対象ゾーンの SOA レコードに付ける 2 つのラベル。値はいずれも文字列（ラベルの値は 1〜63 文字）。

| ラベルキー | 内容 | 形式 | 由来 |
|---|---|---|---|
| `owner.lock.dpf-go` | 保持者 | 第 3 節の形式 | FR-012・FR-015 |
| `deadline.lock.dpf-go` | 奪ってよい時刻 | UTC Unixtime の 10 進表記 | FR-012・FR-018 |

- 2 つのキーは既存の `utils.LockOwnerLabelKey` / `utils.LockDeadlineLabelKey` をそのまま
  用いる。**キー名は変更しない。** 現行の実装が書いたラベルを新しい実装がそのまま読める
  ことが、切り替え時の前提である。
- SOA レコードに既に付いている他のラベルは保持する（FR-013）。`PATCH` はラベルの全置換で
  あるため、読み取った内容に 2 つを足して書き戻す。
- 排他を保持している間、SOA レコードは編集予定（state=3）になる。
- 解放は `deadline.lock.dpf-go` を現在時刻に更新することで行う。ラベルは削除しない
  （削除すると「一度も取得されていない」と区別できなくなる）。

### ラベル数の上限 (FR-014)

1 レコードに付けられるラベルは 10 個まで（DPF-API の `RecordLabels`、`maxProperties: 10`）。

```text
書き込み後のラベル数 = 既存のラベル数 + (ロックのキーのうち既存に無いものの数)
```

この値が 10 を超える場合は、書き込みを試みずに `ErrLabelLimit` を返す。既にロックの
ラベルが付いている場合は置き換えになるため増えない。結果として、利用者が SOA レコードへ
自由に付けられるラベルは 8 個までとなる。

## 2. 一時レコード追加ロック (専用レコード)

排他を取得する区間を保護するための短命なレコード。追加予定（state=1）の状態でのみ存在し、
排他が取得できた時点で取り消される。権威サーバへは公開されない。

| 項目 | 既定値 | 変更手段 |
|---|---|---|
| 名前 | `_dpf-go-lock.<ゾーン名>` | `WithLockRecordLabel`（最左ラベルのみ） |
| RRTYPE | `TXT` | `WithLockRecordContent` |
| rdata | `"dpf-go lock"`（TXT の規則により引用符で囲む） | `WithLockRecordContent` |
| TTL | 300 | 変更手段を設けない（公開されない値であり意味を持たない） |
| ラベル | 第 1 節と同じ 2 キー。`deadline` は**この専用レコード自身の失効時刻** | `WithLockRecordTTL`（既定 1 分） |

- ゾーン名は SOA レコードの `name` から得る（[research.md](./research.md) D4）。FQDN の
  組み立てと比較は `miekg/dns` で行う（憲章 原則 IV）。
- 名前は最左ラベルのみを受け取るため、ゾーンの範囲外にならない（同 D3）。
- ラベルの `deadline` は「この一時ロックを奪ってよい時刻」であり、第 1 節の
  「排他を奪ってよい時刻」とは別の対象を指す。キーを共有するのは、どちらも同じ意味
  （奪ってよい時刻）でありレコードごとに独立しているためである。
- RRTYPE と rdata を 1 つの Option で対にして受け取るのは、RRTYPE ごとに妥当な rdata が
  異なり、独立に変更できないためである。

## 3. 保持者 (owner)

```text
<ホスト名の nodename>-<PID>-<ランダム 4 バイトの 16 進>
例: web01-31415-9f3c2a10
```

- `NewMutex` の呼び出しごとに生成する。**インスタンスごとに一意**である（FR-015、
  [research.md](./research.md) D9）。
- ホスト名は最初の `.` より前のみを用い、全体が 63 文字に収まるようホスト名側を切り詰める。
- ホスト名を取得できない場合は `dpf-go`（既存の `DefaultLockOwner`）を用いる。
- `WithOwner` で任意の値を指定できる。一意でない値を指定しても**排他は壊れない**
  （排他は奪ってよい時刻で成立する）。壊れるのは延長・解放の宛先の判別だけである。
  この点を godoc に明記する。

## 4. Mutex の設定と内部状態

| 項目 | 種別 | 既定値 | 対応する要件 |
|---|---|---|---|
| `zoneID` | 設定（必須） | — | — |
| `owner` | 設定 | 第 3 節 | FR-015・FR-016 |
| `ttl` | 設定 | 15 分 | 003 から継承 |
| `lockRecordTTL` | 設定 | 1 分 | FR-005・FR-010 |
| `verifyTimeout` | 設定 | 10 秒 | FR-020・FR-021 |
| `lockRecordLabel` | 設定 | `_dpf-go-lock` | FR-011 |
| `lockRecordRrtype` / `lockRecordRdata` | 設定 | `TXT` / `"dpf-go lock"` | FR-011 |
| `zoneName` | 内部（キャッシュ） | 未取得 | [research.md](./research.md) D4 |
| `now` | 内部（試験用の差し替え） | `time.Now` | — |

`zoneName` 以外の内部状態を持たない。排他の保持状況をプロセス内に記録しない
（記録すると、それと API 上の状態が食い違ったときにどちらが正しいか決められなくなる）。

## 5. レコードの状態遷移

DPF-API の state は 0=反映済み / 1=追加予定 / 2=削除予定 / 3=更新予定 / 5=更新前の状態。

### 専用レコード

```text
(無)
 │ 追加 (POST)
 ▼
追加予定 (1) ──── 取り消し (DELETE /changes) ────▶ (無)      ← 通常の解放
 │
 │ 他者のゾーン反映
 ▼
反映済み (0) ──── 削除 (DELETE) ────▶ 削除予定 (2)            ← FR-008 の回復経路
                                        │ 同名の追加 (POST)
                                        ▼
                              削除予定 (2) と追加予定 (1) が並存
                                        │ 追加予定の取り消し
                                        ▼
                              削除予定 (2) のみ
                                        │ 利用者のゾーン反映
                                        ▼
                                      (無)
```

削除予定が重複判定に影響しないことは実測済みである（[research.md](./research.md) D1）。

### SOA レコード

```text
反映済み (0) ──── ラベルの書き込み (PATCH) ────▶ 更新予定 (3)
更新予定 (3) ──── ラベルの書き込み (PATCH) ────▶ 更新予定 (3)   ← 延長・解放
更新予定 (3) ──── 利用者のゾーン反映 ────▶ 反映済み (0)          ← ラベルは維持される
```

SOA レコードは常に 1 つ存在し、削除もできない（仕様の前提）。判定材料としては state=3 の
行を優先し、無ければ state=0 の行を用いる。どちらも無い場合、または同じ state が複数ある
場合はエラーとする（同 D10）。

## 6. 判定表

### 事前判定 (FR-002・FR-003)

一時レコード追加ロックを取得する前に、SOA のラベルに対して下の「排他の取得」と同じ判定と、
第 1 節のラベル数の判定を行う。

| 事前判定の結果 | 動作 |
|---|---|
| 取得できない | 専用レコードを作らず `ErrStillLock` を返して終える |
| ラベル数が上限を超える | 専用レコードを作らず `ErrLabelLimit` を返して終える |
| 取得できる | 一時レコード追加ロックへ進み、取得後に**同じ判定をやり直す** |

事前判定の結果は書き込みの根拠にしない。判定と書き込みの間に他者が取得しうるためである
（[research.md](./research.md) D12）。

### 一時レコード追加ロックの取得 (FR-004〜FR-008)

| 専用レコードの状態 | 判定 | 動作 |
|---|---|---|
| 存在しない | 取得できる | 追加する |
| 追加予定、失効時刻を過ぎていない | 取得できない | `ErrStillLock` |
| 追加予定、失効時刻を過ぎている | 取得できる | 取り消してから追加する（1 回のみ） |
| 追加予定、失効時刻が解釈できない | 取得できる | 同上（保持者不明として扱う） |
| 反映済み | 取得できる | 削除予定にしてから追加する。削除予定は残す |
| 削除予定のみ | 取得できる | 追加する（重複判定に影響しない） |
| 追加予定が 2 件以上 | ID の昇順で最小の 1 件が勝者 | 自分が勝者でなければ取り消して `ErrStillLock` |

### 排他の取得 (FR-017〜FR-019)

| SOA のラベルの状態 | 判定 |
|---|---|
| `deadline` が無い | 取得できる |
| `deadline` が数値として解釈できない | 取得できる（保持者不明） |
| `deadline` を現在時刻が過ぎている | 取得できる（owner が誰であっても） |
| `deadline` を過ぎていない | 取得できない（`ErrStillLock`）。**owner が自分自身でも同じ** |

### 延長と解放 (FR-023・FR-024)

| SOA のラベルの状態 | `Renew` | `Unlock` |
|---|---|---|
| `owner` が自分 | 奪ってよい時刻を進める | 奪ってよい時刻を現在時刻にする |
| `owner` が他者 | `ErrNotLockHolder` | `ErrNotLockHolder`（他者の排他を変更しない） |
| `deadline` が無い | `ErrNotLockHolder` | 何もせず成功（FR-025） |

## 7. 検証規則の一覧

| 対象 | 規則 | 違反時 | 要件 |
|---|---|---|---|
| ラベル数 | 書き込み後に 10 を超えない | `ErrLabelLimit`（書き込み前に判定） | FR-014 |
| ラベル値 | 1〜63 文字 | owner は生成時に切り詰める | 第 3 節 |
| 専用レコードの名前 | ゾーンの範囲内 | 最左ラベルのみ受け取るため構造的に発生しない | FR-011 |
| SOA の行 | state=3 または state=0 が 1 件に定まる | エラー（黙って選ばない） | [research.md](./research.md) D10 |
| 書き込みの反映 | 自分が書いた owner と deadline が読み出せる | `ErrStillLock`（取得）/ `ErrNotLockHolder`（延長） | FR-020 |
| 一時ロックの解放 | 取得の成否によらず必ず行う | 解放に失敗した場合は取得を失敗として返す | FR-009 |
| ゾーン反映 | 取得・延長・解放では行わない | — | FR-024 |
