# 実装計画: ゾーン単位の排他の見直し

**ブランチ**: `006-zone-lock-redesign` | **日付**: 2026-09-18 | **仕様**: [spec.md](./spec.md)

**入力**: 次の機能仕様 `/specs/006-zone-lock-redesign/spec.md`

**注記**: `ブランチ` は `.specify/feature.json` が示す機能ディレクトリ名である。実際の
git ブランチは `main`（`before_specify` フックが無いためブランチは作成していない）。

## 概要

`utils.Mutex` の排他が、1 つのアクセストークンを複数のプログラムから使う構成で成立して
いない。DPF-API は編集中のレコードへの他ユーザからの編集を拒否するが、同一ユーザからの
編集は拒否しないため、SOA ラベルの読み取りから書き込みまでの間に競合すると両者が取得に
成功する。加えて「owner が自分自身ならロック可能」という判定が、既定 owner（ホスト名）の
一致するプログラム同士の排他を完全に無効にしている（[research.md](./research.md) D2）。

これを、ラベルへ書き込む区間自体を排他することで解決する。技術的な方針は 6 つある。

1. **レコードの新規追加に対する重複拒否を排他の原始手段として使う。** 専用レコードを
   追加予定の状態で作る操作を**一時レコード追加ロック**とし、その保護下で SOA ラベルの
   排他を取得して、取得できたら解放する。重複拒否は編集者が誰かに依らないため同一ユーザ
   同士でも効く。**この性質は実 API で確認済みである**（[research.md](./research.md) D1、
   `TestLockRecordPremises`、2026-09-18）。
2. **`NewMutex` のシグネチャを変えない。** 専用レコードの名前に必要なゾーン名は SOA
   レコードの `name` から得る（同 D4）。非同期の確立待ちと競合の検出は `GetRecordList` の
   ポーリング 1 つで兼ねる（同 D6）。追加で必要になるのは `dpf.RecordsApi` への 3 メソッド
   追加だけであり、`client.RecordsAPI` を渡している利用者への影響は無い（同 D5）。
3. **`lockable` から owner 一致の分岐を外し、延長を `Renew` に分離する。** 分岐が残る限り、
   利用者が同じ owner を渡した瞬間に排他が壊れる。**安全性を値の一意性に依存させない**
   （同 D8）。owner はインスタンスごとに一意とするが、それが効くのは延長・解放の宛先の
   判別のみである（同 D9）。
4. **公開されてしまった専用レコードから自力で回復する。** 削除予定にしてから追加予定を
   入れる。削除予定は取り消さずに残すため、利用者の次のゾーン反映で公開済みのレコードが
   消える。ライブラリからゾーン反映は行わない（FR-008、同 D1）。
5. **高価な追加の前に安く諦める。** 一時ロックを取得する前に SOA を読み、取得できないと
   分かっている場合は専用レコードを作らずに終える。取得できない場合が最も頻繁に起こり、
   `LockWait` の試行 1 回あたりの呼び出しが 7 回から 1 回になる。**事前判定は早く諦める
   ためだけに使い、書き込みの根拠にはしない**（同 D12）。
6. **判定材料は「いま編集中の SOA の行」に限る。** 現行の `getSOA` は state=0 を優先する
   ため、編集中の行と反映済みの行が同時に返る仕様であった場合、ロックのラベルが付いて
   いない古い行を掴んで保持中の排他を他者へ渡す。state=3 を優先する形に改める（同 D10）。

排他の強さは競合相手によって異なり、それを godoc に明記する（FR-029）。別ユーザとの間は
DPF-API がサーバ側で保証する。同一ユーザとの間は上記 1 の手順で成立する。同一プロセス内の
別インスタンスも、重複拒否が API 側で行われるため同じ仕組みで排他される（同 D9 の
「採らなかった案」）。

## 技術的な前提

**言語 / バージョン**: Go 1.27（`go.mod` は `go 1.27.0`）

**主要な依存**: 追加なし。本体の `go.mod` は変更しない。実装で新たに使う標準ライブラリは
`crypto/rand` と `encoding/hex`（owner のランダム部分、[research.md](./research.md) D9）。
ドメイン名の結合・正規化は既存の依存である `github.com/miekg/dns` を用いる（憲章 原則 IV）

**保存先**: 該当なし。排他の状態は DPF-API 上のレコードとラベルとして保持する
（[data-model.md](./data-model.md)）。プロセス内に状態を持たない

**テスト**: 単体テストは `go test ./... -race -count=1`（既存の `make test`）。継ぎ目は
既存の `httptest` による模擬サーバ（`utils/lock_test.go` の `lockServer`）を拡張して使う。
実 API の確認は `make test-integration`（`internal/integration`）

**対象環境**: 本ライブラリを取り込む Go プログラム全般。想定する競合の範囲は、同一ホストの
別プロセス、別ホストの別プロセス、同一プロセス内の別インスタンス、および別ユーザ

**プロジェクト種別**: Go ライブラリ（既存パッケージ `utils` の挙動変更。新規モジュールなし）

**性能目標**: 取得 1 回あたりの API 呼び出しは、取得できる場合が 8 回、他者が保持中で
取得できない場合が **1 回**（事前判定のみ。research.md D12）。内訳は
[contracts/lock-record.md](./contracts/lock-record.md) 第 2 節。既定のレート制限（5 req/s）
では取得できる場合が約 1.6 秒に加えて非同期の確立待ち（`verify`）の実測時間、取得できない
場合が 1 回分である。`LockWait` で待ち続ける間の費用は試行あたり 1 回に収まる。
現行は取得の可否によらず 2 回であるため、取得できる場合は増える。**排他が成立していない
2 回より、成立する 8 回を選ぶ**

**制約**:
- 本体の `go.mod` に依存を追加しない（憲章 原則 V）
- ライブラリ内でログを出力しない。`unsafe` を使わない（同）
- 単体テストはネットワークを必要としない（憲章 原則 II）

  （ロック TTL 15 分）は変えない。新設する既定値は一時ロックの失効 1 分、反映確認の上限
  10 秒、専用レコードの最左ラベル `_dpf-go-lock`、RRTYPE は TXT
- 排他の取得・延長・解放でゾーンへの反映を行わない（FR-024、003 から継承）
- 専用レコードの名前はゾーンの範囲外になり得ない形で受け取る（最左ラベルのみ。同 D3）
- SOA のラベルは 10 個まで。排他が 2 つ使うため、上限を超える場合は書き込み前に失敗する
  （FR-013・FR-014）

**規模 / 範囲**: 要件 29 件（FR-001〜FR-031）／成功基準 7 件（SC-001〜SC-007）。
新規に公開するものは、メソッド 1 件（`Renew`）、Option 4 件、番兵エラー 2 件、定数 3 件。
挙動が変わる公開要素は 3 件（`Lock` / `Unlock` / 既定 owner）。`dpf.RecordsApi` に

新規ファイルは無い

**要明確化**: なし。仕様に未解決のマーカーは無い。仕様が実装に委ねた選択は

**API 呼び出し回数について**: 憲章に呼び出し回数の規範は無いが、原則 V の
「呼び出し側の環境を侵さない」に関わるため記録する。取得できる場合は 2 回から 8 回へ増え、
取得できない場合は 2 回から 1 回へ減る（research.md D12）。増える側は既定のレート制限
（5 req/s）の下で約 1.6 秒であり、15 分の保持期間に対して無視できる。排他は「編集の前に
1 度だけ」行う操作であって、レコードごとに行うものではない。減る側は `LockWait` で待ち続ける
間ずっと効くため、実運用での総呼び出し回数はむしろ下がる。

**破壊的変更の一覧**（`CHANGELOG.md` に記載する内容）:

1. `Lock` が再入できなくなる。保持中の再取得は `ErrStillLock` を返す。保持期間の延長は
   新設の `Renew` を使う（FR-017）
2. 既定 owner の形式が「ホスト名の nodename」から
   「nodename-PID-乱数」へ変わり、`NewMutex` の呼び出しごとに異なる値になる（FR-015）
3. `Unlock` と `Renew` が保持者の確認を伴う。保持者でない場合は `ErrNotLockHolder` を返し、
   他者の排他を変更しない（FR-023・FR-024）
4. `dpf.RecordsApi` に 3 メソッドが増える。自分で実装している利用者は追随が必要
   （research.md D5）
5. 取得の判定が奪ってよい時刻のみになる。owner が自分自身であることは取得の条件ではなく
   なった（FR-017、research.md D8）

## 複雑さの記録

> **憲章への適合確認で、正当化が必要な逸脱があった場合にのみ記入する**

憲章違反なし。ただし、単純さを損なう選択を 2 つ意図して行っているため記録する。

| 選択 | 必要な理由 | より単純な代替案を採らない理由 |
