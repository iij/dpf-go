# 機能仕様: 憲章準拠のツール整備

**機能ブランチ**: `specify`

**作成日**: 2026-09-09

**状態**: ドラフト

**憲章**: v2.0.0 の規範に整合（母集団・作業ツリー不変・版の単一出典・脆弱性のマージ前ゲート化）

**入力**: 利用者による記述: "憲章 v1.1.0 で追加した MUST のうち、実装が追随していない 4 件（SPDX ヘッダの補完と検査、golangci-lint 設定の固定、govulncheck の組み込み、依存ライセンスの機械的検査）を、人手のレビューに頼らず機械的に強制されるゲートとして整備する"

## 利用シナリオと検証 *(必須)*

### 利用シナリオ 1 - ファイル冒頭の規約違反が機械的に止まる (優先度: P1)

コントリビューターが新しい Go ファイルを追加する。ライセンスヘッダを書き忘れたまま変更を提出すると、レビューを待つ前に検査が失敗し、どのファイルで欠けているかが示される。ヘッダを足せば通る。同じ検査が、ファイル全体に効く位置に置かれた抑制指示も止める。どちらもファイル冒頭の規約であり、同じ検査が扱う。

**この優先度の理由**: 憲章の他の 3 件は「将来の混入を防ぐ」ものだが、これは**現に違反している**唯一の項目である（`internal/integration/` の 8 ファイルで欠落）。憲章は「欠けたファイルをマージしないこと (MUST NOT)」と定めているため、この状態が続く限り憲章と実装が矛盾したままになる。また 4 件のうち最も実装が小さく、単独で完結する。最初に実装されるゲートであるため、4 種の検査が共有する性質（手元での再現、未導入時の中断、省略理由の記録、対象モジュールの導出）もここで確立される。

**独立した検証**: 現在の作業ツリーに対して検査を実行し、8 ファイルが列挙されることを確認できる。ヘッダを付与したのち再実行して 0 件になることを確認できる。ヘッダを欠いたファイルを 1 つ作って検査が失敗することも確認できる。`package` 宣言より前に抑制指示を置いたファイルを作れば、理由と対象を伴っていても検出されることを確認できる。共有される性質は、検査ツールを外した環境での実行、およびモジュールを 1 つ増やした状態での実行によって確認できる。

**受け入れシナリオ**:

1. **前提** SPDX ヘッダを欠いた Go ファイルが作業ツリーにある、**操作** 検査を実行する、**結果** 検査は失敗し、欠落しているファイルのパスがすべて列挙される
2. **前提** すべての Go ファイルにヘッダがある、**操作** 検査を実行する、**結果** 検査は成功する
3. **前提** ヘッダを欠いたファイルを含む変更が提出された、**操作** 統合前の検査が走る、**結果** その変更は統合できない
4. **前提** テストファイル、またはビルドタグによって既定のビルド対象から外れるファイルがヘッダを欠いている、**操作** 検査を実行する、**結果** それらも検出される
5. **前提** API 仕様から生成物を再生成した、**操作** 検査を実行する、**結果** 生成物のヘッダは維持されており検査は成功する
6. **前提** `package` 宣言より前に抑制指示が置かれたファイルがある（理由と対象の記載を伴う場合を含む）、**操作** 検査を実行する、**結果** 検査は失敗し、そのファイルが列挙される

**受け入れシナリオ（4 種の検査に共通する性質。最初のゲートとしてここで確立する）**:

7. **前提** 検査ツールが実行環境に存在しない、**操作** 検査を実行する、**結果** 検査は中断し、成功扱いにならない
8. **前提** 統合前の検査が何らかの事情で検査を省略した、**操作** 実行結果を見る、**結果** 省略した理由がログと実行サマリに残っている
9. **前提** 独立したモジュールが新しくリポジトリに追加された、**操作** 検査を実行する、**結果** 対象一覧を書き換えなくてもそのモジュールが検査対象に含まれる
10. **前提** clone 直後の開発者、**操作** 手元で単一のコマンドを実行する、**結果** 統合前の検査と同じ結果が再現される

### 利用シナリオ 2 - 許容外ライセンスの依存が持ち込めない (優先度: P2)

コントリビューターが新しい依存を追加する。その依存自身、またはその依存の依存に許容リスト外のライセンスが含まれていると、検査が失敗し、どの依存のどのライセンスが問題かが示される。

**この優先度の理由**: ライセンスの不備は、機能の欠陥と違って利用者側で顕在化し、後から回収できない。とりわけ本プロジェクトはライブラリであり、許容外の依存は利用者の配布物全体に条件を及ぼす。混入は依存の依存として静かに起きるため、人手の確認では取りこぼす。P1 の次に置くのは、影響が本リポジトリの外（利用者の法務判断）に及ぶ唯一の項目だからである。

**独立した検証**: 現在の依存構成に対して検査を実行し、許容リスト外の検出が 0 件であることを確認できる。許容外ライセンスの依存を一時的に追加して検査が失敗することも確認できる。

**受け入れシナリオ**:

1. **前提** すべての依存のライセンスが許容リストに収まっている、**操作** 検査を実行する、**結果** 検査は成功する
2. **前提** 許容リスト外のライセンスを持つ依存が追加された、**操作** 検査を実行する、**結果** 検査は失敗し、対象の依存名・バージョン・ライセンスが示される
3. **前提** ライセンスを判別できない依存が追加された、**操作** 検査を実行する、**結果** 検査は失敗する（判別不能は「許容」として扱われない）
4. **前提** 許容リスト外のライセンスが依存の依存（間接依存）として入った、**操作** 検査を実行する、**結果** 検査は失敗し、どの直接依存を経由して入ったかが示される
5. **前提** ソース提供義務のあるライセンス（MPL-2.0）の依存がある、**操作** 検査を実行する、**結果** 検査は成功するが、義務を伴う依存として区別して報告される
6. **前提** ソース提供義務のあるライセンスの依存が本体モジュールに入った、**操作** 検査を実行する、**結果** 検査は失敗する（義務のある依存は optional な機能のモジュールに隔離されていなければならない）

### 利用シナリオ 3 - 静的解析の結果が手元と統合前で一致する (優先度: P3)

コントリビューターが手元で静的解析を実行し、指摘を解消してから変更を提出する。統合前の検査でも同じ指摘が出ないため、手元で通ったものが統合前で落ちることがない。指摘を抑制する場合は理由の記載が求められる。

**この優先度の理由**: 現在は設定が固定されていないため、実行する場所と時期によって指摘が変わりうる。手元で通ったものが後で落ちると、コントリビューターは指摘を「環境の差」として扱い、ツールの判断を信頼しなくなる。憲章が「ツールの判断を人の裁量で覆さないこと」を求める前提として、まず判断が再現可能である必要がある。

**独立した検証**: 同一コミットに対して手元と統合前の検査を実行し、指摘の集合が一致することを確認できる。理由のない抑制コメントを 1 つ入れて検査が失敗することも確認できる。ファイル全体に効く抑制の検出は 利用シナリオ 1 が担うため、本 story の検証には含めない。

**受け入れシナリオ**:

1. **前提** 有効な検査項目とそのバージョンが設定ファイルで固定されている、**操作** 同一コミットに対して手元と統合前で検査を実行する、**結果** 指摘の集合は一致する
2. **前提** 理由の記載がない抑制コメントがある、**操作** 検査を実行する、**結果** 検査は失敗する
3. **前提** 対象 linter を明示しない抑制コメントがある、**操作** 検査を実行する、**結果** 検査は失敗する
4. **前提** ビルドタグによって既定のビルド対象から外れるコードがある、**操作** 検査を実行する、**結果** そのコードも検査対象に含まれる
5. **前提** 整形が崩れたファイルがある、**操作** 検査を実行する、**結果** 検査は失敗し、対象ファイルが列挙される

### 利用シナリオ 4 - 到達可能な既知脆弱性を抱えたまま統合できない (優先度: P4)

コントリビューターが変更を提出する。依存に既知の脆弱性があり、かつ本プロジェクトのコードからそこへ到達しうる場合、その変更は統合できない。到達しない脆弱性では止まらない。リリースは統合済みの状態から行うため、この時点で止めればリリース時の条件も満たされる。

**この優先度の理由**: 他の 3 つのゲートは、現に違反している項目（ヘッダ欠落）か、リポジトリ内の状態だけで判定できる項目である。これだけは判定が外部の脆弱性データベースの状態に依存し、コード変更と無関係に結果が変わる。最も後に置くのは、他の 3 つを先に固めてから、外部要因で止まりうるゲートを足すほうが、止まった原因の切り分けが容易になるからである。

**独立した検証**: 現在の依存構成に対して検査を実行し、到達可能な報告が 0 件であることを確認できる。統合前の検査で失敗した場合に変更が統合できないことも確認できる。

**受け入れシナリオ**:

1. **前提** 到達可能な既知脆弱性がない、**操作** 統合前の検査が走る、**結果** 検査は成功し、変更は統合できる
2. **前提** 到達可能な既知脆弱性がある、**操作** 統合前の検査が走る、**結果** 検査は失敗して変更は統合できず、脆弱性の識別子と到達経路が示される
3. **前提** 依存に既知脆弱性があるが本プロジェクトのコードから到達しない、**操作** 統合前の検査が走る、**結果** 検査は成功する
4. **前提** 新しい脆弱性の公表により、脆弱性を含まない変更が止まった、**操作** 対処を行う、**結果** 依存の更新または到達しない形への修正によって通る。検査の迂回・一時的な無効化・報告のみへの格下げでは通らない

---

### 境界的な状況

- 検査ツールが実行環境に入っていない場合はどうなるか？ → 検査を省略して成功扱いにしてはならない。既存のシークレット検査 hook と同じく中断する。
- 統合前の検査が何らかの事情で検査を省略した場合、その事実はどう伝わるか？ → 省略した理由をログと実行サマリに残す。「省略されたが成功に見える」状態を作らない。
- 独立した `go.mod` を持つモジュールが新しく追加された場合、検査対象から漏れないか？ → モジュールの一覧を固定で列挙するのではなく、リポジトリ内の `go.mod` から導出する。
- 生成物のヘッダはどこから来るのか？ → 生成テンプレート由来である。テンプレートを公式版へ戻した場合、再生成でヘッダが失われうる。
- ライセンスが複数指定されている依存（デュアルライセンス）はどう判定するか？ → 許容リストに収まる選択肢が一つでもあれば許容とし、選択したライセンスを報告に残す。
- 新しい脆弱性が公表され、コード変更なしに検査が失敗するようになった場合はどうなるか？ → 統合が止まる。対処は依存の更新、または脆弱な経路へ到達しない形への修正である。検査を迂回して通すことはできない。
- 依存の更新でライセンスが変わった場合に気づけるか？ → 検査は依存の版ごとにライセンスを取得するため、更新時に再判定される。
- 抑制コメントの「理由」がどの程度であれば通るか？ → 機械的に判定できるのは理由の有無のみである。内容の妥当性はレビューが判断する。

## 要件 *(必須)*

### 機能要件

**ファイル冒頭の規約**

- **FR-001**: システムは、リポジトリ内のすべての Go ファイルの先頭行に `// SPDX-License-Identifier: Apache-2.0` があることを機械的に検査できなければならない
- **FR-002**: 検査対象には、テストファイル、ビルドタグによって既定のビルド対象から外れるファイル、および生成物を含めなければならない
- **FR-003**: 検査は、リポジトリ内のすべてのモジュールを対象としなければならない
- **FR-004**: 欠落を検出した場合、検査は失敗し、欠落しているファイルのパスをすべて列挙しなければならない
- **FR-005**: 現に欠落している `internal/integration/` の 8 ファイルにヘッダを付与し、検査が 0 件で通る状態にしなければならない
- **FR-006**: 生成物のヘッダは、API 仕様からの再生成後も維持されなければならない
- **FR-018**: システムは、`package` 宣言より前に置かれた抑制指示を検出し、検査を失敗させなければならない。この位置にある抑制はファイル全体に効くためである。理由や対象 linter の記載を伴う場合も検出しなければならない。対象行に限定された抑制は本要件の対象外とし、その理由の有無は FR-017 が扱う

**依存ライセンス**

- **FR-007**: システムは、各モジュールが**実際に import しているパッケージ**について、間接依存（依存の依存）を含めてライセンスを収集し、許容リストと照合できなければならない。宣言されているが import されていない依存を含むモジュールグラフ全体を母集団としてはならない
- **FR-008**: 許容リストは、表示のみで足りるもの（Apache-2.0 / MIT / BSD-2-Clause / BSD-3-Clause / ISC）と、ソース提供義務を伴うもの（MPL-2.0）を区別して保持しなければならない
- **FR-009**: 許容リスト外のライセンス、およびライセンスを判別できない依存を検出した場合、検査は失敗しなければならない。判別不能を「許容」として扱ってはならない
- **FR-010**: 検出時は、依存名・バージョン・判定されたライセンス・どの直接依存を経由して入ったかを示さなければならない
- **FR-011**: ソース提供義務を伴うライセンスの依存は、許容として通しつつ、義務を伴う依存として区別して報告しなければならない
- **FR-012**: ソース提供義務を伴うライセンスの依存が本体モジュールに現れた場合、検査は失敗しなければならない（optional な機能のモジュールへの隔離を維持するため）
- **FR-013**: 許容リストは、憲章の許容リストと一対一で対応し、リポジトリ内の単一の場所で定義されなければならない

**静的解析と整形**

- **FR-014**: 有効な検査項目とそのバージョンは、リポジトリ内の設定ファイルで固定されなければならない
- **FR-015**: 手元と統合前の検査は、同一の設定・同一のバージョンで動作しなければならない。同一コミットに対する指摘の集合が一致しなければならない
- **FR-016**: 検査対象には、ビルドタグによって既定のビルド対象から外れるコードを含めなければならない
- **FR-017**: 指摘の抑制に理由の記載がない場合、検査は失敗しなければならない
- **FR-019**: 整形が規定と一致しないファイルがある場合、検査は失敗し、対象ファイルを列挙しなければならない

**脆弱性**

- **FR-020**: システムは、依存の既知脆弱性のうち本プロジェクトのコードから到達しうるものを、すべてのモジュールについて検査できなければならない
- **FR-021**: 到達可能な既知脆弱性が報告される状態では、変更を統合できてはならない。リリースは統合済みの状態から行うため、リリース時点の条件もこれによって満たされる
- **FR-022**: 検査の迂回、一時的な無効化、報告のみへの格下げによって、到達可能な既知脆弱性を抱えた変更を統合できてはならない。新しい脆弱性の公表によって脆弱性を含まない変更が止まった場合の対処は、依存の更新、または脆弱な経路へ到達しない形への修正でなければならない
- **FR-023**: 検出時は、脆弱性の識別子と到達経路を示さなければならない

**共通**

- **FR-024**: 4 種の検査はいずれも、clone 直後の開発者が手元で単一のコマンドから実行でき、統合前の検査と同じ結果を再現できなければならない
- **FR-030**: 一括実行の入口は、変更を統合する前に満たすべき**すべてのゲート**を実行しなければならない。本機能が追加する 4 種だけでなく、既存のビルド・単体テスト・シークレット検査を含む。1 つが失敗しても残りを実行し、最後にまとめて報告しなければならない
- **FR-025**: 検査ツールが実行環境に存在しない場合、検査を省略して成功扱いにしてはならない。中断しなければならない
- **FR-026**: 統合前の検査が検査を省略した場合、省略した理由をログと実行サマリに残さなければならない
- **FR-027**: 検査対象のモジュール一覧は、固定の列挙ではなくリポジトリ内の実際のモジュール定義から導出されなければならない
- **FR-028**: 検査は作業ツリーを書き換えてはならない。整形の是正は検査とは別の手段で行い、検査は違反の報告のみを行う
- **FR-029**: 検査ツールの版は単一の出典で固定されなければならない。統合前の検査が独自に版を持ってはならない

### 主要な実体

- **許容ライセンスリスト**: 依存に許してよいライセンスの集合。各要素は識別子と、表示のみで足りるか／ソース提供義務を伴うかの区分を持つ。憲章の許容リストが唯一の出典である
- **依存目録**: 検査時に収集される依存の一覧。各要素はモジュール名、バージョン、判定されたライセンス、直接／間接の区別、どのモジュールの依存か、間接の場合の経由元を持つ
- **ライセンスヘッダ**: Go ファイルの先頭行に置かれる SPDX 識別子。ファイル単位で由来を追跡するための単位である
- **静的解析設定**: 有効な検査項目とそのバージョンを固定する定義。手元と統合前で同一であることが要件である
- **抑制記録**: 個別の指摘を抑制する宣言。対象行と理由を伴う
- **脆弱性報告**: 検査が返す到達可能な既知脆弱性。識別子と到達経路を持つ

## 成功基準 *(必須)*

### 測定可能な成果

- **SC-001**: リポジトリ内の Go ファイルのうち、ライセンスヘッダを欠くものが 0 件である（現在は 8 件）
- **SC-002**: ヘッダを欠いた変更、ファイル全体に効く抑制を含む変更、許容外ライセンスの依存を含む変更、整形が崩れた変更、理由なき抑制を含む変更、到達可能な既知脆弱性を含む変更は、いずれも人手の確認を経ずに 100% 不合格となる
- **SC-003**: 同一コミットに対する手元と統合前の静的解析の指摘の差異が 0 件である
- **SC-004**: 理由の記載がない指摘抑制が 0 件である
- **SC-005**: 許容リスト外および判別不能なライセンスの依存が 0 件である
- **SC-006**: 本体モジュールの依存のうち、表示のみでは足りないライセンスを持つものが 0 件である
- **SC-007**: 統合された状態（`main`）において、到達可能な既知脆弱性が 0 件である
- **SC-008**: 4 種の検査すべてが、リポジトリ内のすべてのモジュールを対象とする（対象外のモジュールが 0 件）
- **SC-009**: 検査ツールの未導入により検査が黙って省略される経路が 0 件である
- **SC-010**: clone 直後の開発者が、追加の説明を読まずに 4 種の検査すべてを実行できる（実行方法がリポジトリ内の 1 か所で示されている）
- **SC-011**: 4 種の検査を実行しても作業ツリーに変更が生じない（検査前後で差分が 0 件）

## 前提

- 本仕様の要件は、憲章の「ライセンス」「Go コード品質」ブロックおよび「開発ワークフローと品質ゲート」を出典とする。憲章が名指しするツール（`gofmt`、`golangci-lint`、`govulncheck`）は選択の余地がない制約として扱う。それ以外のツール選定（依存ライセンス検査の手段）は本仕様では定めず、計画段階の判断とする（計画で決定済み）
- 依存ライセンス検査の母集団は FR-007 が定める「実際に import されるパッケージ」である。これは本仕様の判断ではなく憲章の規範であり、モジュールグラフ全体を母集団とすることは憲章が禁じている。根拠は、GPL 系を排除する理由が「依存が利用者のバイナリへ静的リンクされること」であり、リンクされない依存は利用者の配布物に条件を及ぼさない点にある。間接依存は import されている限り母集団に含まれる（憲章の「混入は依存の依存として静かに起きる」に対応する）
- 脆弱性検査は統合（`main` へのマージ）の必須ゲートとする。これは本仕様の判断ではなく憲章の規範である。新しい脆弱性の公表はコード変更と無関係に起きるため、脆弱性を含まない変更が止まる事象は起こりうる。憲章はこれを承知のうえでマージ前に置き、`main` を常にリリース可能な状態に保つことを選んでいる。リリース直前に発見すると、そのとき初めて依存の更新を迫られリリース自体が遅れるためである
- 検査ツール未導入時に中断する方針は、既存のシークレット検査 hook の方針を踏襲する
- 生成物のライセンスヘッダは生成テンプレート由来であり、本仕様では生成物へ後から付与する仕組みは設けない
- 抑制の妥当性そのものは機械的に判定できないため、検査が担うのは理由の有無と範囲の広さに限る。内容の妥当性はレビューが判断する
- 統合前の検査は既存の CI と同じ基盤上で動作する前提とする
- FR-024 の「単一のコマンド」は段階的に充足される。各 user story の段階では当該 story の検査コマンドが単一の入口であり、すべてのゲートを 1 つにまとめる入口（FR-030）は全 story の完了時に用意する。憲章はこの入口を必須としているため、機能の完了条件には含まれるが、個々の story の受け入れ条件には含めない
- FR-030 の一括実行が既存のゲート（ビルド・単体テスト・シークレット検査）も含むのは憲章の規定による。本機能はそれらの検査自体を変更せず、一括実行の入口から呼ぶだけである
- FR-018 の対象は `package` 宣言より前に置かれた抑制に限る。関数宣言やブロックに付いた抑制の範囲の広さは機械的に判定できないため、その妥当性はレビューが判断する
- 本仕様はシークレット検査ツールの移行（gitleaks から betterleaks へ）を含まない。別の機能として扱う
