# Contract: 許容ライセンスリストのファイル形式

**Date**: 2026-09-09
**Spec**: [../spec.md](../spec.md) / **Data model**: [../data-model.md](../data-model.md)

FR-013 は、許容リストがリポジトリ内の単一の場所で定義され、憲章の許容リストと
一対一で対応することを求める。その形式を定める。

## 配置

`licenses-allowlist.txt`（リポジトリルート）

手書きファイルであるため `.openapi-generator-ignore` に登録する（憲章 原則 I）。

## 形式

1 行 1 ライセンス。`<SPDX 識別子><TAB><区分>` とする。

```text
# 憲章「ライセンス」ブロックの許容リストと一対一で対応する。
# 変更する場合は、先に憲章を改訂すること。
#
# 区分:
#   notice     : 表示のみで足りる
#   reciprocal : ソース提供義務を伴う。本体モジュールでは許容しない

Apache-2.0	notice
MIT	notice
BSD-2-Clause	notice
BSD-3-Clause	notice
ISC	notice
MPL-2.0	reciprocal
```

- `#` から行末までをコメントとする
- 空行は無視する
- 識別子は SPDX の識別子をそのまま用いる。大文字小文字を区別する
- 同じ識別子を 2 回書いた場合はエラーとする（どちらが有効か曖昧になるため）
- 未知の区分はエラーとする（新しい区分を黙って `notice` として扱わないため）

**なぜ独立したファイルにするか**: Makefile や `.golangci.yml` に埋め込むと、
「憲章と一対一で対応する」ことを読み手が確認しにくい。単独のファイルであれば、
憲章の表と並べて差分を見られる。

**なぜ TSV か**: 依存を増やさずに読めること（原則 V）。YAML や JSON は
標準ライブラリだけでも読めるが、この内容に構造は要らない。

## 変更手続き

このファイルへの追加は、憲章の許容リストの改訂を先に行うことを要する
（憲章「個別の判断で例外を作らないこと (MUST NOT)」）。検査ツールは
リストの妥当性を判断せず、リストとの一致のみを見る。
