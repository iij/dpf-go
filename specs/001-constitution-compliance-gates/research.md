## D1: 依存ライセンス検査のツール

**Decision**: `go-licenses` を採用する。`syft` はライセンス判定の権威としては使わない。

**根拠**: 両者を同じ作業ツリーで実行して比較した。

`syft scan dir:.`（116 パッケージ）の判定:

| 件数 | 判定 |
|---|---|
| 29 | BSD-3-Clause |
| 23 | MIT |
| 18 | Apache-2.0 |
| **15** | **NOASSERTION（判別不能）** |
| 10 | MPL-2.0 |
| 9 | Apache-2.0 AND BSD-3-Clause |
| 4 | ISC / 4 Apache-2.0 AND MIT / 2 BSD-2-Clause |
| 2 | `Apache-2.0 AND BSD-3-Clause AND LicenseRef-<hash>` |

`go-licenses csv ./...` をモジュールごとに実行した判定（合計 75 行、重複除去後 65 件）:

| 件数 | 判定 |
|---|---|
| 23 | BSD-3-Clause |
| 20 | Apache-2.0 |
| 10 | MPL-2.0 |
| 8 | MIT |
| **4** | **Unknown（すべて自前モジュール。D4 参照）** |

`syft` を採らない理由は 3 つある。

1. **判別不能が多い。** NOASSERTION 15 件には `golang.org/x/crypto`、`golang.org/x/mod`、
   `golang.org/x/tools`、`github.com/mitchellh/go-homedir` が含まれる。いずれも
   ライセンスが明確なモジュールである。FR-009 は判別不能を失敗として扱うため、
   このままではゲートが常に赤くなり、抑制の運用が必要になる。抑制が増えれば
   ゲートの意味が失われる。
2. **対象が広すぎる。** `actions/checkout`、`actions/setup-go`、`anchore/sbom-action`、
   `actions/attest-build-provenance` といった GitHub Actions のエントリまで
   パッケージとして拾う。これらは依存モジュールではなく、憲章の許容リストの対象外である。
3. **モジュールごとの帰属が取れない。** ディレクトリ全体を 1 つの文書にまとめるため、
   ある依存が本体のものか `misc/vault` のものかを区別できない。FR-012（本体モジュールに
   ソース提供義務のある依存が無いことの検査）を実装できない。

`go-licenses` はモジュールのディレクトリで実行するため帰属が自然に取れ、判別不能は
自前モジュールの 4 件だけだった。

**検討した代替案**:

- **syft + 許容リスト照合**: SBOM 生成に既に使っており、依存の追加が無い点は魅力だった。
  上記 3 点により却下。ただし `sbom.yml` での SBOM 生成用途は継続する。用途が異なる。
- **trivy のライセンススキャン**: 未導入であり、コンテナ前提の機能が多い。
  本リポジトリはコンテナを配布しないため導入の対価が見合わない。
- **`go list -m all` + ライセンス辞書の自作**: 判定ロジックを自前で持つことになり、
  ライセンス本文の分類器を維持する負担が発生する。却下。

## D2: 検査対象の母集団

**Decision**: 実際に import されるパッケージを母集団とする（`go-licenses` の既定の挙動）。
モジュールグラフ全体（`go list -m all`）は使わない。

**根拠**: 憲章が GPL 系を排除する根拠は「利用者のバイナリへ静的リンクされる」ことである。
リンクされない依存は利用者の配布物に条件を及ぼさない。モジュールグラフ全体には、依存の
テスト専用依存や未使用の依存が含まれ、実害のない偽陽性でゲートを止めることになる。

**注記**: 憲章の「依存ライセンスの実測 (2026-09-09 時点)」は合計 114 件
（Apache-2.0 57 / BSD-3-Clause 32 / MIT 14 / MPL-2.0 10 / BSD-2-Clause 1）であり、
本調査の 65 件と母集団が異なる。憲章側はモジュールグラフに近い数え方と思われる。
**MPL-2.0 が 10 件でありすべて HashiCorp 系である点は両者で一致した。**
実装後、憲章の実測値をどちらの母集団で更新するかは別途の憲章改訂で扱う（本計画の範囲外）。

**検討した代替案**:

- **モジュールグラフ全体**: 網羅性は高いが偽陽性が多い。却下。
- **両方を検査し、グラフ側は報告のみ**: 2 つの母集団を維持する負担に対し、
  得られる情報が「リンクされない依存のライセンス」に限られる。却下。

## D3: 自前モジュールが判別不能になる問題

**Decision**: `misc/vault`、`misc/aws`、`misc/azure`、`misc/gcp` の各ディレクトリに
`LICENSE` を置く（**本計画の作成時に実施済み**）。これにより判別不能は解消するため、
検査側に自前モジュールを除外するロジックは設けない。

**根拠**: `go-licenses` の Unknown 4 件は、すべて自前モジュールだった。

```
github.com/iij/dpf-go/misc/vault,Unknown,Unknown
github.com/iij/dpf-go/misc/aws,Unknown,Unknown
github.com/iij/dpf-go/misc/azure,Unknown,Unknown
github.com/iij/dpf-go/misc/gcp,Unknown,Unknown
```

原因は、`LICENSE` がリポジトリルートにしか無く、各 `misc/*` のディレクトリには
無いことである。Go モジュールの配布単位はモジュールのディレクトリ配下であるため、
`misc/vault` を独立に取得した利用者には `LICENSE` が届かない可能性が高い。
現在のタグは `v0.0.1` / `v0.0.2` のみで `misc/*` は未公開であり、公開前に是正できる。

したがってこれは検査の都合ではなく、**配布上の実際の不備**として扱う。

**実施と検証**: ルートの `LICENSE` を 4 つの `misc/*` へ複製した（内容は md5 一致、
著作権表示は `Copyright 2026 Internet Initiative Japan Inc.`）。実施後に
`misc/vault` で再測定した結果、**Unknown は 0 件**になった。

| | 実施前 | 実施後 |
|---|---|---|
| MPL-2.0 | 10 | 10 |
| BSD-3-Clause | 4 | 4 |
| MIT | 3 | 3 |
| Apache-2.0 | 1 | 2 |
| **Unknown** | **1** | **0** |

自前モジュールは Apache-2.0 として判定され、許容リストに収まる。当初想定していた
「自前モジュールを検査対象から除外する」ロジックは不要になった。判定を歪めずに
実装を単純化できるため、除外は設けない。

**検討した代替案**:

- **除外のみ（`LICENSE` を置かない）**: Unknown は消えるが、公開時に利用者へ
  ライセンスが届かない不備が残る。また検査側に「自分自身」を知る特別扱いが増える。却下。
- **シンボリックリンク**: モジュール zip での扱いが環境依存になる。実ファイルを置いた。

## D4: SPDX ヘッダ検査とファイル冒頭規約の実装手段

**Decision**: 標準ライブラリのみの Go プログラム `tools/checkheaders` を追加する。
SPDX ヘッダの検査（FR-001〜FR-006）と、`package` 宣言より前に置かれた `nolint`
指示の検出（FR-018）を担う。

**根拠**: 既存の `tools/genexecuteall` が前例であり、`doc.go` + `main.go`、
標準ライブラリのみ、先頭に SPDX ヘッダという構成になっている。同じ形に揃えられる。

Go プログラムを選ぶ理由:

- 憲章 II が手書きコードに単体テストを要求する。除外規則や `package` 宣言前の
  `nolint` 検出のような判定はテーブル駆動テストで検証できる。シェルスクリプトでは
  同等の検証を用意しにくい。
- 標準ライブラリのみで書けるため、原則 V（本体の依存を増やさない）に抵触しない。
- ルートモジュールに属するため、`make build-all` と `make test` の既存の反復で
  自動的にビルド・テストされる。

`package` 宣言前の `nolint` を Go 側で見るのは、`nolintlint` では防げないためである
（D5 参照）。どちらも「ファイル冒頭の規約」であり、1 つのツールにまとめる。

**検討した代替案**:

- **シェルスクリプト（`find` + `grep`）**: 単体テストを付けにくく、憲章 II を満たしにくい。却下。
- **`google/addlicense`**: `--check` で検査でき付与もできるが、外部ツールの導入と
  バージョン固定の対象が 1 つ増える。判定内容が単純なため対価が見合わない。却下。
- **`apache/skywalking-eyes`**: 設定ファイルで柔軟に書けるが、依存が重い。却下。

## D5: 静的解析の設定と抑制の検査

**Decision**: リポジトリルートに `.golangci.yml` を置く。設定スキーマは v2 系。
抑制の検査は `nolintlint` に任せ、`package` 宣言前の広域抑制のみ `tools/checkheaders`
で補う。

**根拠**: golangci-lint 2.13.2 では `gofmt` は linter ではなく **formatter** に
移動している（`golangci-lint formatters` で確認）。整形（FR-019）は `formatters` 節で
扱う。抑制の検査は `nolintlint` が担当する。

以下の設定案を `golangci-lint config verify`（JSON スキーマ検証）にかけ、通ることを確認した。

```yaml
version: "2"

linters:
  default: standard
  enable:
    - nolintlint
  settings:
    nolintlint:
      require-explanation: true
      require-specific: true
      allow-unused: false
      allow-no-explanation: []

formatters:
  enable:
    - gofmt
```

`require-explanation` が FR-017（理由の記載がない抑制）、`require-specific` が
対象 linter を明示しない `//nolint` を弾く。

**`nolintlint` では足りない点**: `package` 宣言より前に置かれた `nolint` 指示は
ファイル全体に効く。理由と linter 名を伴っていれば `nolintlint` は通してしまうため、
FR-018（ファイル単位・パッケージ単位の広域抑制）を満たさない。テキスト規則として
`tools/checkheaders` で検出する。

**検討した代替案**:

- **`gofmt` を `make fmt` の差分検査だけで担保する**: 既存の `make fmt` は `-w` で
  書き換えるため、検査にならない。`formatters` 節に入れて検査させる。
- **広域抑制を人のレビューに委ねる**: 憲章が「機械的に」を求めている項目であり、
  かつ見落としやすい。却下。

## D6: ツールのバージョン固定と単一の出典

**Decision**: Makefile を版の唯一の出典とする。CI はバージョンを自前で持たず、
`make` ターゲットを呼ぶ。ローカルの `make` ターゲットは導入済みの版が固定値と
一致するかを検証し、不一致なら中断する。

**根拠**: FR-015 は「手元と統合前が同一の設定・同一のバージョンで動作し、
指摘の集合が一致する」ことを求める。版の定義が 2 か所にあると必ず乖離する。
本 research 時点の `gitleaks` は CI 側に `GITLEAKS_VERSION: 8.30.1` を持ち、
`make gitleaks` は手元に入っている版を使うため、この乖離がすでに存在していた。
（その後 betterleaks へ移行し、版は Makefile の `BETTERLEAKS_VERSION` を
唯一の出典として本 D6 の方式に揃えた。）

golangci-lint は `go install` での導入を勧めていない（ビルドに使う Go の版によって
結果が変わりうる）。公式リリースのバイナリを版指定で導入する方式は、既存の
当時の `gitleaks.yml` が採っていた方式と同じであり、リポジトリの慣行に沿う。

ローカルで版が違うときに黙って続行しないのは、FR-025 および既存の
`.githooks/pre-commit` の方針（ツールが無ければ検査を省略せず中断する）と同じである。

**検討した代替案**:

- **`golangci/golangci-lint-action` の `version` 指定のみ**: CI だけが固定され、
  手元と乖離する。FR-015 を満たさない。却下。
- **`go.mod` の `tool` ディレクティブ**: ルートモジュールに依存が入り、
  原則 V（本体の依存を増やさない）に反する。却下。
- **ツール専用の独立モジュール（`tools/go.mod`）**: 原則 V には抵触しないが、
  モジュールが 6 つになる。憲章の品質ゲート表と原則 II が「全 5 モジュール」と
  書いているため、憲章の改訂を伴う。得られるものが版固定だけであるのに対して
  影響が大きい。却下。

## D7: 脆弱性検査のゲート位置（憲章 v2.0.0 で改定）

**Decision**: **`main` への統合を必須ゲートとする。** 到達可能な既知脆弱性が報告される
状態でマージできない。リリース専用のゲートは設けない。`continue-on-error` は使わない。

**根拠**: 憲章 v2.0.0 が、v1.2.0 の「脆弱性の検査結果が `main` への統合を
止めてはならない (MUST NOT)」を「止める (MUST)」へ反転させた。これは選択の余地のない
制約である。リリースは `main` から行うため、マージ前に止めればリリース時点の条件も
満たされる。

**当初（v1.2.0 前提）の決定とその変更**: 本計画は当初「リリースを必須ゲートとし、
提出時は報告のみ」と決めていた。理由は、新しい脆弱性の公表がコード変更と無関係に
起きるため、統合の必須ゲートに置くと脆弱性を含まない変更が止まる、というものだった。
憲章はこの事象を承知のうえでマージ前に置くことを選んだ。`main` を常にリリース可能な
状態に保つほうが、リリース直前に依存の更新を迫られてリリース自体が遅れるより
損失が小さい、という判断である。

**止まった場合の対処**: 依存の更新、または脆弱な経路へ到達しない形への修正である。
検査の迂回、一時的な無効化、報告のみへの格下げは憲章が禁じている（MUST NOT）。
したがって実装側に迂回の経路を用意してはならない。

`continue-on-error` を使わないのは、`sbom.yml` が「`continue-on-error` で黙って飛ばすと
『失敗したのに成功に見える』」という理由でこれを避けているためである。統合を止める
ゲートになった本件では、そもそも成功終了させる余地がない。

**検討した代替案**:

- **リリースのみを必須ゲートにする（当初の決定）**: 憲章 v2.0.0 に反する。却下。
- **提出時は報告のみに格下げできる例外を設ける**: 憲章が明示的に禁じている。却下。
- **定期実行を併用して早期に気づく**: マージゲートである以上、`main` が緑であれば
  新しい公表は次の PR で必ず現れる。定期実行を足しても検出の早さは変わらないため、
  実装しない。

## D8: 検査対象モジュールの導出

**Decision**: Makefile の `MODULES` を、リポジトリ内の `go.mod` の位置から導出する形に
変更する。`vendor` と `testdata` は除外する。

**根拠**: 現在は `MODULES := . misc/vault misc/aws misc/azure misc/gcp` と
ハードコードされている。FR-027 は固定の列挙を禁じており、SC-008（検査対象外の
モジュールが 0 件）も満たせない。モジュールが増えたときに `make` の各ターゲットと
新しい 4 種の検査が同時に追随する必要がある。

**検討した代替案**:

- **`git ls-files` から導出**: git 管理外のチェックアウト（アーカイブ展開）で壊れる。
  `find` に prune を併用する方式を採る。
- **列挙を維持し、漏れを検査する別のチェックを足す**: 検査対象の定義が 2 か所に
  分かれる。却下。

## D9: ツールの版の固定値と、版の取得手段が揃わない問題

**Decision**: 固定値は `golangci-lint` = 2.13.2、`govulncheck` = v1.7.0、`go-licenses` = v2.0.1 とする。
版の検証は**ツールごとに手段を切り替える**。`go-licenses` は自身の版を報告できないため、
`go version -m $(command -v go-licenses)` の `mod` 行から取得する。

**根拠**: D6 で「版の固定値は Makefile を唯一の出典とし、ローカルは導入済みの版が
固定値と一致するかを検証する」と決めたが、検証の実装手段を確認したところ、3 つのツールで
取得方法が揃っていなかった。

| ツール | 固定値 | 版の取得 | 出力 |
|---|---|---|---|
| golangci-lint | 2.13.2 | `golangci-lint --version` | `golangci-lint has version 2.13.2 built with go1.27.0 ...` |
| govulncheck | v1.7.0 | `govulncheck --version` | `Scanner: govulncheck@v1.7.0` を含む複数行 |
| go-licenses | v2.0.1 | **`go version -m $(command -v go-licenses)`** | `mod github.com/google/go-licenses/v2 v2.0.1 h1:...` |

`go-licenses` に `--version` を渡すと `flag provided but not defined: -version` となり
使用法を表示して終了する。`version` サブコマンドも `-version` も持たない。ビルド情報から
読むほかない。

これを設計に書き残さないと、実装時に「3 ツールを同じヘルパーで検証する」前提で書き始め、
`go-licenses` で行き詰まる。版の固定（FR-029）と未導入・不一致での中断（FR-025）は
どちらも憲章の MUST であるため、取得できないから省略するという逃げ道はない。

**注記**: 出力の形式も 3 者で異なる（版の前置きの語、`v` の有無、行数）。ヘルパーは
ツールごとに抽出規則を持ち、抽出に失敗した場合も終了コード 2 で中断しなければならない。
「版が取れなかった」を「一致した」として扱ってはならない。

**検討した代替案**:

- **`go-licenses` の版検証を省略する**: 版が違えばライセンス判定が変わりうる。
  FR-015（手元と CI で同一の版）を満たさない。却下。
- **`go-licenses` を `go run` で版指定して呼ぶ**: 版は固定できるが、ルートモジュールの
  `go.mod` に依存が入り原則 V に反する。別モジュールを作る案は D6 で却下済み。却下。
- **3 ツールとも公式リリースバイナリを固定パスへ導入する**: 版は確実に揃うが、
  開発者の環境に踏み込む。導入は開発者に委ね、検証のみを行う方針を維持する。

## D10: 終了コードの契約が make では表現できない

**Decision**: 「違反あり (1)」と「検査できなかった (2)」の区別は、`make` の終了コードでは
表現しない。**各ゲートのツール自身が 0 / 1 / 2 を返し、`make check` は先に版検証を
まとめて行ったうえで `RESULT` 行に区別を出す。**

**Rationale**: 実装中に判明した。GNU make はレシピが失敗すると**必ず 2 で終了する**ため、
`make check-headers` のようなターゲットの終了コードで 1 と 2 を分けることは原理的に
できない。実測でも、違反 8 件（ツール自身は 1 を返す）に対して `make` の終了コードは
2 だった。

当初 [contracts/gates.md](./contracts/gates.md) は各 `make` ターゲットの終了コードとして
0 / 1 / 2 を定めていたが、これは実現できない契約だった。区別の意味は捨てずに、
表現する場所を移す。

- **ツール単体**は契約どおり 0 / 1 / 2 を返す。`go run ./tools/checkheaders` を直接
  呼べば違反は 1、内部エラーは 2 である。区別を要するスクリプトはこちらを呼ぶ。
- **`make check` は版検証を先頭にまとめる。** 4 つのツールの導入と版をゲート実行前に
  検証するため、ここで止まれば「検査できなかった」、通った後の失敗は「違反」と決まる。
  順序で意味を担保する。
- **`make check` は `RESULT: ok` / `RESULT: violated` 行と失敗したゲート名を出す。**
  読み手はこれで区別できる。

**Alternatives considered**:

- **`-` 接頭辞や `|| true` で失敗を飲む**: make の終了コードは 0 になるが、ゲートが
  機能しなくなる。却下。
- **`make` を包む薄いスクリプトを置く**: 終了コードを自由に返せるが、実行の入口が
  `make` とスクリプトの 2 つになる。憲章は `make check` を入口と定めており、
  入口を増やす対価に見合わない。却下。
- **契約から 1 と 2 の区別を削る**: 「検査できなかったことを違反なしとして扱わない」
  という憲章の MUST NOT を実装が担保できなくなる。却下。

## D11: 版検証の probe をシェル変数に入れてはならない

**Decision**: 版を取得するコマンドは `make` のレシピ内で**コマンド位置へ直接展開する**。
シェル変数へ代入して `eval` してはならない。probe の定義は遅延展開 (`=`) とする。

**Rationale**: 実装中に踏んだ。当初は `probe="$(3)"` と代入して `eval "$$probe"` で
実行していたが、`go-licenses` の版が常に空になった。原因は二重展開である。

- 代入時にシェルが `"..."` の中の `$1` / `$3`（awk のフィールド参照）を未設定の
  位置パラメータとして空へ展開し、`awk '==mod{print ; exit}'` になっていた。
- 同じく `$(command -v go-licenses)` が代入時に置換され、probe の内容が固定化されていた。

さらに probe の定義を即時展開 (`:=`) にすると、`$$(` が `$(` になった時点で make が
自身の変数参照として解釈し、コマンド置換が消える。遅延展開 (`=`) にして、レシピへ
展開される瞬間に `$$` を解く必要がある。

この失敗は「版が取得できない」という形で現れる。ここで黙って通すと版の固定
（FR-029）が効かなくなるため、取得失敗も終了コード 2 で中断させている。

**Alternatives considered**:

- **probe をシェル関数として定義する**: クォートの問題は避けられるが、`make` の変数と
  シェルの変数が入り混じって読みにくい。却下。
- **ツールごとに版検証ターゲットを分ける**: 引数の受け渡しが無くなり最も安全だが、
  同じ 8 行が 4 つ並ぶ。1 つの `define` に寄せ、probe の渡し方だけを直した。
