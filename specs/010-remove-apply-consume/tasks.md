## 実行結果 (2026-09-29)

### 計画に無かった判断: `runLockedHold` を畳んだ

`hold.consume` を取り除いた時点で、**`runLockedHold` の存在理由が消えた**ことに気づいた。
godoc は「fn へ hold を渡すため非公開にしている」と述べていたが、その hold を受け取る唯一の
目的が `consume()` の呼び出しであった。残せば、使われない `*hold` が 3 箇所の署名を通り、
godoc の理由が偽になる。

**利用者の判断（2026-09-29）で `RunLocked` へ畳んだ。** `runLockedHold` を削除し、
`ZoneApplier.apply` の引数からも `*hold` を落とした。

**代償が 1 つある。** `TestMutexDo_RenewLoopStopped` は `*hold` を直接掴んで `done` が
閉じていることを見ていた。取り出し口が無くなったため、**白箱の観測を失い、振る舞いでの観測
（復帰後に延長の書き込みが起きないこと）へ寄せた**。`RunLocked` は復帰の前に goroutine の
終了を待つため性質は変わらないが、確認は決定的でなくなった。

**歯止めを 1 件越えた。** tasks.md は「落とすテストは 3 件まで」と定めていた。実際に触った
テストは 4 件である（削除 1・縮約 1・1 行削除 1・書き換え 1）。4 件目は範囲を広げる判断に
伴うものであり、**利用者の決定の後に越えた**。範囲を広げずに済ませた場合は 3 件で収まっていた。

### 実 API での確認 (2026-09-29、利用者が実行)

**全件 PASS**（`ok github.com/iij/dpf-go/internal/integration 697.343s`）。スキップは
`TestZoneLabelLock_UnpublishedZone` の 1 件のみ（公開前のゾーンが契約に無いため。009 の

| 確認すること | 証拠 |
|---|---|
| 一括置き換えの後も排他が保持され、解放が成功する | `[atomic_changes 後] 排他の保持=true` → `Unlock: err=<nil>` |
| 1 レコードずつの流れでも排他が反映の影響を受けない | `[PatchZoneChanges 後] 排他の保持=true` |
| 排他がゾーンに未反映の編集を作らない | どの段でも `未反映件数=0` |
| 排他がレコードを触らない | `SOA: state=0(反映済み) labels=map[]` |
| 権威サーバへ影響しない | 公開レコードが排他の前後で 2 件のまま |

### 1 回目の失敗について（2026-09-29）

**1 回目は 5 件が失敗したが、原因は GitHub Actions の並行実行であった。** 010 の変更とは
無関係である。実行を止めて再実行したところ全件 PASS した。

並行実行が説明したもの:

| 観測 | 説明 |
|---|---|
| 開始時点で別の排他が保持されていた | 相手の実行が保持していた |
| 直後の `Lock` が成功した | ログの読み取りと `Lock` の間に相手が解放した |
| ゾーンのラベルが空に見えた | 相手の後始末（`clearZoneLock`）がラベルごと削除した |
| 空なのに別 owner の取得が拒否された | **一時レコード追加ロックの競合**。ゾーンのラベルが無くても、相手が専用レコードを握っていれば `ErrStillLock` になる |
| 未反映件数が想定と合わない | 相手の `applyZone` がこちらの未反映分を巻き込んで反映した |

**当初「ゾーンのラベルの読み取りが一貫していない」と見立てたが、これは誤りであった。**
とくに「ラベルが空でも取得が拒否される」は専用レコードの競合でしか説明できず、読み取りの
不整合では説明がつかない。2 回目の実行で `GetZoneLabels` の値はすべて辻褄が合っている。

**残る課題（本機能の範囲外）**: この統合テスト群は並行実行に対して無防備である。どの実行も
同じゾーンを使い、保持者も `dpf-go-ci` で固定されている。ワークフロー側で直列化する
（`concurrency` グループ）のが有効である。011 として起こす価値がある。
