# 検証手順: 一括置き換えが排他を解くことの申告の仕組みを取り除く

**機能**: [spec.md](./spec.md) | **計画**: [plan.md](./plan.md) | **日付**: 2026-09-29

挙動を変えない変更であるため、**既存のテストが通ることが検証の中心**である。

## 前提

```bash
cd $(git rev-parse --show-toplevel)
```

- Go 1.27 以上。`make check` の各ツールが導入済みであること。
- 第 4 節（実 API）には `DPF_TOKEN_RO` / `DPF_TOKEN_RW` / `DPF_TEST_SERVICE_CODE` が必要。

## 1. 公開されている要素に差分が無いこと

**着手する前に**控えを取る。

```bash
go doc -all ./utils > /tmp/utils-before.txt
```

変更の後に取り直して比較する。

```bash
go doc -all ./utils > /tmp/utils-after.txt
diff /tmp/utils-before.txt /tmp/utils-after.txt && echo "OK: 公開 API に差分なし"
```

**期待**: 差分が無い。差分が出た場合は取り除く対象を誤っている
（[contracts/api.md](./contracts/api.md) 第 1 節）。

## 2. 品質ゲート

```bash
make check
```

**期待**: すべて成功。とくに `check-lint` の**未使用の検出**が、取り残しを見つける。
取り除いたつもりの要素が残っていれば、ここで落ちる。

## 3. 単体テスト

```bash
go test ./utils/... -race -count=1
```

| 確認すること | 対応 |
|---|---|
| **取り除いた要素を検証するテスト以外は、1 行も変えずに通る** | [contracts/api.md](./contracts/api.md) 第 4 節 |
| 排他の取得・延長・解放の結果が変わらない | FR-004 |
| ゾーン全体の一括置き換えの後も排他が保持され、終了時に解放される | FR-005 |
| 排他を差し替えた場合と既定の場合で結果が同じ | FR-006 |
| 解放の失敗がそのまま返る | [data-model.md](./data-model.md) 第 2 節 |

**落とすテスト**（[research.md](./research.md) D5）:

- 申告の判定そのものを確認するテスト → 削除
- 印の有無で解放の扱いが変わることを確認するテスト → 「解放の失敗はそのまま返る」へ縮約
- 既定の排他が申告することの確認（1 行） → 削除

**落とすテストが上記より増える場合は、取り除く範囲が広すぎる。**

## 4. 実 API での確認

挙動を変えないため、**既存の統合テストが通ることをもって確認とする**。新しいテストは足さない。

```bash
make test-integration
```

**期待**: 009 と同じ結果になる。とくに次の 2 つを見る。

| 確認すること | 対応 |
|---|---|
| レコードの一括更新とゾーン反映の後も排他が保持され、解放が成功する | FR-005・SC-004 |

**トークン未設定でスキップされた結果を確認結果として報告してはならない**（憲章 品質ゲート）。
