# 機能仕様: OpenAPI からの Go クライアント生成パイプライン

**機能ブランチ**: `002-openapi-generation-pipeline`

**作成日**: 2026-09-09

**状態**: 実装済み (CLAUDE.md から移行した事後仕様)

**憲章**: v2.0.0 の原則 I (生成コードと手書きコードの分離)、原則 II、原則 III、原則 V に整合

**入力**: CLAUDE.md「go package 生成用プログラム作成タスク」仕様 1〜7 の移行。すなわち「openapi.json の定義に基づいて go package を生成するプログラムを作成する。generator は openapitools/openapi-generator-cli の最新版を用い、API Client を OpenTelemetry Trace に対応させる。DPF の Execute() は Pager であるため全体を取得する ExecuteAll() を作る。api / model はプロジェクト直下に置き、make で再生成すると古いファイルはすべて新しくなる。生成物には生成元を示すコメントを付与する。Error 系の Response は API のレスポンスに応じた Error 構造体を用意する」

## 利用シナリオと検証 *(必須)*

### 利用シナリオ 1 - API 仕様の更新が 1 コマンドで反映される (優先度: P1)

DPF-API の仕様が更新されたので、開発者は新しい `openapi.json` をリポジトリルートへ置き、単一のコマンドを実行する。API クライアントの実装は再生成され、そのままビルドが通る。仕様から消えたスキーマや API に対応する古いファイルは残らない。一方で、手書きで足した高レベルのユーティリティは失われない。

**この優先度の理由**: 本リポジトリのコードの大半は生成物である。再生成が 1 コマンドで完結しないか、あるいは再生成で手書きコードが失われるなら、API 仕様が更新されるたびに実装が消えるか、再生成を諦めて仕様と実装が乖離する。他の 3 シナリオはいずれもこのパイプラインの上に乗るため、これが土台となる。

**独立した検証**: 現在の `openapi.json` に対して再生成を実行し、作業ツリーに差分が生じないこと (すなわち生成物が仕様と一致していること) を確認できる。`openapi.json` から 1 つのスキーマを削除して再生成し、対応するファイルが消えることを確認できる。手書きファイルが再生成後も残ることを確認できる。

**受け入れシナリオ**:

1. **前提** `openapi.json` が更新されている、**操作** 再生成のコマンドを実行する、**結果** 生成物が更新され、整形の指摘なくビルドが成功する
2. **前提** `openapi.json` からスキーマまたは API が削除された、**操作** 再生成する、**結果** それに対応する生成物のファイルが残らない
3. **前提** 手書きのファイルおよび手書きのパッケージが存在する、**操作** 再生成する、**結果** それらは上書きも削除もされない
4. **前提** 生成が完了した、**操作** 生成物の先頭を確認する、**結果** すべてに生成元を示すコメントとライセンス識別子が付与されている
5. **前提** 生成器のテンプレートを公式版へ戻した、**操作** 再適用せずに再生成する、**結果** ライセンス識別子とトレース計装を欠いたコードが生成される (再適用が必要であることが分かる)

---

### 利用シナリオ 2 - Pager の一覧 API を全件取得できる (優先度: P2)

利用者はゾーンの一覧を取得したい。DPF-API の一覧取得は `limit` と `offset` によるページングであり、素の呼び出しでは 1 ページ分しか得られない。利用者はページングを自分で書く代わりに、全件を結合して返す呼び出しを使う。ログ系の一覧も同じ形で扱えるが、1 ページあたりの件数は API の性質に合わせて自動的に変わる。

**この優先度の理由**: ページングは一覧 API のほぼすべてに現れ、利用者が最も頻繁に踏む。自分で書くとオフセットの進め方と終了条件を誤りやすく、取りこぼしや無限ループになる。生成物の一部として提供することで、対象の一覧 API が増えたときにも追随が漏れない。

**独立した検証**: `limit` と `offset` の双方を持つリクエスト型を数え、そのすべてに全件取得の呼び出しが生成されていることを確認できる。ログ系と通常の一覧で 1 ページあたりの件数が異なることを確認できる。ページ境界 (最終ページがちょうど 1 ページ分の件数だった場合) の挙動を確認できる。

**受け入れシナリオ**:

1. **前提** 一覧が 1 ページに収まらない件数ある、**操作** 全件取得を呼ぶ、**結果** すべてのページの結果が結合された 1 つの結果が返る
2. **前提** 通常の一覧 API である、**操作** 全件取得を呼ぶ、**結果** 1 ページあたり 10000 件で取得される
3. **前提** ログ系の一覧 API である、**操作** 全件取得を呼ぶ、**結果** 1 ページあたり 100 件で取得される
4. **前提** 2 ページ目の取得でエラーが発生する、**操作** 全件取得を呼ぶ、**結果** 1 ページ目までの結果とエラーの双方が返る
5. **前提** 最終ページの件数がちょうど 1 ページあたりの件数と等しい、**操作** 全件取得を呼ぶ、**結果** 次のページを引いて 0 件を得た時点で終了し、結果は重複しない
6. **前提** `openapi.json` に `limit` と `offset` を持つ一覧 API が追加された、**操作** 再生成する、**結果** 対象一覧を書き換えなくても全件取得が生成される

### 利用シナリオ 3 - エラーレスポンスの内容を型付きで取り出せる (優先度: P3)

利用者の API 呼び出しが失敗する。利用者はエラーメッセージの文字列を解析する代わりに、返されたエラーから、DPF-API が返したエラーコードやメッセージを構造として取り出し、状況に応じた処理を行う。

**この優先度の理由**: 本ライブラリは他者のゾーンとレコードを操作する。「なぜ失敗したか」を利用者が機械的に判別できなければ、再試行してよい失敗と、してはならない失敗を区別できない。文字列の解析に頼らせると、API のメッセージ文言の変更が利用者側の分岐を静かに壊す。

**独立した検証**: `openapi.json` がエラースキーマを定義しているステータスコードを列挙し、そのすべてに対して復号先の型が生成されていることを確認できる。エラー応答を返す実 API に対して、抽出したエラーコードとメッセージが得られることを統合テストで確認できる。

**受け入れシナリオ**:

1. **前提** API が 400 を返した、**操作** 返されたエラーから内容を取り出す、**結果** `openapi.json` が 400 に定義するエラースキーマに対応した型として得られる
2. **前提** API が 404 / 406 / 429 / 500 / 503 / 504 を返した、**操作** 返されたエラーから内容を取り出す、**結果** それぞれのステータスに定義されたエラースキーマに対応した型として得られる
3. **前提** エラー応答の本文を復号できなかった、**操作** 返されたエラーを確認する、**結果** ステータスを含むエラーが返り、HTTP レスポンス自体も失われない
4. **前提** エラー応答を受け取った、**操作** エラーの文言を確認する、**結果** ステータス行とレスポンスから抽出したエラー内容の双方が含まれている

---

### 利用シナリオ 4 - API 呼び出しが分散トレースに現れる (優先度: P4)

利用者は自分のアプリケーションに OpenTelemetry を設定している。本ライブラリ経由の DPF-API 呼び出しが、利用者のトレースの中に子スパンとして現れ、どの呼び出しが遅いか、どこで失敗したかが分かる。設定していない場合は何も起こらず、余分な負荷もない。

**この優先度の理由**: 本ライブラリはログを出力しない (憲章 原則 V)。異常の観測手段はエラーの戻り値とトレースだけであり、トレースがなければ利用者は「どの API 呼び出しで時間がかかっているか」を外から知る手段を持たない。最後に置くのは、他の 3 つが機能そのものであるのに対し、これは観測手段であり、他が動いていなければ観測する対象がないためである。

**独立した検証**: トレースの収集先を差し替えた状態で API を呼び、スパンが 1 つ生成され、期待する属性を持つことを確認できる。送信されたリクエストヘッダにトレースコンテキストが載っていることを確認できる。

**受け入れシナリオ**:

1. **前提** 利用者が OpenTelemetry を設定している、**操作** API を呼ぶ、**結果** クライアント種別のスパンが 1 つ生成される
2. **前提** API 呼び出しが成功した、**操作** スパンの属性を確認する、**結果** HTTP メソッド・URL・接続先ホスト・応答ステータスコードが記録されている
3. **前提** API を呼ぶ、**操作** 送信されたリクエストヘッダを確認する、**結果** トレースコンテキストが伝播されている
4. **前提** 通信自体が失敗した、または異常なステータスが返った、**操作** スパンの状態を確認する、**結果** エラーとして記録されている
5. **前提** 利用者が OpenTelemetry を設定していない、**操作** API を呼ぶ、**結果** 呼び出しは通常どおり成功し、計装は何も出力しない

### 境界的な状況

- 生成器のテンプレートを公式版へ再抽出したらどうなるか？ → ライセンス識別子の付与とトレース計装という独自のカスタマイズがすべて失われる。再適用してから再生成しなければ、識別子もトレースもないコードが生成される。再抽出は通常の再生成とは別のコマンドに分離してある。
- `openapi.json` から消えたスキーマの古い生成物は残らないか？ → 再生成は既存の生成物の削除を経由するため残らない。削除の対象は生成物のみで、手書きファイルは対象外である。
- 生成物と手書きファイルが同じ場所に置かれているのに、なぜ手書きが消えないのか？ → 手書きファイルと手書きパッケージを生成器の無視リストに登録して保護している。手書きファイルを新しく追加したときは、同時に登録する必要がある。
- 全件取得の途中でエラーが起きたら、それまでの結果は失われるか？ → 失われない。取得済みの結果とエラーの双方を返す。
- 最終ページの件数がちょうど 1 ページあたりの件数と等しい場合、終了を判定できるか？ → 次のページを引き、0 件を得た時点で終了する。1 回分の余分な呼び出しが発生するが、取りこぼしは起きない。
- ログ系 API とそれ以外を、どう取り違えずに判別するか？ → API 名の文字列で判別しない。`openapi.json` において `limit` パラメータがログ用のスキーマを参照しているかどうかから導出する。
- 生成器のバージョンが上がると出力が変わるか？ → 変わりうる。生成器のイメージは最新版を参照しており、同じ `openapi.json` でも生成器の更新によって差分が出ることがある。
- 生成器の出力はそのままで整形の基準を満たすか？ → 満たさない。構造体フィールドが整列されず、余分な空行やコメントのインデント差異が残るため、生成のたびに整形する。これを省くと、整形の指摘に大量の生成物が並び、手書きコードの整形漏れが埋もれる。

## 要件 *(必須)*

### 機能要件

**生成の入力と出力**

- **FR-001**: システムは、リポジトリルートの `openapi.json` を生成の単一の入力としなければならない
- **FR-002**: 生成には `openapitools/openapi-generator-cli` を用い、その最新版を参照しなければならない
- **FR-003**: 生成された API とモデルのファイルは、プロジェクト直下に置かれなければならない
- **FR-004**: 文書やテストなどの補助ファイルを生成してはならない。生成物は API・モデル・クライアント基盤に限る
- **FR-005**: 再生成は単一のコマンドで完結しなければならない。生成、全件取得の生成、整形、依存の整理、ビルドまでが一続きで実行される
- **FR-006**: 再生成は既存の生成物の削除を経由しなければならない。`openapi.json` から消えたスキーマや API に対応する古いファイルが残ってはならない
- **FR-007**: 削除の対象は生成物に限らなければならない。手書きファイルを削除してはならない
- **FR-008**: すべての生成物の先頭に、生成元のツールを示すコメントを付与しなければならない
- **FR-009**: すべての生成物の先頭に、ライセンス識別子を付与しなければならない
- **FR-010**: 手書きファイルおよび手書きパッケージは、生成器の無視リストに登録して保護しなければならない
- **FR-011**: 生成物は、生成の直後に整形されなければならない。生成器の出力はそのままでは整形の基準を満たさない

**全件取得**

- **FR-012**: システムは、`limit` と `offset` の双方を持つリクエスト型を検出し、そのすべてに対して全件取得の呼び出しを生成しなければならない。対象の固定の列挙を持ってはならない
- **FR-013**: 全件取得は、ページを繰り返し取得し、すべての結果を結合した 1 つの結果を返さなければならない
- **FR-014**: 1 ページあたりの取得件数は、通常の一覧 API では 10000、ログ系の一覧 API では 100 でなければならない
- **FR-015**: ログ系か否かの判定は、`openapi.json` において `limit` パラメータが参照するスキーマから導出しなければならない。API 名の文字列による判定を用いてはならない
- **FR-016**: 途中でエラーが発生した場合、それまでに取得した結果とエラーの双方を返さなければならない
- **FR-017**: 取得したページの件数が 1 ページあたりの件数を下回った時点で終了しなければならない。結果に重複を生じてはならない
- **FR-018**: 全件取得のコードは生成物として扱い、FR-008 および FR-009 の対象としなければならない

**エラーレスポンス**

- **FR-019**: システムは、HTTP ステータスコードごとに、`openapi.json` がそのステータスに定義するエラースキーマへ応答本文を復号しなければならない
- **FR-020**: 復号した内容は、返されるエラーから利用者が取り出せる形で保持されなければならない
- **FR-021**: 返されるエラーの文言には、ステータス行と、応答から抽出したエラーの内容の双方を含めなければならない
- **FR-022**: 応答本文の復号に失敗した場合も、ステータスを含むエラーを返し、HTTP レスポンス自体を失ってはならない

**トレース**

- **FR-023**: システムは、API 呼び出しごとにクライアント種別のスパンを生成しなければならない
- **FR-024**: スパンには、HTTP メソッド・URL・接続先ホスト・応答ステータスコードを属性として付与しなければならない
- **FR-025**: トレースコンテキストを、送信するリクエストのヘッダへ伝播しなければならない
- **FR-026**: 通信自体の失敗、および異常な応答ステータスの場合は、スパンの状態をエラーにしなければならない
- **FR-027**: 計装スコープの名前は、本モジュールのパスでなければならない
- **FR-028**: 利用者が OpenTelemetry を設定していない場合、計装は何も出力してはならない。API 呼び出しの挙動を変えてはならない

**生成器のカスタマイズの保全**

- **FR-029**: ライセンス識別子の付与とトレース計装は、生成器のテンプレートのカスタマイズとして実現され、生成物の前提としなければならない
- **FR-030**: テンプレートを公式版へ再抽出する手段は、通常の再生成とは別のコマンドとして分離しなければならない。再抽出がカスタマイズを失わせることを、その手段の位置に明記しなければならない

### 主要な実体

- **API 仕様 (`openapi.json`)**: 生成の単一の入力。API・モデル・エラースキーマ・ページングのパラメータの定義を持つ
- **生成物と手書きコードの境界**: どのファイルが再生成で作り直されるかの定義。生成物の一覧 (削除の対象) と、手書きの保護一覧 (無視リスト) の 2 つで表される
- **Pager リクエスト**: `limit` と `offset` の双方を持つリクエスト型。全件取得を生成する対象であり、ログ系か否かの区分を持つ
- **エラーモデル**: HTTP ステータスコードごとに `openapi.json` が定義するエラー応答の構造。ステータスコードから対応する型が定まる
- **計装スコープ**: トレースの発生源を示す名前。本モジュールのパスと一対一で対応する
- **テンプレートのカスタマイズ**: 生成物の前提となる独自の変更。ライセンス識別子の付与と、トレース計装の 2 つからなる

## 前提

- 本機能は実装済みである。本仕様は、CLAUDE.md「go package 生成用プログラム作成タスク」の記述と現在の実装から起こした事後仕様であり、新規の作業を含まない。CLAUDE.md は本仕様への移行に伴って削除された
- CLAUDE.md 仕様 7 は「400 Bad Request の場合は BadRequestError 構造体を作成し」と例示していたが、実装はエラー型の名前を `openapi.json` のスキーマ名から導出する (400 に対応する型は `BadRequestError` ではない)。固定の命名規約を持たないのは、生成器がスキーマ名をそのまま型名に用いるためである。ステータスコードから対応する型を得るという要件 (FR-019) は満たされており、名前の差は生成方式に由来する
- 生成元を示すコメントの文面は、生成器由来の生成物と全件取得の生成物とで句読点が異なる。いずれも Go の慣行が定める形式を満たすため、統一は要件としない
- 生成器のイメージは最新版を参照する。CLAUDE.md 仕様 2 が最新版の使用を求めていたためである。このため、同じ `openapi.json` に対しても生成器の更新によって出力が変わりうる。厳密な再現性が必要になった場合は、版の固定を別途検討する。憲章が版の単一出典を求めているのは検査ツールに対してであり、生成器はその対象ではない
- 生成物に対する単体テストは生成しない (憲章 原則 II)。検証は手書きコードの単体テストと統合テストで行う
- 生成には Docker の実行環境を必要とする
- 全件取得の 1 ページあたりの既定件数 (通常 10000 / ログ系 100) の変更は、破壊的変更として扱う (憲章 原則 V)
- 本仕様は、生成された API クライアントの上に載る高レベルのユーティリティを含まない。それは 003-utils-highlevel-api が扱う
