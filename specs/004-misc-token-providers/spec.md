# 機能仕様: シークレット管理サービスからのトークン取得

**機能ブランチ**: `004-misc-token-providers`

**作成日**: 2026-09-09

**状態**: 実装済み (CLAUDE.md から移行した事後仕様)

**憲章**: v2.0.0 の原則 II、原則 III、原則 V (本体への依存追加の禁止と optional な機能の隔離)、および「ライセンス」ブロックに整合

**入力**: CLAUDE.md「misc」節の移行。すなわち「他のパッケージに依存する optional な機能は `github.com/iij/dpf-go/misc` に配置する。misc 以下は go.mod を持つ独立したモジュールとする」および HashiCorp Vault・AWS Secrets Manager・Azure Key Vault・Google Secret Manager の 4 つからトークンを取得する処理

## 利用シナリオと検証 *(必須)*

### 利用シナリオ 1 - シークレット管理サービスに置いたトークンで API を呼べる (優先度: P1)

利用者は DPF-API のアクセストークンを、ファイルや環境変数ではなくシークレット管理サービスに置いている。利用者は使っているサービスに対応する追加モジュールを取り込み、認証済みのクライアントとシークレットの位置を渡して、トークンを取得する処理を得る。それをそのまま DPF-API のクライアント生成へ渡すと、API リクエストのたびにサービスからトークンが取得される。シークレットを更新すれば、プログラムを再起動せずに反映される。

**この優先度の理由**: 本機能の存在理由そのものである。アクセストークンをファイルや環境変数に置くと、ローテーションのたびに配置の更新が必要になり、平文で残る期間も長い。シークレット管理サービスを使う利用者にとって、そこから取得できないことは本ライブラリを採用できない理由になりうる。

**独立した検証**: 各サービスの操作を差し替えた状態でトークンの取得処理を作り、期待するトークンが返ることを確認できる。得られた処理が DPF-API のクライアント生成へそのまま渡せる形であることを確認できる。同じ処理を複数回評価したときに、そのたびにサービスへ問い合わせることを確認できる。

**受け入れシナリオ**:

1. **前提** シークレット管理サービスにトークンが格納されている、**操作** クライアントとシークレットの位置を渡して取得処理を作り、それを評価する、**結果** 格納されているトークンが返る
2. **前提** 取得処理を得た、**操作** それを DPF-API のクライアント生成へ渡す、**結果** 追加の変換なしに受け付けられる
3. **前提** 取得処理を得た、**操作** 複数回評価する、**結果** そのたびにサービスへ問い合わせ、更新後のシークレットが反映される
4. **前提** シークレットの位置に何も格納されていない、または値が空である、**操作** 取得処理を評価する、**結果** 空であることを判別できるエラーが返る
5. **前提** シークレットへの問い合わせ自体が失敗する、**操作** 取得処理を評価する、**結果** 元の失敗の原因が判別できるエラーが返る
6. **前提** 呼び出し側が処理を打ち切る、**操作** 取得処理を評価する、**結果** 打ち切りに応じる

---

### 利用シナリオ 2 - シークレットの置き方に合わせて取り出せる (優先度: P2)

利用者のシークレットは、値そのものがトークンである場合もあれば、複数の値を含む構造の中の 1 つのキーである場合もある。バージョンを指定して取り出したい場合もある。利用者は、既定のまま使えるならオプションを渡さず、必要な場合にのみ置き方を指定する。

**この優先度の理由**: シークレットの置き方は利用者の運用に依存し、本ライブラリが決められない。既定を決め打ちにすると、既存の運用に合わない利用者は使えない。一方で、選択肢を必須の引数にすると、既定で足りる大多数の利用者に不要な指定を強いる。既定値とオプションの組み合わせにする必要がある。

**独立した検証**: 値そのものがトークンである場合と、構造の中のキーである場合の双方で、期待する値が取り出せることを確認できる。存在しないキーを指定した場合にそれを判別できるエラーが返ることを確認できる。バージョンを指定した場合に、そのバージョンが問い合わせに使われることを確認できる。既定値が用いられることを、オプションを渡さない場合の問い合わせ内容で確認できる。

**受け入れシナリオ**:

1. **前提** シークレットの値そのものがトークンである、**操作** 取り出すキーを指定せずに評価する、**結果** 値の全体がトークンとして返る
2. **前提** シークレットが複数の値を含む構造である、**操作** 取り出すキーを指定して評価する、**結果** そのキーの値が返る
3. **前提** 指定したキーがシークレットの中に存在しない、**操作** 評価する、**結果** キーが見つからないことを判別できるエラーが返る
4. **前提** バージョンを指定した、**操作** 評価する、**結果** そのバージョンのシークレットが問い合わせに使われる
5. **前提** バージョンを指定していない、**操作** 評価する、**結果** そのサービスにおける既定のバージョンが使われる
6. **前提** オプションに空の値を渡した、**操作** 取得処理を作る、**結果** その指定は無視され、既定値が使われる
7. **前提** シークレットの位置を、識別子ではなく完全な形で指定した、**操作** 取得処理を作る、**結果** 補助的な指定 (所属など) は不要である

---

### 利用シナリオ 3 - 使わないサービスの依存を持ち込まずに済む (優先度: P3)

利用者は Vault だけを使っている。DPF-API のクライアントを取り込んでも、AWS・Azure・Google の SDK は依存に現れない。Vault を使わない利用者には、Vault の SDK もソース提供義務のあるライセンスも及ばない。

**この優先度の理由**: シークレット管理サービスの SDK はいずれも依存が重く、ライセンスの条件も一様でない。本ライブラリはライブラリであり、依存は利用者のビルドと配布物へそのまま漏れる。分離できていなければ、4 つのサービスの SDK すべてが、どれも使わない利用者の配布物に入る。優先度を最後に置くのは、これが個々の取得機能の正しさではなく、モジュールの分割という構造の要件であるためである。

**独立した検証**: 本体モジュールの依存の一覧に、シークレット管理サービスの SDK が現れないことを確認できる。各追加モジュールが独立して取得・ビルドできることを確認できる。ソース提供義務のあるライセンスの依存が、本体ではなく特定の追加モジュールに閉じていることを確認できる。

**受け入れシナリオ**:

1. **前提** 利用者が本体モジュールのみを取り込んだ、**操作** 依存の一覧を確認する、**結果** シークレット管理サービスの SDK は現れない
2. **前提** 利用者が 1 つのサービスの追加モジュールを取り込んだ、**操作** 依存の一覧を確認する、**結果** 他の 3 つのサービスの SDK は現れない
3. **前提** 追加モジュールを単独で取得した、**操作** その内容を確認する、**結果** ライセンスの全文が同梱されている
4. **前提** ソース提供義務のあるライセンスの依存がある、**操作** それがどのモジュールに属するかを確認する、**結果** 本体ではなく、そのサービスの追加モジュールに閉じている
5. **前提** 各追加モジュールである、**操作** ビルドとテストを実行する、**結果** それぞれ独立して成功する

---

### 境界的な状況

- 4 つのサービスで取得処理の作り方は揃っているか？ → 揃っている。いずれもクライアントとシークレットの位置を必須の引数とし、置き方の違いをオプションで表す。返るものはいずれも同じ形の取得処理であり、DPF-API のクライアント生成へそのまま渡せる。
- クライアントが渡されなかった場合はどうなるか？ → 取得処理を作る時点でエラーを返す。評価の時点まで遅らせない。
- シークレットの位置が空だった場合はどうなるか？ → 取得処理を作る時点でエラーを返す。
- Vault の KV シークレットエンジンのバージョンが 1 と 2 で読み出し方が違うが、どう扱うか？ → バージョンをオプションで指定し、それに応じた読み出しを行う。既定はバージョン 2 とする。1 と 2 以外を指定した場合は、取得処理を作る時点でエラーを返す。
- AWS のシークレットが文字列ではなくバイナリで格納されている場合はどうなるか？ → 文字列とバイナリの双方から値を取り出せる。
- Google のシークレットの位置は、識別子と完全な形のどちらで指定するか？ → どちらでも指定できる。識別子で指定する場合は所属の指定が必須であり、欠けていれば取得処理を作る時点でエラーを返す。完全な形で指定する場合、バージョンまで含めることもでき、その場合はバージョンのオプションは無視される。
- シークレットの値が空だった場合と、キーが見つからなかった場合は区別できるか？ → 区別できる。それぞれ別のエラーとして返す。
- 認証はどう行うか？ → 本機能は認証を行わない。認証済みのクライアントを利用者から受け取る。認証の方式はサービスごとに多岐にわたり、利用者の環境に依存するためである。
- 単体テストのために実際のサービスへ接続する必要があるか？ → ない。各サービスの操作は差し替えられる形で受け取る。
- トークンをどこかに保持するか？ → 本機能では保持しない。評価のたびにサービスへ問い合わせる。保持したい場合は、DPF-API のクライアント側の有効期間の指定を用いる。

## 要件 *(必須)*

### 機能要件

**配置と分離**

- **FR-001**: 他のパッケージに依存する optional な機能は、本体とは別の位置に配置しなければならない
- **FR-002**: 各サービスの機能は、それぞれ独立したモジュールとして構成されなければならない。1 つのモジュールに複数のサービスをまとめてはならない
- **FR-003**: 本体モジュールの依存に、シークレット管理サービスの SDK が現れてはならない
- **FR-004**: あるサービスの追加モジュールの依存に、他のサービスの SDK が現れてはならない
- **FR-005**: 各追加モジュールには、ライセンスの全文を同梱しなければならない。独立して取得した利用者にライセンスが届かない状態を作ってはならない
- **FR-006**: ソース提供義務を伴うライセンスの依存は、本体モジュールに現れてはならない。当該サービスの追加モジュールに閉じていなければならない

**取得処理の形**

- **FR-007**: 各サービスは、トークンを返す処理を生成する手段を提供しなければならない。生成された処理は、DPF-API のクライアント生成が受け付ける形と一致しなければならない
- **FR-008**: 生成の必須の引数は、認証済みのクライアントと、シークレットの位置の 2 つでなければならない
- **FR-009**: クライアントが与えられていない場合、またはシークレットの位置が空である場合は、生成の時点でエラーを返さなければならない。評価の時点まで遅らせてはならない
- **FR-010**: 置き方の違いはオプションで指定されなければならない。既定で足りる利用者にオプションの指定を要求してはならない
- **FR-011**: オプションに空の値が渡された場合は、その指定を無視し既定値を用いなければならない
- **FR-012**: 生成された処理は、評価のたびにサービスへ問い合わせなければならない。本機能の内部でトークンを保持してはならない
- **FR-013**: 生成された処理は、呼び出し側の打ち切りに応じなければならない
- **FR-014**: 本機能は認証を行ってはならない。認証済みのクライアントを利用者から受け取らなければならない
- **FR-015**: 各サービスの操作は、テスト時に差し替えられる形で受け取らなければならない。単体テストが実際のサービスへの接続を必要としてはならない

**シークレットの取り出し**

- **FR-016**: シークレットの値そのものをトークンとして扱えなければならない
- **FR-017**: シークレットを複数の値を含む構造として解釈し、指定したキーの値をトークンとして取り出せなければならない
- **FR-018**: 指定したキーが存在しない場合は、キーが見つからないことを判別できるエラーを返さなければならない
- **FR-019**: シークレットの値が空である場合は、空であることを判別できるエラーを返さなければならない。キーが見つからない場合と区別できなければならない
- **FR-020**: シークレットのバージョンを指定できなければならない。指定がない場合は、そのサービスにおける既定のバージョンを用いなければならない
- **FR-021**: シークレットへの問い合わせが失敗した場合は、元の失敗の原因が判別できるエラーを返さなければならない

**サービスごとの要件**

- **FR-022**: Vault については、KV シークレットエンジンのマウントパス、トークンを格納するキー名、KV のバージョンを指定できなければならない。既定はそれぞれ標準のマウントパス、`token`、バージョン 2 とする
- **FR-023**: Vault の KV のバージョンは 1 と 2 の双方に対応し、それぞれの読み出し方で読まなければならない。1 と 2 以外が指定された場合は、生成の時点でエラーを返さなければならない
- **FR-024**: AWS については、シークレットを名前と識別名のいずれでも指定でき、バージョンの識別子とステージのラベルのいずれでも指定できなければならない
- **FR-025**: AWS のシークレットは、文字列で格納されている場合とバイナリで格納されている場合の双方から値を取り出せなければならない
- **FR-026**: Azure については、シークレットを名前で指定し、バージョンを指定できなければならない。指定がない場合は最新のバージョンを用いなければならない
- **FR-027**: Google については、シークレットを識別子で指定する形と、所属を含む完全な形で指定する形の双方に対応しなければならない。識別子で指定する場合は所属の指定を必須とし、欠けていれば生成の時点でエラーを返さなければならない
- **FR-028**: Google において、完全な形の指定にバージョンまで含まれている場合は、バージョンのオプションを無視しなければならない

**共通**

- **FR-029**: 公開されたパッケージ・型・関数・エラー値には、godoc 形式のコメントを付与しなければならない
- **FR-030**: 各パッケージは用途・使い方・関連パッケージを記述した文書を持たなければならない
- **FR-031**: 公開挙動には単体テストを付与しなければならない。単体テストはネットワークアクセスを必要としてはならない
- **FR-032**: すべてのファイルの先頭にライセンス識別子を置かなければならない
- **FR-033**: ビルド・テスト・各検査の対象は、リポジトリ内のモジュールの定義から導出されなければならない。追加モジュールが増えたときに対象から漏れてはならない
- **FR-034**: `unsafe` パッケージおよび unsafe な機能を使用してはならない
- **FR-035**: 各モジュールの内部でログを出力してはならない

### 主要な実体

- **トークンの取得処理**: 評価のたびにシークレット管理サービスへ問い合わせ、アクセストークンを返す処理。DPF-API のクライアントが受け付ける形と一致する
- **シークレットの位置**: 対象のシークレットを一意に指す情報。サービスごとに構成が異なり、Vault はマウントパスとパス、AWS は名前または識別名、Azure は名前、Google は識別子と所属または完全な形からなる。バージョンの指定を伴いうる
- **取り出しの設定**: シークレットの置き方を表す指定。値の全体を用いるか、構造の中の特定のキーを用いるかの区別と、サービスごとの固有の設定 (Vault の KV のバージョンなど) からなる
- **追加モジュール**: 1 つのサービスに対応する独立したモジュール。自身の依存の定義とライセンスの全文を持ち、他のサービスの依存を含まない

- **SC-002**: 4 つのサービスが返す取得処理のうち、DPF-API のクライアント生成へそのまま渡せないものが 0 件である
- **SC-003**: 本体モジュールの依存に現れるシークレット管理サービスの SDK が 0 件である
- **SC-004**: ある追加モジュールの依存に現れる他のサービスの SDK が 0 件である
- **SC-005**: ライセンスの全文を同梱していない追加モジュールが 0 件である
- **SC-006**: 本体モジュールの依存のうち、ソース提供義務を伴うライセンスを持つものが 0 件である
- **SC-007**: 単体テストが実際のシークレット管理サービスへの接続を必要とする箇所が 0 件である
- **SC-008**: クライアントの欠落、シークレットの位置の空、および設定の矛盾が、取得処理の評価時ではなく生成時に 100% 検出される
- **SC-009**: シークレットの値が空である場合と、指定したキーが存在しない場合を区別できないサービスが 0 件である
- **SC-010**: 公開された型・関数・エラー値のうち、godoc 形式のコメントを欠くものが 0 件である

- **SC-013**: 各追加モジュールが独立してビルドおよびテストに成功する (失敗するモジュールが 0 件)
- **SC-014**: 各モジュールの内部によるログ出力が 0 件である

## 前提

- 本機能は実装済みである。本仕様は、CLAUDE.md「misc」節の記述と現在の実装から起こした事後仕様であり、新規の作業を含まない。CLAUDE.md は本仕様への移行に伴って削除された
- CLAUDE.md は 4 つのサービスについて「token 取得の処理を提供する」とのみ記していた。シークレットの置き方に関する要件 (値の全体か構造の中のキーか、バージョンの指定、Vault の KV のバージョン、AWS のバイナリ形式、Google の完全な形の指定) は CLAUDE.md に記載がなく、実装時に各サービスの仕様へ合わせて追加されたものである
- 認証は本機能の範囲外である。利用者は各サービスの標準的な方式で認証済みのクライアントを用意する。方式が多岐にわたり、利用者の実行環境に依存するためである
- トークンの短期的な保持は本機能の範囲外である。DPF-API のクライアント側の有効期間の指定 (003-utils-highlevel-api) が担う
- Vault の SDK はソース提供義務を伴うライセンスの依存をもたらす。これが本体へ及ばないことは、追加モジュールとしての分離 (FR-006) によって担保される。この分離は憲章の原則 V が本体への依存追加を禁じる理由の 1 つである
- 各追加モジュールの依存は、それぞれのサービスの公式な SDK を用いる前提とする。SDK の選定は本仕様では定めない
- 追加モジュールが増えた場合も、ビルド・テスト・検査の対象はモジュールの定義から導出されるため、対象一覧の書き換えを必要としない (憲章 原則 II)
