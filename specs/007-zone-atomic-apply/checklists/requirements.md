## 補足

- 未チェックの項目は、`/speckit-clarify` または `/speckit-plan` の前に仕様の更新を要する

### 検証で修正した点

- **初版の FR-007 と FR-009 が矛盾していた**。「反映が成功した場合は解放を行ってはならない」
  と無条件に書いており、「排他が残っていた場合は解放を試みる」と両立しなかった。
  層を分けた改訂版では、後始末を「自分が保持者である場合に限り解放する」(FR-007) と
  定めることで解消した。一括置き換えの側は、反映の前に延長を止めて解放の対象から外し
  (FR-017)、反映の後に残っていた場合に限り解放する (FR-021)。
- **層を分ける改訂を行った**。初版はゾーン全体の一括置き換えだけを扱っていた。利用者の
  指摘により、「排他を保持したまま処理を実行する」汎用の操作を下の層として切り出し、
  一括置き換えをその上に載せる構成へ改めた。汎用の操作は単独で価値があり（取得と解放の
  対、保持期間の自動延長、奪われたときの通知を利用者に書かせない）、1 レコードずつ反映する
  流れにも使える。利用シナリオの優先度は、汎用の操作を P1、一括置き換えを P2 とした。

### 判断の記録

- **「実装の詳細を含んでいない」について**: 本仕様は SOA レコード、Zone Apex の NS
  レコード、公開されているレコード、未反映の編集といった語を用いている。これらは DPF-API の
  仕様書が定める語彙であり、本ライブラリにとっては実装技術ではなく問題領域そのものである。
  API そのものは「一括置き換えと反映を行う API」「公開されているレコードの一覧を取得する
  API」と役割で書き、関数名を持ち込んでいない。003〜006 と同じ水準に揃えた。
  既定値の変更手段を Option として公開すること (FR-012・FR-016)、godoc と `CHANGELOG.md` の
  更新 (FR-017〜FR-020)、`integration` の区分 (FR-022) は憲章が定める規律であり、要件として
  明記する必要があるため残した。
- **「異常終了（panic）」という語について**: FR-015 は実装言語の用語を含む。捕捉するか
  しないかで排他の後始末が変わり、利用者に見える挙動が分かれるため、曖昧な言い換えでは
  要件として検証できない。この 1 語に限って持ち込んだ。
- **呼び出しの形と関数名を定めていないことについて**: 引数の並び、どの API クライアントを
  受け取るか、既存の排他の型 (006 の Mutex) との関係、関数名は、いずれも実装の詳細である
  ため前提に「計画で決める」と記し、要件には含めていない。検討中の案は、汎用の操作を
  排他の型のメソッドとする形（利用者の記述にあった `LockedProcess` に相当）、および
  一括置き換えを (1) 排他の型を渡す関数、(2) API クライアント全体を渡す関数、
  (3) 本ライブラリのクライアントラッパーのメソッド、のいずれかとする形である。
- **FR-017 が「公開する API の形に現れてはならない」と定めていることについて**: これは
  実装の制約ではなく、利用者に見える性質の要件である。一括置き換えが排他を解くという
  事情は一括置き換えの側の問題であり、汎用の操作を使う利用者に持ち込むべきではない。
  この要件があることで、汎用の操作の引数に「排他が解かれる場合の扱い」を表す要素を
  加える設計は選べなくなる。
- **実測に基づく前提について**: 「一括置き換えは SOA を作り直すため排他が失われる」
  「実行後に未反映の編集が残らない」「公開されているレコードの一覧は編集中の SOA を更新前の
  状態として返す」の 3 点は、2026-09-18 に実 API で確認した事実である
  (`internal/integration` の `TestLockFlow_AtomicChanges`)。006 が前提を確認せずに記述して
  同一ユーザ間で排他が成立しない状態を招いた経緯があるため、本仕様では確認済みの事実と
  未確認の事項 (反映の途中で排他が失われるか) を区別して記した。
