# 機能仕様: 排他を保持したままの実行と、ゾーン全体の一括置き換え

**機能ブランチ**: `007-zone-atomic-apply`

**作成日**: 2026-09-18

**状態**: ドラフト

**憲章**: v2.0.1 の原則 II (テストを伴う実装、統合テストの隔離)、原則 III (godoc と CHANGELOG の同時更新)、原則 V (ライブラリとしての規律、既定値は保守的に定め変更手段を Option として公開する) に整合

**入力**: 利用者による記述: "安全に案1が実行できるようなfuncを作った方がいいですかね。ZoneIDを指定して、Lockし、CurrentRecordsを取得して、ユーザ引数の関数で処理、その結果をPatchZoneAtomicChangesで適用"。および "まず、funcをLock内で実行するfuncを作ります。LockedProcess(func()) errorみたいなやつです。これは自動的にRenewします。そして、atomic_changes処理を実行するfuncもこのLockedProcess内で実行します。"

**関連**: 006-zone-lock-redesign（ゾーン単位の排他）。本機能はその排他の上に 2 つの層を重ねる。下の層は「排他を保持したまま処理を実行する」汎用の操作、上の層はその上に載る「ゾーン全体の一括置き換え」である

## 利用シナリオと検証 *(必須)*

### 利用シナリオ 1 - 排他を保持したまま処理を実行できる (優先度: P1)

利用者はゾーンを編集する処理を書く。その処理を排他の下で動かしたい。いま必要なのは
「取得する」「処理する」「解放する」を自分で並べ、失敗の経路ごとに解放を書き、さらに
処理が長引いたときに保持期間が切れないよう延長を仕込むことである。書き漏らすと、排他が
残って他のプログラムを止めるか、逆に気づかないうちに保護が切れる。

そこで、処理を渡すと排他の下で実行する操作を提供する。**保持期間は処理の実行中に自動で
延長される。** 処理がどれだけ長引いても、利用者が延長を書く必要はない。

排他を他者に奪われた場合（保持期間が切れた後に奪われた場合など）は、**処理へ渡した
打ち切りを発火させる。** 保護が切れたことを処理が知らないまま走り続ける状態を作らない。

**この優先度の理由**: 単独で価値がある。利用シナリオ 2 はこの上に載るため、こちらが土台で
ある。取得と解放の対を利用者に書かせないことは、排他の見直し（006）で塞いだ穴の続きで
ある。006 は「排他が成立しない」穴を塞いだが、「解放を書き忘れる」「延長を書き忘れる」
穴は利用者側に残っていた。

**独立した検証**: 処理を渡して操作を呼び、処理の実行中に排他が保持されていること、
終了後に解放されていることを確認できる。保持期間より長い処理でも保持が続くことを確認
できる。排他を他者に奪われた状況を作り、処理へ渡した打ち切りが発火し、判別できるエラーが
返ることを確認できる。

**受け入れシナリオ**:

1. **前提** 排他が取得されていない、**操作** 処理を渡して操作を呼ぶ、**結果** 排他が取得され、処理が実行され、終了後に解放される
2. **前提** 処理の実行に保持期間より長い時間がかかる、**操作** 操作を呼ぶ、**結果** 実行中に保持期間が自動で延長され、処理は中断されない
3. **前提** 処理の実行中に他者が排他を奪った、**操作** 延長の周期が到来する、**結果** 処理へ渡した打ち切りが発火し、保持者でないことを判別できるエラーが返る
4. **前提** 処理がエラーを返す、**操作** 操作の戻り値を確認する、**結果** そのエラーが種類を判別できる形で返り、排他は解放されている
5. **前提** 他者が排他を保持している、**操作** 操作を呼ぶ、**結果** まだ保持されていることを判別できるエラーが返る。処理は実行されない
6. **前提** 延長が通信の失敗などで一時的に失敗した、**操作** 次の延長の周期が到来する、**結果** 再試行され、成功すれば処理は継続する

### 利用シナリオ 2 - ゾーン全体を読んで編集し、一括で反映できる (優先度: P2)

利用者はゾーンのレコードを一括で書き換えたい。たとえば別の管理台帳と内容を突き合わせて、
差分をまとめて反映する。手順は「排他を取得する」「現在公開されているレコードを全件取得
する」「編集する」「一括置き換えと反映を行う」の 4 つである。

利用者が書くのは**編集の内容だけ**である。この操作は利用シナリオ 1 の上に載り、排他の
取得・延長・後始末に加えて、次の 3 つの落とし穴を塞ぐ。いずれも「知らないと踏む」種類の
もので、踏んだことに気づけない。

1. **SOA レコードを取り込むか否かのフラグは、既定が「取り込む」である。** 省略すると、
   現在公開されているレコードの一覧から組み立てたリクエストによって SOA が置き換わる。
   Zone Apex の NS レコードについても同じフラグがあり、同じく既定が「取り込む」である。
2. **一括置き換えは排他を解く。** 排他の情報（SOA に書いたラベル）は「未反映の編集」
   としてのみ存在し、一括置き換えは未反映の編集を引き継がない。したがってフラグの値は
   関係なく、どちらにしても排他は失われる。その結果、反映の後に解放を試みると
   「保持者でない」エラーになり、成功した操作が失敗として返る。反映の最中に延長が走ることも
   避けなければならない。
3. **現在公開されているレコードの一覧は、編集中の SOA を「更新前の状態」として返す。**
   レコードの一覧を取得する別の API が「更新予定」として返すのとは見え方が異なる。

**この優先度の理由**: 本機能の発端であり、利用者にとっての価値が最も大きい。ただし
利用シナリオ 1 の上に載るため、実装の順序は 1 の後になる。

**独立した検証**: 編集の内容を表す関数を 1 つ渡して操作を呼び、ゾーンのレコードが期待どおり
置き換わることを確認できる。呼び出しの前後で、排他が残らないこと、未反映の編集が残らない
ことを確認できる。SOA と Zone Apex の NS が置き換わっていないことを確認できる。

**受け入れシナリオ**:

1. **前提** ゾーンに排他が取得されていない、**操作** 編集の内容を表す関数を渡して操作を呼ぶ、**結果** 排他が取得され、公開されているレコードが関数に渡され、その戻り値でゾーンが置き換わって反映される
2. **前提** 操作が成功した、**操作** ゾーンの状態を確認する、**結果** 未反映の編集は残っていない。排他も残っていない
3. **前提** 操作が成功した、**操作** SOA レコードと Zone Apex の NS レコードを確認する、**結果** 操作の前と同じ内容である。編集の結果に含めていても取り込まれない
4. **前提** 操作が成功した、**操作** 戻り値を確認する、**結果** 成功である。解放を試みたことによる「保持者でない」エラーは返らない
5. **前提** 操作を呼んだ、**操作** 反映が完了するまで待つ、**結果** 反映の完了を待ってから復帰する。呼び出し側が非同期処理の完了を待つ必要はない
6. **前提** 編集の内容を表す関数が空の結果を返す、**操作** 操作を呼ぶ、**結果** 反映を試みずに判別できるエラーが返り、排他は解放されている

### 利用シナリオ 3 - 排他が取れないときの振る舞いを選べる (優先度: P3)

利用者の運用によって、排他が取れないときの望ましい振る舞いは異なる。定期実行の処理は
すぐ諦めて次回に任せたい。人が起動する処理は、取れるまで待ってほしい。

既定はすぐ諦めることとし、待つ場合は待機の間隔を指定できるようにする。待機の打ち切りは
呼び出し側の打ち切りに従う。

**この優先度の理由**: 待たない場合でも、呼び出し側が自分で繰り返せば同じことができる。
利便性の向上であり、正しさには関わらない。

**独立した検証**: 他者が排他を保持している状態で、待たない設定では即座にエラーが返り、
待つ設定では取得できるまで繰り返すことを確認できる。打ち切りに従うことを確認できる。

**受け入れシナリオ**:

1. **前提** 他者が排他を保持しており、待機を指定していない、**操作** 操作を呼ぶ、**結果** まだ保持されていることを判別できるエラーがただちに返る
2. **前提** 他者が排他を保持しており、待機を指定している、**操作** 操作を呼ぶ、**結果** 排他が取得できるまで指定した間隔で繰り返す
3. **前提** 待機中である、**操作** 呼び出しを打ち切る、**結果** 打ち切りを表すエラーが返る。ゾーンは変更されない

### 境界的な状況

- 処理が異常終了（panic）した場合はどうなるか？ → 捕捉しない。呼び出し側の異常をライブラリが握り潰すべきではない。この場合、排他は保持されたまま残り、保持期間の経過によって解ける。延長も止まるため、いずれ他者が取得できる。この振る舞いを文書に明記する。
- 延長が失敗し続けた場合はどうなるか？ → 保持期間が切れれば他者が奪える。奪われた時点で延長は「保持者でない」となり、処理へ渡した打ち切りが発火する。失敗が続く間も打ち切りは発火しないため、処理は保護が切れた状態で走りうる。この窓の長さは延長の間隔に依存することを文書に明記する。
- 処理が渡された打ち切りを無視した場合はどうなるか？ → ライブラリは処理の終了を待つ。打ち切りは通知の手段であり、強制的な中断はできない。処理が打ち切りを尊重することを前提とする旨を文書に明記する。
- 編集の内容を表す関数が空の結果を返した場合はどうなるか？ → 一括置き換えはレコードを 1 件以上必要とする。反映を試みずに判別できるエラーを返す。空のゾーンを作ってしまう事故を防ぐためでもある。
- 編集の内容を表す関数が SOA や Zone Apex の NS を結果に含めなかった場合はどうなるか？ → いずれも取り込まれないため結果は変わらない。含めても含めなくてもよい。
- 一括置き換えが成功した後に排他が残っていた場合はどうなるか？ → 反映が排他を解くことは実測済みだが、将来変わりうる。残っていた場合は解放を試み、その結果を呼び出し側へ返す。
- ゾーンに他者の未反映の編集がある場合はどうなるか？ → 一括置き換えは未反映の編集を残さないため、他者の編集中の内容を巻き込む。排他の下で行うことがその防止策であり、本機能が排他を必須とする理由である。
- ゾーンプロキシの設定が有効なゾーンではどうなるか？ → レコードを編集できないため、排他の取得の時点で失敗する。理由が判別できるエラーを返す。
- 1 レコードずつ変更して反映する流れには使えるか？ → 利用シナリオ 1 の操作は使える。この流れでは排他が解かれないため、処理の中で反映まで行い、その後に自動で解放される。利用シナリオ 2 の操作はゾーン全体の一括置き換えに限る。

## 要件 *(必須)*

### 機能要件

**排他を保持したままの実行**

- **FR-001**: 排他の取得、利用者が指定した処理の実行、終了時の後始末を 1 つの操作として提供しなければならない
- **FR-002**: 処理の実行中、排他の保持期間を自動で延長しなければならない。利用者に延長を書かせてはならない
- **FR-003**: 延長の間隔は既定値を持ち、変更手段を Option として公開しなければならない。既定値は保持期間から導き、保持期間より十分短くしなければならない
- **FR-004**: 延長によって保持者でないと判明した場合は、利用者の処理へ渡した打ち切りを発火させ、保持者でないことを判別できるエラーを返さなければならない。利用者の処理が返したエラーも併せて判別できる形で返さなければならない
- **FR-005**: 延長がそれ以外の理由で失敗した場合は、次の周期で再試行しなければならない。ただちに処理を中止してはならない
- **FR-006**: 利用者の処理には、打ち切りを伝えられる形の引数を渡さなければならない
- **FR-007**: 終了時の後始末では、自分が保持者である場合に限り解放しなければならない
- **FR-008**: 利用者の処理が返したエラーは、種類を判別できる形のまま返さなければならない。ライブラリ側のエラーで置き換えてはならない
- **FR-009**: 利用者の処理の異常終了（panic）を捕捉してはならない
- **FR-010**: 排他が取得できない場合は、まだ保持されていることを判別できるエラーを返さなければならない。このとき利用者の処理を実行してはならず、ゾーンを変更してはならない
- **FR-011**: 排他が取得できるまで待つかどうかを選べなければならない。既定は待たないこととし、待つ場合の間隔を指定する手段を Option として公開しなければならない
- **FR-012**: 待機は呼び出し側の打ち切りに従わなければならない

**ゾーン全体の一括置き換え**

- **FR-013**: ゾーン全体の読み取り・編集・一括置き換えと反映を 1 つの操作として提供しなければならない。この操作は FR-001 の操作の上に構築しなければならない
- **FR-014**: 利用者が指定する編集は、反映したいレコードの一覧を受け取り、同じ形の一覧を返すものでなければならない。公開されているレコードからその形への変換は本操作が行う。排他の操作やフラグの指定を利用者に求めてはならない
- **FR-014b**: 編集で触れなかった項目（ラベル・TTL・コメントを含む）は、編集の前と同じ内容で反映されなければならない。利用者が項目を落とす余地を作ってはならない
- **FR-015**: SOA レコードを取り込むか否かのフラグには、常に「取り込まない」を指定しなければならない。利用者が変更する手段を設けてはならない
- **FR-016**: Zone Apex の NS レコードを取り込むか否かのフラグについても、常に「取り込まない」を指定しなければならない。利用者が変更する手段を設けてはならない
- **FR-017**: 一括置き換えは排他を解くため、その実行前に自動延長を止め、終了時の解放も行わないようにしなければならない。この扱いは公開する API の形に現れてはならない。利用シナリオ 1 の操作を使う利用者に、排他が解かれる場合の扱いを意識させてはならない
- **FR-018**: 編集の結果が空の場合は、反映を試みずに、空であることを判別できるエラーを返さなければならない
- **FR-019**: 一括置き換えと反映の非同期処理の完了を待ってから復帰しなければならない
- **FR-020**: 反映に付けるコメントを指定する手段を Option として公開しなければならない
- **FR-021**: 反映が成功した後に排他が残っていた場合に限り、解放を試み、その結果を呼び出し側へ返さなければならない。残っているかどうかは、保持者が自分であるかによって判定する

**文書と検証**

- **FR-022**: 公開されているレコードの一覧が、編集中の SOA を「更新前の状態」として返すことを godoc に明記しなければならない
- **FR-023**: 一括置き換えが排他を解くこと、したがってこの操作が成功時に解放を行わないことを godoc に明記しなければならない
- **FR-024**: 利用シナリオ 1 の操作について、異常終了時に排他が残ること、延長が失敗し続けた場合に保護が切れた状態で処理が走りうること、打ち切りは通知であって強制的な中断ではないことを godoc に明記しなければならない
- **FR-025**: 1 レコードずつ変更して反映する流れでは、利用シナリオ 1 の操作を使えばよいことを godoc に明記しなければならない
- **FR-026**: 利用者に見える機能追加を `CHANGELOG.md` に記録しなければならない
- **FR-027**: 各段の成否の組み合わせ、延長の成功と失敗、打ち切りの発火を単体テストで確認しなければならない。ネットワークを必要としてはならない
- **FR-028**: 実 API での確認を、`integration` の区分で隔離された統合テストによって行わなければならない。確認する内容は、反映の成功、SOA と Zone Apex の NS が置き換わらないこと、操作の後に排他と未反映の編集が残らないこと、保持期間より長い処理で保持が続くこととする

### 主要な実体

- **利用者の処理**: 排他の下で実行される処理。打ち切りを伝えられる引数を受け取り、エラーを返す
- **編集の内容を表す関数**: 公開されているレコードの一覧を受け取り、反映したいレコードの一覧を返す。ゾーン全体の一括置き換えにおいて利用者が用意する唯一の部品
- **操作の設定**: 排他の設定（保持者・保持期間など、006 の排他が持つもの）、延長の間隔、取得を待つ間隔、反映に付けるコメント

## 成功基準 *(必須)*

### 測定可能な成果

- **SC-001**: 保持期間より長い処理を排他の下で実行したとき、処理の途中で排他が失われる事象が 0 件である
- **SC-002**: 排他を他者に奪われたときに、利用者の処理がそれを知らされないまま継続する事象が 0 件である（延長の間隔以内に通知される）
- **SC-003**: ゾーン全体の一括置き換えを本操作で行ったとき、SOA レコードまたは Zone Apex の NS レコードが意図せず置き換わる事象が 0 件である
- **SC-004**: 本操作が成功した後に、呼び出し側が「保持者でない」エラーを受け取る事象が 0 件である
- **SC-005**: 処理または反映の失敗によって排他が保持されたまま残る事象が 0 件である（利用者の処理の異常終了を除く）
- **SC-006**: 利用者が書く必要があるのは、処理の内容（または編集の内容）だけである。排他の取得・延長・解放、取り込みの可否を決めるフラグ、非同期処理の完了待ちのいずれも書く必要がない
- **SC-007**: ゾーン全体の一括置き換えの完了後、ゾーンに未反映の編集が残る事象が 0 件である
- **SC-008**: 排他を取得できなかった場合に、利用者の処理が実行される事象、およびゾーンが変更される事象が 0 件である
- **SC-009**: 本操作によって、利用者がレコードに付けたラベル・TTL・コメントが意図せず失われる事象が 0 件である。編集で触れなかった項目は、編集の前と同じ内容で反映される

## 前提

- 本機能は 006-zone-lock-redesign の排他を用いる。排他そのものの性質（再入できない、延長は取得とは別の操作、取得・延長・解放がゾーン反映を伴わない）は 006 に従う
- 一括置き換えと反映を行う API を実行すると、排他の情報が失われる。排他のラベルは SOA の「未反映の編集」としてのみ存在し、この API は未反映の編集を引き継がないためである。SOA を取り込むか否かのフラグの値は関係しない。2026-09-18 に実 API で確認した（反映の完了後、SOA のラベルは失われ、他者が排他を取得できる状態になっていた）
- 反映の完了時点で排他が失われていることは確認したが、反映の途中（非同期処理の完了前）に失われるかどうかは確認していない。本機能は反映の前に延長を止め、完了を待ってから解放の判定を行うため、この区別は利用者には影響しない
- 一括置き換えと反映を行う API は、レコードを 1 件以上必要とする
- 一括置き換えと反映を行う API は、実行後にゾーンの未反映の編集を残さない。2026-09-18 の実測では、排他による未反映の編集 1 件がある状態で実行し、実行後の未反映件数は 0 件であった
- 公開されているレコードの一覧を取得する API は、編集中の SOA を「更新前の状態」として返す。2026-09-18 の実測で確認した。このため、この一覧から組み立てたリクエストに排他のラベルは含まれない
- 反映済みのラベルは一括置き換えの後も残る（利用者による確認）。失われるのは未反映の編集として書かれたラベル、すなわち排他のものだけである。したがって利用者が SOA に付けた 8 つのラベル（006 FR-014）は本操作で失われない。この点は統合テストで確認する（SC-009）
- SOA 以外のレコードのラベルは、リクエストに含めたから残るのであって、一括置き換えが保存するわけではない。リクエストから落とせば消える。このため編集の入出力を同じ形にし、利用者が項目を落とす余地を作らない
- 1 レコードずつ変更して反映する流れ（編集中レコードのゾーン反映）では排他が解かれない。2026-09-18 の実測で確認した。この流れは利用シナリオ 1 の操作で扱える
- 上記の流れでは、ゾーン反映によって排他のラベルが反映済みになる。その後の解放は未反映の編集を作るため、**これを破棄すると反映済みの側に残った排他（奪ってよい時刻が未来）が復活する。** 2026-09-24 の統合テストで実際にこれが起き、後続の操作が保持期間のあいだ取得できなくなった。解放は破棄ではなく反映によって確定させる必要がある。この注意は利用者向けの文書に明記する（FR-024）
- 打ち切りは通知であり、強制的な中断ではない。利用者の処理が打ち切りを尊重することを前提とする
- 呼び出しの形（引数の並び、どの API クライアントを受け取るか、既存の排他の型との関係、関数名）は本仕様では定めない。実装計画で決める
- 既定値は保守的に定め、変更手段を Option として公開する（憲章 原則 V）。既定値の変更は破壊的変更として扱う
- 実 API に触れる挙動の確認は `integration` の区分で隔離された統合テストで行い、`make test` の対象には含めない（憲章 原則 II）
