## 概要

006 で排他そのものの欠陥は塞いだが、利用者側には「取得と解放の対を書く」「長い処理では
延長を書く」「一括置き換えの落とし穴を避ける」という負担が残った。とくに最後は深刻で、
**ゾーン全体の一括置き換えは排他を解く**（[research.md](./research.md) D1 で実測）。
これを知らずに使うと、編集の途中で保護が切れ、反映の後の解放が「保持者でない」エラーに
なる。文書で注意を促す方針は本作業の途中で一度採ったが、**踏めない形にする**方針へ改めた。

2 つの層を作る。

1. **`Mutex.Do`** — 排他を保持したまま処理を実行する。保持期間は自動で延長する。処理へ渡す
   context は、排他を奪われた時点で打ち切る（[research.md](./research.md) D3・D4）。
   1 レコードずつ反映する流れはこの層で足りる。実測で、その流れでは排他が解かれないことを
   確認している（同 D1）。
2. **`ZoneApplier.Apply`** — ゾーン全体を読んで編集し、一括置き換えと反映を行う。`Do` の
   上に載る。取り込みの可否を決める 2 つのフラグは常に「取り込まない」で固定し、利用者が
   変更する手段を設けない（同 D2）。

方針は 5 つある。

1. **排他を外へ見せない。** `ZoneApplier` は `Mutex` を内部に持つ。消費済みの排他を利用者が
   持ち続けられないようにするためである。排他は再入できないため（006 FR-017）、共有しても
   使い道が無く、見せないことによる損失は無い（[research.md](./research.md) D2）。
2. **一括置き換えが排他を解くという事情を、公開 API の形に出さない。** `Do` の内部に
   非公開の値を置き、一括置き換えの実装だけが「この先で排他が解かれる」ことを通知する。
   `Do` を使う利用者のコールバックは 1 引数のままである（FR-017、同 D7）。
3. **延長の失敗は理由で分ける。** 「保持者でない」はただちに打ち切り、それ以外は次の周期で
   再試行する。保持期間の 1/3 を既定の間隔とすることで、2 回連続の失敗でも間に合う
   （同 D5・D6）。
4. **終了時の解放は `Unlock` の性質をそのまま使う。** `Unlock` は保持者でない場合に
   `ErrNotLockHolder` を返すため、「自分が保持者である場合に限り解放する」は追加の
   読み取りなしで満たせる（同 D8）。
5. **goroutine を Do の外へ漏らさない。** 延長は `Do` の中で起動し、`Do` が復帰する前に
   必ず終了を待つ。ライブラリが呼び出し側のプロセスに goroutine を置き去りにしない
   （憲章 原則 V「呼び出し側の環境を侵さない」）。

## 技術的な前提

**言語 / バージョン**: Go 1.27（`go.mod` は `go 1.27.0`）

**主要な依存**: 追加なし。本体の `go.mod` は変更しない。実装で新たに使う標準ライブラリは
`errors`（`errors.Join` による延長エラーと処理エラーの併記）、`sync`、`time`

**保存先**: 該当なし。排他の状態は DPF-API 上のレコードとラベルとして保持する（006）。
`Do` の実行中のみ、延長のための goroutine と派生 context をメモリ上に持つ

**テスト**: 単体テストは `go test ./... -race -count=1`（既存の `make test`）。goroutine を
使うため `-race` での検証が要件である。継ぎ目は既存の `httptest` 模擬サーバ
（`utils/lock_test.go` の `lockServer`）を拡張して使う。実 API の確認は
`make test-integration`

**対象環境**: 本ライブラリを取り込む Go プログラム全般

**プロジェクト種別**: Go ライブラリ（既存パッケージ `utils` への機能追加。新規モジュールなし）

**性能目標**: `Apply` 1 回あたりの API 呼び出しは 12 回程度（排他の取得 8 回、公開レコードの
取得 1 回、一括置き換え 1 回、終了時の解放の判定 2 回）に加えて、反映の JOB のポーリングと、
処理時間に応じた延長（1 回につき 3 回）である。既定のレート制限（5 req/s）では取得と反映で
約 3 秒。`Do` のみの場合は排他の取得と解放で 10 回程度

**制約**:
- 本体の `go.mod` に依存を追加しない（憲章 原則 V）
- ライブラリ内でログを出力しない。`unsafe` を使わない（同）
- `Do` が起動した goroutine を、`Do` の復帰後に残してはならない（同）
- 単体テストはネットワークを必要としない（憲章 原則 II）
- 既定値は保守的に定め、変更手段を Option として公開する（憲章 原則 V）
- 取り込みの可否を決める 2 つのフラグは利用者に変更させない（FR-015・FR-016）。これは
  「変更手段を Option として公開する」の例外であり、意図的な制約である
- 利用者の処理の異常終了（panic）を捕捉しない（FR-009）

**規模 / 範囲**: 要件 28 件（FR-001〜FR-028）／成功基準 8 件（SC-001〜SC-008）。
新規に公開するものは、メソッド 2 件（`Mutex.Do` / `ZoneApplier.Apply`）、型 3 件
（`ZoneApplier` / `ZoneRecordsEditor` / `ApplyOption`）、コンストラクタ 1 件、Option 3 件、
番兵エラー 1 件、定数 1 件（延長の間隔の既定を表す比またはその導出）。`dpf.ZonesApi` に
メソッド 1 件を追加し、`dpf.JobsApi` を新設。新規ファイルは 2 件、変更するファイルは
10 件（[research.md](./research.md) D12）

**要明確化**: なし。仕様に未解決のマーカーは無い。仕様が実装に委ねた選択（呼び出しの形、
関数名、延長の間隔の既定値、非公開の内部経路の作り）は [research.md](./research.md) D2〜D11
で決定した。実測が必要だった前提は D1 で確認済みである

**延長の一時的な失敗を報告しないことについて**: 憲章 原則 V はライブラリ内でのログ出力を
禁じており、異常は error として返すことを求めている。延長が一時的に失敗し、その後回復して
処理も成功した場合、返せる error は無い（処理は成功しているため）。この事象を利用者へ
伝える手段は現状の設計には無い。**意図的にそうしている。** 回復した一時的な失敗は利用者に
対処の余地がなく、伝えても行動が変わらない。伝えるべきなのは「排他を失った」ことだけで
あり、それは打ち切りとエラーで伝える。将来、観測が必要になれば OpenTelemetry の
トレース（憲章が観測手段として挙げているもの）へ載せる余地がある。

**2 つのフラグを Option にしないことについて**: 憲章 原則 V は「挙動の既定値は保守的に定め、
変更手段を Option として公開しなければならない」と定める。本機能は取り込みの可否を決める
2 つのフラグを固定し、変更手段を設けない（FR-015〜FR-017）。これは原則の文言からの逸脱に
見えるが、逸脱ではない。**これらは本機能の既定値ではなく、本機能が成立するための前提で
ある。** 変更を許せば排他が壊れ、機能そのものが目的を果たさなくなる。変更したい利用者は
生成された API を直接呼べばよく、その道は閉じていない。

**破壊的変更の一覧**（`CHANGELOG.md` に記載する内容）:

1. `dpf.ZonesApi` に `PatchZoneAtomicChanges` が増える。`client.ZonesAPI` を渡している
   場合は影響しない。このインターフェースを自分で実装している場合は追随が必要

## 複雑さの記録

> **憲章への適合確認で、正当化が必要な逸脱があった場合にのみ記入する**

憲章違反なし。ただし、単純さを損なう選択を 3 つ意図して行っているため記録する。

| 選択 | 必要な理由 | より単純な代替案を採らない理由 |
|---|---|---|
| 公開の `Do` とは別に、非公開の `doHold` / `hold` を設ける | 一括置き換えは排他を解くため、反映の前に延長を止め、終了時の無条件の解放を避ける必要がある | 公開の `Hold` 型をコールバックへ渡す案は、`Do` を使うすべての利用者に一括置き換えの都合を背負わせる（FR-017 が禁じている）。終了時の `ErrNotLockHolder` を常に無視する案は、本当に奪われた場合の信号を失う |
| 延長のために goroutine を起動する | 処理の実行中に延長する手段が他に無い。利用者に延長を書かせないことが FR-002 である | 処理の前後でしか延長しない案は、長い処理で保持期間が切れる。利用者に「定期的に `Renew` を呼べ」と要求する案は、書き漏らしが元の問題そのものである |
| `ZoneApplier` という型を新設する | 排他を外へ見せないため（消費済みの排他を持ち続けられないようにする） | `Mutex` を引数に取る自由関数は `utils` の既存の作法に最も近いが、`Apply` の後に利用者が解放を試みる余地が残る。本機能はその誤用を構造的に防ぐことを目的としている |
