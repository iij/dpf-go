# 調査と決定: 排他を保持したままの実行と、ゾーン全体の一括置き換え

**機能**: [spec.md](./spec.md) | **計画**: [plan.md](./plan.md) | **日付**: 2026-09-18

仕様に `[要明確化]` は無い。本ファイルは、仕様が実装に委ねた選択について、決定・根拠・
採らなかった案を記録する。D1 は実 API で確認した事実、D2 以降は設計の決定である。

## D1: 一括置き換えは排他を解く（実測）

**決定**: ゾーン全体の一括置き換えは、排他を解く操作として扱う。反映の前に自動延長を止め、
反映の後は「残っていた場合に限り解放する」。

**根拠**: 2026-09-18 に `internal/integration` の `TestLockFlow_AtomicChanges` で実測した
（対象ゾーン `sub.sub.dns-tool-test.jp.`）。

| 段 | SOA の ID | state | ロックのラベル | 未反映件数 |
|---|---|---|---|---|
| ロック前 | `rzxbovrgki2lnd` | 0 (反映済み) | なし | 0 |
| ロック後 | `rzxbovrgki2lnd` | 3 (更新予定) | あり | 1 |
| 一括置き換えの後 | **`rbyi35uxodn42a`** | 0 (反映済み) | **なし** | 0 |

**排他のラベルは、一括置き換えが保存できる対象ではない。** 理由は次のとおりである。

1. 排他は SOA のラベルを書くことで成立するが、その書き込みは**未反映の編集としてだけ**
   存在する（state=3）。反映済みの SOA にはラベルが付いていない。
2. 公開されているレコードの一覧は反映済みの姿を返すため、排他のラベルは含まれない。実測でも
   SOA は state=5（更新前の状態）として返っていた。
3. 一括置き換えは未反映の編集を引き継がない（実行後の未反映件数が 0 になっている）。

したがって、SOA を取り込むか否かのフラグをどちらにしても、未反映の編集が復活することはない。
このフラグは「リクエストに入れた SOA を取り込むか」を決めるだけである。SOA レコードの ID が
変わったことは結果の観察であり、原因ではない。

同じテストで次も確認した。

- 一括置き換えの直後、別の保持者が排他を取得できた（排他が実際に失われている）
- 解放を試みると「保持者でない」エラーになった
- 実行後の未反映件数は 0 件であった（排他による未反映の編集 1 件が残らない）
- 公開されているレコードの一覧は、編集中の SOA を **state=5（更新前の状態）** として返した

**同じ実測で、1 レコードずつ反映する流れは安全であることも確認した**
（`TestLockFlow_ZoneChanges`）。編集中レコードのゾーン反映では SOA の ID が変わらず
（`rbyi35uxodn42a` のまま）、ロックのラベルは反映後も残り、続けて解放できた。

**採らなかった案**:

- **フラグを「取り込まない」にすれば排他が保たれる、という前提に立つ設計。** 実測で否定
  された。この前提で書いた godoc は本機能の作業で訂正する。
- **編集中の SOA（ラベル付き）を自分で指定し、フラグを「取り込む」にして排他を保つ設計。**
  理屈の上では成立する。レコードの一覧を取得する API は編集中の SOA を state=3 として返す
  ため、そのラベルごとリクエストへ入れて「取り込む」を指定すれば、ラベルは反映されて残る。
  採らない理由は、**SOA の内容（シリアルを含む rdata）を利用者側が上書きすることになる**
  ためである。シリアルは DPF が管理する値であり、取得した時点の値を送り返すことが安全か
  どうかは分からない。排他を保つために、ゾーンの根幹にあたるレコードの内容へ手を出す取引は
  割に合わない。排他は反映によって解かれるものとして扱う方が、影響範囲が小さい。

## D1b: 反映済みのラベルは残る

**決定**: 利用者が付けて反映したラベルは、一括置き換えの後も残るものとして扱う。書き戻しの
仕組みは設けない。

**根拠**: 反映済みのラベルは残る（利用者による確認）。これは D1 の整理と整合する。
SOA を取り込むか否かのフラグを「取り込まない」にした場合、既存の（反映済みの）SOA が
そのまま維持されるため、そこに付いていたラベルも維持される。失われるのは**未反映の編集
として書かれたラベル**、すなわち排他のものだけである。

006 は SOA のラベルのうち 2 つを排他が使い、残る 8 つは利用者が使えると定めた
（006 FR-014）。その 8 つは本機能の操作で失われない。

**SOA 以外のレコードのラベルについては事情が異なる。** これらはリクエストに含めたから
残るのであって、一括置き換えが保存してくれるわけではない。リクエストから落とせば消える。
この違いが D9b の決定につながる。

**確認の位置づけ**: 2026-09-24 の統合テストで実測した。一括置き換えの後、SOA レコードの
ID は変わった（`rrqwl23avu5ipc` → `rp8k2it0rub3oc`）が、**反映済みのラベルはそのまま
引き継がれていた**（`owner.lock.dpf-go` と `deadline.lock.dpf-go` が、一括置き換えの前の
反映済みの値のまま残っていた）。ID が変わってもラベルが失われないことが確かめられた。

## D2: ゾーン全体の一括置き換えは専用の型として提供する

**決定**: `ZoneApplier`（仮）という型を新設し、その `Apply` メソッドとして提供する。
排他を表す `Mutex` は内部に持ち、公開しない。

```go
ap := utils.NewZoneApplier(client.RecordsAPI, client.ZonesAPI, client.JobsAPI, zoneID,
    utils.WithTTL(30*time.Minute))
err := ap.Apply(ctx, edit, utils.WithApplyDescription("台帳と同期"))
```

**根拠**: 排他を外へ見せると、`Apply` の後に利用者が解放を試みて「保持者でない」エラーを
受け取る余地が残る。本仕様が塞ごうとしている落とし穴そのものであり、**文書で注意を促すより
構造的に踏めなくする**方が確実である（同じ判断を仕様の FR-015〜FR-017 でも採っている）。

排他を外に出さないことによる損失は無い。排他は再入できないため（006 FR-017）、同じ
`Mutex` を `Do` と `Apply` で同時に使うことはそもそもできない。共有しても使い道が無い。

排他の設定（保持者・保持期間・延長の間隔・取得の待機）は `NewZoneApplier` が受け取った
Option をそのまま内部の `Mutex` へ渡す。オプションの二重定義は生じない。反映のコメントは
`Apply` 固有であるため別の Option 型とし、可変長引数の衝突を避ける。

**採らなかった案**:

- **`Mutex` を引数に取る自由関数** `ApplyZoneAtomic(ctx, mu, cz, cj, edit, opts...)`:
  `utils` の既存の作法（部分インターフェースを受け取る自由関数）には最も近い。しかし
  呼び出し側が消費済みの `Mutex` を持ち続けるため、上記の誤用が残る。
- **`Mutex` のメソッド** `mu.ApplyZoneAtomic(ctx, cz, cj, edit, opts...)`: 同じ誤用が残る。
- **`*dpf.APIClient` を受け取る**: テスト時の差し替えができず、憲章 原則 II のテスト方針
  （ネットワーク不要の単体テスト）と両立しない。
- **`utils.Client` のメソッド**: 生の `*dpf.APIClient` を使う利用者が使えなくなる。

## D3: 汎用の操作は `Mutex.Do` とする

**決定**: 排他を保持したまま処理を実行する操作は、`Mutex` のメソッド `Do` とする。

```go
func (t *Mutex) Do(ctx context.Context, fn func(ctx context.Context) error) error
```

**根拠**: `Mutex` のメソッドであるため「排他を保持して実行する」ことが文脈から明らかで、
標準ライブラリの `sync.Once.Do` と同じ読み方になる。`Mutex` がゾーン ID とレコード API を
持っているため、引数は処理そのものだけで足りる。

利用者の記述にあった `LockedProcess` は採らない。`Process` が何を指すか（処理か、OS の
プロセスか）が曖昧であり、`Mutex` のメソッドとしては `Locked` が冗長になる。

**採らなかった案**: `Locked` / `Run` / `Hold`（いずれも意味は通るが `Do` より長く、
標準的な語感から遠い）。自由関数 `WithZoneLock(ctx, mu, fn)`（`Mutex` を渡す冗長さが残る）。

## D4: 処理へ渡す context は、排他を失ったときに打ち切る

**決定**: `Do` は呼び出し側の context から派生した context を処理へ渡し、延長によって
「保持者でない」と判明した時点でそれを打ち切る。

**根拠**: 保護が切れたことを処理が知らないまま走り続ける状態が最も危険である。排他は
「これから編集する」ことの宣言であり、失った時点で編集を止められなければ意味がない。
context は Go における打ち切りの標準的な伝達手段であり、利用者が新しい約束を学ぶ必要がない。

打ち切りは通知であって強制的な中断ではない。処理が context を無視すれば走り続ける。
`Do` は処理の終了を待つ。この限界を godoc に明記する（FR-024）。

**採らなかった案**: 処理へ「排他を失った」ことを伝える専用のチャネルや戻り値を渡す
（context で足りるものを増やす）。処理を goroutine で動かして置き去りにする
（ライブラリが利用者の処理を放置することになり、後始末の責任が曖昧になる）。

## D5: 延長の失敗は理由で分ける

**決定**: 延長が「保持者でない」を返した場合はただちに処理の context を打ち切り、
その旨のエラーを記録する。それ以外の失敗は次の周期で再試行し、処理を止めない。

**根拠**: 通信の一時的な失敗で編集作業を落とすのは割に合わない。一方、他者に奪われた場合は
ただちに止めなければならない。延長の間隔を保持期間より十分短く取れば、一時的な失敗は次の
周期で回復し、本当に失効した場合は他者に奪われて「保持者でない」となるため、単純な規則でも
最終的に正しい側へ収束する。

残る窓は「延長が失敗し続けているが、まだ誰にも奪われていない」区間である。この間、排他は
実際には失効しているのに処理は走り続ける。窓の長さは延長の間隔に依存する。この限界を
godoc に明記する（FR-024）。

**採らなかった案**: すべての失敗でただちに中止する（一時的な失敗に弱い）。最後に成功した
延長の期限を覚えておき、期限が近づいたら中止する（窓を塞げるが、時計のずれに依存する
判定が増える。本ライブラリは保持期間 15 分に対して延長 5 分であり、3 回連続の失敗が
必要になるため、まずは単純な規則で始める）。

## D6: 延長の間隔の既定値は保持期間の 1/3

**決定**: 既定の延長の間隔は保持期間の 1/3 とする（既定の保持期間 15 分では 5 分）。
`WithRenewInterval` で変更できる。

**根拠**: 保持期間が切れるまでに 3 回の機会があり、2 回連続で失敗しても間に合う。固定値に
しないのは、保持期間を変えた利用者に対して比が崩れるためである（たとえば保持期間を 1 分に
した利用者にとって、固定 5 分の延長は一度も走らない）。

**採らなかった案**: 固定値（保持期間との整合が崩れる）。保持期間の 1/2（機会が 2 回に減る）。
保持期間の 1/10（API 呼び出しが増える。15 分なら 90 秒ごとで、得るものが無い）。

## D7: 「排他が解かれる操作」は非公開の内部経路で扱う

**決定**: `Do` の内部に、保持中の排他を表す非公開の値を置き、一括置き換えの実装だけが
「この先で排他が解かれる」ことを通知できるようにする。公開 API には現れない。

```go
// 非公開
func (t *Mutex) doHold(ctx context.Context, fn func(context.Context, *hold) error) error
func (h *hold) consume()   // 自動延長を止め、終了時の無条件の解放を行わないようにする

// 公開
func (t *Mutex) Do(ctx context.Context, fn func(context.Context) error) error
```

**根拠**: 一括置き換えが排他を解くのは一括置き換えの側の事情である。これを公開 API に
持ち出すと、`Do` を使うすべての利用者が「排他が解かれる場合の扱い」を表す引数
（たとえば 2 引数のコールバック）を受け取ることになる。仕様 FR-017 がこれを禁じている。

実装は同じ `utils` パッケージ内にあるため、非公開の経路で足りる。

`consume` を通知する位置は「編集が終わり、一括置き換えを呼ぶ直前」である。これより早いと
編集中の延長が止まり、遅いと反映中に延長が走って、作り直される SOA を掴もうとする。

**採らなかった案**: 公開の `Hold` 型を `Do` のコールバックへ渡す（FR-017 に反する）。
`Do` が終了時の「保持者でない」を常に無視する（本当に奪われた場合の信号を失う）。
一括置き換えだけ `Do` を使わず独自に実装する（延長と後始末の実装が 2 つになる）。

## D8: 終了時の解放は `Unlock` の性質をそのまま使う

**決定**: 終了時の後始末は `Unlock` を呼ぶ。`Unlock` は保持者が自分でない場合に
`ErrNotLockHolder` を返すため、「自分が保持者である場合に限り解放する」（FR-007）は
これで満たされる。`consume` された場合は `ErrNotLockHolder` を成功として扱う。

**根拠**: 006 の `Unlock` は既に保持者の確認を行う。判定のための追加の読み取りは要らない。
`consume` された場合の「残っていた場合に限り解放する」（FR-021）も、`Unlock` を呼んで
`ErrNotLockHolder` を無視するだけで実現できる。API 呼び出しは 1 回で足りる。

延長が既に「奪われた」を報告している場合は、終了時の `ErrNotLockHolder` を重ねて報告
しない。報告していない場合は、黙って失われていたことを意味するため呼び出し側へ返す。

**採らなかった案**: 解放の前に保持者を読んで判定する（`Unlock` が同じことを行うため
呼び出しが 1 回増えるだけ）。

## D9: 編集の結果に SOA と Zone Apex の NS が無ければ補う

**決定**: 編集の結果に SOA レコードまたは Zone Apex の NS レコードが含まれていない場合は、
取得した一覧のものを補ってリクエストへ含める。

**根拠**: 取り込むか否かのフラグは常に「取り込まない」であるため、含めても内容に影響しない。
一方、DPF-API のエラーには `soa_not_found` と `apex_ns_not_found` がある。フラグが
「取り込まない」のときにこれらが必須かどうかは実測していない。補っておけば、どちらの仕様で
あっても失敗しない。利用者が SOA を意識せずに編集関数を書けることは仕様の狙い
（FR-014）でもある。

**採らなかった案**: 編集の結果をそのまま送る（必須だった場合に失敗する。利用者に
「SOA はそのまま返してください」と要求することになる）。SOA と Zone Apex の NS を編集関数へ
渡さない（利用者がゾーンの全体像を見られなくなる。TTL の確認などで必要になりうる）。

なお D9b により、編集関数は受け取った一覧をそのまま返せば SOA と Zone Apex の NS も保たれる。
補完が働くのは、利用者が明示的にこれらを取り除いた場合だけである。

## D9b: 編集関数の入出力は同じ型にする

**決定**: 編集関数は、反映したいレコードの一覧と同じ型を受け取り、同じ型を返す。
公開されているレコードから一覧への変換は `ZoneApplier` が行う。

```text
(打ち切りを伝えられる引数, 反映したいレコードの一覧) → (反映したいレコードの一覧, エラー)
```

**根拠**: 公開されているレコードの型と、一括置き換えのリクエストに入れる型は別である。
変換を利用者に書かせると、**ラベルのコピーを書き忘れた瞬間に利用者のラベルが消える**
（D1b のとおり、SOA 以外のレコードのラベルはリクエストに含めたから残っているだけである）。
TTL やコメントについても同じことが起こる。これは本仕様が塞ごうとしている「気づけない事故」
と同じ性質を持つ。

入出力を同じ型にすれば、編集しない項目はそのまま返すだけでよく、落とすものが構造的に
無くなる。利用者が書くのは「変えたいところだけ」になる。

失われる情報は、公開されているレコードのうちレコード ID・状態・編集者である。いずれも
リクエストには入れられない項目であり、ゾーン全体を置き換える判断に必要ない。排他を
保持している間は他者が編集できないため、状態はすべて「反映済み」で一様である。

**採らなかった案**:

- **公開されているレコードの型で受け取り、リクエストの型で返す**（当初案）。ゾーンの全体像を
  そのまま見せられるが、変換の負担とラベル落ちの危険を利用者へ渡すことになる。
- **変換用の補助関数を公開し、変換は利用者に任せる。** 補助関数を使うかどうかが利用者に
  委ねられるため、落とし穴は残る。踏めない形にする方針に反する。

## D10: `dpf.ZonesApi` の拡張と `dpf.JobsApi` の新設

**決定**: `interfaces.go` の `ZonesApi` に `PatchZoneAtomicChanges` を追加し、
`JobsApi` を新設する。

```go
type JobsApi interface {
	SyncWaitContext(ctx context.Context, async *AsyncResponse, resp *http.Response, err error) (*GetJobs, *http.Response, error)
}
```

**根拠**: 一括置き換えは非同期であり、反映の完了を待ってから復帰する必要がある（FR-019）。
006 では反映の確認をレコードのポーリングで代替したが（006 D6）、ここでは「一括置き換えの
JOB が完了したか」を知る必要があり、レコードの内容からは判定できない。`SyncWaitContext` が
その唯一の手段である。

`ZonesApi` へのメソッド追加は、このインターフェースを自分で実装している利用者にとって
破壊的変更である。`*dpf.ZonesAPIService` は追加後も満たすため、`client.ZonesAPI` を
渡している利用者への影響は無い。006 で `RecordsApi` を広げたのと同じ種類の変更である。

**採らなかった案**: `*dpf.APIClient` を受け取る（D2 のとおりテストで差し替えられない）。
反映の完了をレコードのポーリングで判定する（何を見れば完了と言えるかが決まらない。
SOA の ID の変化は実装依存の観察であり、契約にできない）。

## D11: 空の結果には専用の番兵エラーを設ける

**決定**: 編集の結果が空の場合は `ErrNoRecords`（仮）を返す。API を呼ばない。

**根拠**: 一括置き換えはレコードを 1 件以上必要とする。API に投げれば 400 が返るが、
呼び出し側が「編集関数が空を返した」ことを判別できる方が対処しやすい。空のゾーンを作る
事故を防ぐ意図も込める。番兵にするのは、利用者が `errors.Is` で分岐できるようにするため
である（既存の `ErrStillLock` などと同じ作法）。

**採らなかった案**: API のエラーをそのまま返す（原因が「自分の編集関数が空を返した」こと
だと分かりにくい）。空の結果を「何も変更しない」と解釈して成功を返す（利用者の意図が
「全削除」なのか「変更なし」なのか判別できない。黙って何もしないのは危険）。
