# 調査: ゾーン単位の排他のラベルをゾーンへ移す

**機能**: [spec.md](./spec.md) | **計画**: [plan.md](./plan.md) | **日付**: 2026-09-29

仕様の前提と未実測の項目を、実装の判断まで落とした記録である。決定・根拠・採らなかった案の
形で残す。

## D1: 既定の実装を入れ替える。型の名前と位置づけは変えない

**決定**: `utils.Mutex` の名前と役割を保ったまま、排他の状態の置き場だけを SOA レコードの
ラベルからゾーンのラベルへ入れ替える。新しい型を並べない。

**根拠**: 008 の抽象（`Locker`）から見た既定の実装という位置づけは変わらない。名前を変えると
利用者のコードが動かなくなるうえ、`WithLocker` で差し替える利用者に「どちらが既定か」という
新しい判断を与える。仕様の範囲の境界も「既定の実装の内部を入れ替える」と定めている。

**採らなかった案**: 新しい型（`ZoneLabelMutex` など）を足して選べるようにする。2 つの既定が
並ぶことになり、どちらを使うべきかの説明が要る。混在の危険（仕様 FR-013）も 2 倍になる。

## D2: 値は「保持者 + 区切り + 奪ってよい時刻 10 桁」とし、**右端から固定幅で読む**

**決定**: ゾーンのラベル 1 つに次の形式で書く。

```text
<保持者>-<奪ってよい時刻の 10 桁>
例: web01.tokyo-12345-a1b2c3d4-1790319252
```

読み出しは**右端の 11 文字を固定幅として扱う**。末尾 10 文字が奪ってよい時刻、その直前の
1 文字が区切りであることを確かめ、残りを保持者とする。

**根拠**: この読み方なら、**保持者の側に区切り文字が含まれていても曖昧にならない。** 常に
「末尾 11 文字」を切り離すだけであり、左から最初の区切りを探すのではないためである。結果と
して次の 2 つが同時に成り立つ。

1. **保持者の文字に制約を課さなくてよい。** 利用者が `WithOwner` へ与えられる文字列は、
   長さ以外の制約を受けない。**そもそも制約を課すことはできない。既定の保持者
   （`web01-12345-a1b2c3d4`）自身が区切りと同じ `-` を含むためである**
2. **区切りに `-` を使える。** 既定の保持者（ホスト名・PID・乱数）が既に `-` を含んでおり、
   ラベルの値として受け付けられることが実測済みである。DPF-API はラベルの値の文字種を
   `openapi.json` に定めていないため、**未実測の文字を区切りに選ぶと新しい実測項目が増える**

奪ってよい時刻は Unix 秒であり、2286 年まで 10 桁で固定である。10 桁に満たない場合（1970 年
近傍のみ）は 0 で詰める。

**長さ**: 保持者 32 文字 + 区切り 1 文字 + 10 桁 = 最大 43 文字。ラベルの値の上限 63 文字に
収まる（仕様の前提どおり）。

**仕様への影響**: **FR-005c（区切り文字を保持者に含めてはならない）は不要になるだけでなく、
両立しない。** 区切りを `-` とすると、この要件は**既定の保持者そのものを拒否する**
（`web01-12345-a1b2c3d4` は `-` を含む）。**2026-09-29 に利用者の判断でこの案を採り、仕様を
更新した**（FR-005c を欠番として削除。利用シナリオ 3 の受け入れシナリオを「区切り文字を含んで
いても成功する」へ反転。境界的な状況の区切り文字の項を削除。SC-010 の後半を「正しく読み取られ
ない事象が 0 件」へ改めた）。

**採らなかった案**:

- **区切りを置かず、末尾 10 桁をそのまま連結する**（`...a1b2c3d41790319252`）。制約は同じく
  不要になるが、管理画面で人が読むときに保持者と時刻の境目が分からない。**読みやすさは
  今回の設計判断の論点そのものであった**（既定の保持者のレイアウトの議論）
- **左から最初の区切りを探す**。保持者に区切り文字を含められない制約が必要になり、その検証と
  番兵エラーを増やすことになる。得るものが無い
- **区切りに `|` を使う**。読みやすさは上がるが、ラベルの値として受け付けられるかが未実測で
  あり、実測項目を 1 つ増やす。`-` で足りる

## D3: 既定の保持者はホスト名の枠を 15 文字に固定する

**決定**: 既定の保持者は「ホスト名・PID・乱数 8 桁」から作る。**ホスト名に割り当てる枠を
15 文字に固定**し、超える場合は先頭を残して右側を落とす。PID はゼロ詰めしない。

**根拠**: 仕様の明確化のとおり（`## Clarifications`）。枠を固定するのは、**同じホストなら
常に同じホスト名部分になる**ようにするためである。現行の実装は「接尾辞の実長を引いた残りを
ホスト名に与える」形（`utils/lock.go:107`）なので、PID の桁数によってホスト名の残り方が実行
ごとに変わる。診断で目で突き合わせるときに不便である。

**長さの内訳**: ホスト名 15 + `-` + PID 1〜7 + `-` + 乱数 8 = 26〜32 文字。保持者の上限
32 文字に収まる。

**注意**: 現行の実装は乱数の取得に失敗した場合、接尾辞から乱数を落とす（`utils/lock.go:103`）。
その場合の保持者は「ホスト名 + PID」だけになり、**同一ホスト・同一 PID の再実行と区別が
付かない**。この性質は現行のままとし、本機能では変えない。

## D4: 書き込みの確定は読み戻しで確認する。JOB の待ち合わせは使わない

**決定**: ゾーンのラベルの更新（`PUT`）は非同期（202 + `jobs_url`）であるため、書き込みの
直後に読み戻し、自分が書いた値が見えるまで待つ。既存の `verify`（`utils/lock.go:494`）と
同じ作法で、上限は既存の `DefaultVerifyTimeout`（10 秒）を流用する。**JOB の待ち合わせ
（`JobsApi`）は使わない。**

**根拠**: 読み戻しは「非同期の処理が終わったか」だけでなく「**同時に書き込んだ他者に負けて
いないか**」も同時に確かめる。JOB の完了だけを見ると、自分の書き込みが他者の書き込みに
上書きされた場合を見逃す。現行の実装が読み戻しを選んでいる理由もこれである。加えて、
`JobsApi` を排他へ持ち込むとコンストラクタの引数が 1 つ増える。

**採らなかった案**: `JobsApi` で JOB の完了を待つ（上記の 2 点）。`PUT` の応答だけで成功と
みなす（非同期であるため、直後の読み取りで古い値が見える）。

**実測（2026-09-29）**: 非同期であることを実 API で観測した。`Unlock` は確定を確認しない
ため、**復帰した直後にラベルを読むと解放前の値が返る**ことがある。統合テストの 3 箇所で
この競合が出た（1 箇所は失敗、2 箇所はたまたま通っていた）。解放を見届ける必要がある箇所は
読み戻しで待つように直し、この性質を `Unlock` の godoc にも明記した。**利用者に見える性質
である。**

## D5: ゾーン名は SOA レコードから得て、`Mutex` に保持する

**決定**: 一時レコード追加ロックのための専用レコードの名前を作るために、ゾーン名が必要である
（006 D4）。ゾーン名は従来どおり SOA レコードの `name` から得る。**排他の判定で SOA を読む
必要は無くなるため、ゾーン名を保持している場合は SOA を読まない経路にする。**

**根拠**: 排他の判定にはもう SOA を読まない。読む理由はゾーン名だけである。**ゾーン名の保持は
現行の実装がすでに行っている**（`utils/lock.go:690` の `if t.zoneName == ""`）。現行はそれとは
別に排他の判定で SOA を読むため、保持していても読み取りが発生する。本機能では判定の読み取りが
ゾーンのラベルへ移るので、**2 回目以降は SOA をまったく読まなくなり、呼び出し回数は現行と同じ
8 回に収まる**（下の表）。

ゾーン名の正規化は現行どおり miekg/dns で行う（`dns.Fqdn`。憲章 原則 IV）。

**呼び出し回数**:

| 段 | 現行（SOA のラベル） | 本機能（ゾーンのラベル、初回） | 本機能（2 回目以降） |
|---|---|---|---|
| ゾーン名の取得 | （事前判定と兼用） | GET レコード（SOA） | — （保持済み） |
| 事前判定 | GET レコード（SOA） | GET ゾーンのラベル | GET ゾーンのラベル |
| 専用レコードの追加 | POST | POST | POST |
| 確立の確認 | GET レコード | GET レコード | GET レコード |
| 保護下での再読み取り | GET レコード（SOA） | GET ゾーンのラベル | GET ゾーンのラベル |
| 書き込み | PATCH レコード | PUT ゾーンのラベル | PUT ゾーンのラベル |
| 確定の確認 | GET レコード（SOA） | GET ゾーンのラベル | GET ゾーンのラベル |
| 専用レコードの取り消し | DELETE changes | DELETE changes | DELETE changes |
| 消えたことの確認 | GET レコード | GET レコード | GET レコード |
| **合計** | **8** | **9** | **8** |

**採らなかった案**: ゾーンの一覧からゾーン名を引く（`GetZoneList`）。呼び出し回数は同じで、
名前で絞り込む手間が増える。専用レコードの名前を zoneID から作る（レコードの名前はゾーン内の
FQDN でなければならないため成立しない）。

## D6: `interfaces.go` の `ZonesApi` へ 2 メソッドを追加する

**決定**: `dpf.ZonesApi` に `GetZoneLabels` と `PutZoneLabels` を追加する。

**根拠**: 排他がゾーンのラベルを読み書きするため、テストで差し替えられる部分インターフェースが
必要である。`*dpf.ZonesAPIService` は追加後も満たすため、`client.ZonesAPI` を渡している
利用者への影響は無い。**自分で `ZonesApi` を実装している利用者には破壊的変更**であり、007 が
`PatchZoneAtomicChanges` を追加したのと同じ種類の変更である。

**採らなかった案**: 新しいインターフェース（`ZoneLabelsApi` など）を足す。コンストラクタの
引数が増え、`NewZoneApplier` から渡す値も増える。`ZonesApi` は既に「ゾーンに対する操作」を
表しているため、そこへ足すのが自然である。

## D7: `NewMutex` はゾーン API を受け取る（破壊的変更）

**決定**: `NewMutex(cr dpf.RecordsApi, cz dpf.ZonesApi, zoneID string, opts ...Option)` とする。

**根拠**: ゾーンのラベルを読み書きするために必要である。`NewZoneApplier` は既に `cz` を
受け取っているため（`utils/apply.go:148`）、内部で渡すだけで済む。`RunLocked` と
`ZoneApplier.Apply` の呼び出し方は変わらない（仕様 FR-009）。

**移行**: 既存の呼び出しは引数を 1 つ足す機械的な置き換えで対応できる。

```go
// v0.5.0
mu := utils.NewMutex(client.RecordsAPI, zoneID)
// 以降
mu := utils.NewMutex(client.RecordsAPI, client.ZonesAPI, zoneID)
```

**採らなかった案**: 可変長引数の Option でゾーン API を渡す（必須の依存を任意の形で受け取る
ことになり、渡し忘れが実行時のエラーになる）。

## D8: ラベルのキーは新しく 1 つ設ける。既存の 2 つは専用レコード用に残す

**決定**: ゾーンのラベルのキーとして `ZoneLockLabelKey = "lock.dpf-go"` を公開する。既存の
`LockOwnerLabelKey` / `LockDeadlineLabelKey` は、**一時レコード追加ロックの専用レコードで
引き続き使う**ため残す。

**根拠**: 値を 1 つに詰めるため、キーも 1 つになる。既存の 2 つのキーを流用すると「どちらに
何が入っているか」が対象によって変わり、読み手が混乱する。専用レコードは短命であり、レコードの
ラベルの枠（10 個）を消費する期間も取得の間だけなので、2 キーのままでよい。

**採らなかった案**: 既存の `LockOwnerLabelKey` を流用して値を詰める（キーの名前が「保持者」を
表しているのに時刻も入る）。専用レコードも 1 キーに揃える（本機能の範囲外であり、得るものが
無い）。

## D9: `ErrLabelLimit` は流用し、意味を「ゾーンのラベルの上限」へ改める

**決定**: 番兵の値は `ErrLabelLimit` のまま流用し、godoc とエラーの文言を「ゾーンのラベルの
上限」へ改める。判定は「排他のラベルを足すとゾーンのラベルが 10 個を超えるか」で行う。

**根拠**: 利用者から見た意味（ラベルの枠が足りず、待っても解消しない）は変わらない。番兵の
値を変えると `errors.Is` による既存の分岐が壊れる。**取得を待つ指定があっても待たない**扱いも
現行のまま（`utils/lock.go:437-447`）。

**採らなかった案**: 新しい番兵を設けて `ErrLabelLimit` を非推奨にする（利用者の分岐を 2 つに
増やすだけで、対処は同じ）。

## D10: 保持者の長さの検証は新しい番兵で返す

**決定**: `ErrOwnerTooLong`（仮）を新設する。`WithOwner` で 32 文字を超える保持者を指定された
場合、書き込みを試みずにこれを返す。空文字は既定の保持者へフォールバックし、エラーにしない
（仕様 FR-005e、006 の Option の作法）。

**根拠**: 仕様 FR-005d が「原因を判別できるエラー」を求めている。`ErrLabelLimit` と混ぜると、
利用者は「枠が足りない」と「保持者が長い」を区別できない。対処が異なる（前者はラベルを削る、
後者は保持者を短くする）ため分ける。

**検証の位置**: `Lock` の入口で行う。`NewMutex` / `WithOwner` の時点でエラーを返す道は無い
（Option はエラーを返さない作法である）。

**採らなかった案**: 黙って切り詰める（仕様で明確に否定した。切り詰めると別のインスタンスと
同じ保持者になり、延長と解放の宛先の判別が壊れる）。`ErrLabelLimit` を流用する（原因が
区別できない）。

## D11: 一括置き換えが排他を解くことの申告は、仕組みを残したまま使われなくなる

**決定**: `Mutex` は `consumedByZoneApply`（`utils/locker.go:75-77`）を実装しなくなる。申告の
仕組み自体（非公開インターフェース、`consumesLockOnZoneApply`、`ZoneApplier.Apply` の分岐、
`hold.consume` の特別扱い）は**削除せず残す**。

**根拠**: 仕様の範囲の境界が「008 で定めた排他の抽象そのものの変更は範囲外」と定めている。
申告の仕組みは 008 の設計の一部である。

**この決定の代償**: 申告は非公開メソッドであるため `utils` の外からは実装できない。したがって
**本機能の後、この仕組みを使う実装は 1 つも無くなる**（到達しないコードが残る）。削除は 010
以降の機能として扱うべきである。**この判断は利用者に確認する価値がある**（範囲を守ることと、
到達しないコードを残さないことのどちらを取るか）。

**採らなかった案**: 申告の仕組みごと削除する（仕様の範囲の境界に反する。また 007 の FR-017 が
定めた扱いを覆すため、007 の仕様にも追随が必要になる）。

## D12: 未実測の項目と、実測できなかった場合の扱い

**実測する項目**（統合テストで確認する。仕様 FR-017）:

1. **ゾーンのラベルが、レコードの一括更新とゾーン反映で失われないこと。** 仕様の前提では
   「対象はレコードであり、ゾーンのラベルは別のリソースである」ことから構造的に成立すると
   している。統合テストは念のための確認である
2. 非同期の更新の確定が読み戻しで観測できること（D4）。上限 10 秒で足りるか

**実測の対象から外した項目**: 「ゾーンが公開前の状態でもラベルを読み書きできること」。
**公開状態が決めるのは DNS への反映の有無であり、ゾーンのラベルは管理属性であって権威
サーバのデータではない**（利用者の判断、2026-09-29）。統合テストには公開前のゾーンがあれば
確かめる形で残してあるが、無ければスキップしてよい。仮にこの判断が外れていた場合でも、
公開前のゾーンでの取得は DPF-API のエラーとして表面化するため、黙って壊れることはない。

**旧版が SOA に残したラベル**: 掃除しない（仕様の範囲の境界）。統合テストの後始末では、
テストが作った SOA のラベルを取り除く既存の手順（`clearSOALock`）をそのまま使う。
