# 実装計画: ゾーン単位の排他のラベルをゾーンへ移す

**ブランチ**: `009-zone-label-lock` | **日付**: 2026-09-29 | **仕様**: [spec.md](./spec.md)

**入力**: 次の機能仕様 `/specs/009-zone-label-lock/spec.md`

## 概要

排他の状態（保持者と奪ってよい時刻）は SOA レコードのラベルに書かれている。レコードのラベルの
更新は「未反映の編集」になるため、**排他を取得するとゾーンが汚れ、解放しても汚れが残る。**
008 の契約表はこの状態の実害を「DNSSEC の有効化などが行えない」と記録している。加えて一括
置き換えが排他を解くため、007 はそのための扱いに相当の複雑さを払っている。

**そしてこの置き場を選んだ根拠は既に失われている。** 003 の FR-039 の継承であり、003 が挙げた
理由（編集予定にすれば重ねて編集できない）は 003 自身が「不正確であった」と訂正している。
ゾーンのラベルへ置く案は、001〜008 を通して検討の記録が 1 件も無い。

ゾーンのラベルは**未反映の編集の概念を持たない**。ここへ移す。方針は 5 つある。

1. **既定の実装の内部だけを入れ替える。** 008 の抽象（`Locker`）と `Mutex` の名前・役割は
   変えない。`Lock` / `Renew` / `Unlock` の呼び出し方も変えない
   （[research.md](./research.md) D1）。
2. **値は 1 つのラベルに詰め、右端から固定幅で読む。** `<保持者>-<奪ってよい時刻 10 桁>` と
   し、末尾 11 文字を切り離して解釈する。**この読み方なら保持者に区切り文字が含まれていても
   曖昧にならないため、保持者の文字に制約を課さなくてよい**（同 D2）。
3. **一時レコード追加ロックは 006 のまま使う。** ゾーンのラベルの更新はマップ全体の置き換え
   （`PUT`）であり、読み取りから書き込みまでの危険区間は残る。この区間の保護は 006 の仕組みが
   そのまま担う。**2 者が同時に取得しないことは、この重複の拒否によって機械的に保証され、
   ユーザをまたいで効く**（同 D12、仕様の前提）。
4. **書き込みの確定は読み戻しで確認する。** ゾーンのラベルの更新は非同期である。JOB の
   待ち合わせではなく読み戻しを使うのは、「非同期の処理が終わったか」と「**同時に書き込んだ
   他者に負けていないか**」を同時に確かめられるためである（同 D4）。
5. **保持者は 1〜32 文字とし、超える値は黙って切り詰めない。** 切り詰めると別のインスタンスと
   同じ保持者になり、延長と解放の宛先の判別が壊れる。書き込みを試みずにエラーを返す
   （同 D10、仕様 FR-005d）。

**失うもの**: 保持中に他ユーザや管理画面からの**手作業の編集を止める効果**。これは保持中の
SOA が編集予定であることに由来する。利用者の判断として受容する（仕様の前提、2026-09-25）。
なおこの効果は 006 の時点から実測されていない（006 FR-028 の (3) が宿題のまま）。

## 技術的な前提

**言語 / バージョン**: Go 1.27（`go.mod` の指定に従う）

**主要な依存**: `github.com/miekg/dns`（ゾーン名の正規化。既存の依存）。**新しい依存は追加
しない**

**保存先**: DPF-API のゾーンのラベル（`GET` / `PUT /zones/{ZoneId}/labels`）。ラベルは
最大 10 個、値は 1〜63 文字

**テスト**: `go test`。単体テストは `httptest` の模擬サーバでネットワーク不要。実 API に
触れる確認は `integration` ビルドタグで隔離

**対象環境**: ライブラリ。利用者のプロセスで動く

**プロジェクト種別**: library（`github.com/iij/dpf-go` 本体と `utils` パッケージ）

**性能目標**: 排他の取得 1 回あたりの API 呼び出しを現行（8 回）から増やさない。初回のみ
ゾーン名の取得で 9 回、2 回目以降は 8 回（[research.md](./research.md) D5）

**制約**: 取得・延長・解放はゾーン反映を伴わない。ゾーンに未反映の編集を作らない。権威サーバ
へ公開されるデータに影響しない

**規模 / 範囲**: 1 ゾーンにつき排他は 1 つ。ゾーンのラベルの消費は 1 個

## 複雑さの記録

| 逸脱 | 必要な理由 | より単純な代替案を採らない理由 |
|---|---|---|
| 一括置き換えが排他を解くことの申告の仕組みを、**使われない状態で残す** | 仕様の範囲の境界が「008 で定めた排他の抽象そのものの変更は範囲外」と定めている。申告の仕組み（非公開インターフェース、`consumesLockOnZoneApply`、`hold.consume` の特別扱い）は 008 の設計の一部である | 「仕組みごと削除する」方が単純だが、範囲の境界に反し、007 の FR-017 が定めた扱いも覆すため 007 の仕様にも追随が必要になる。**ただし申告は非公開メソッドであるため `utils` の外からは実装できず、本機能の後はこの仕組みを使う実装が 1 つも無くなる**（到達しないコードが残る）。削除は 010 以降の機能として扱う。この判断は利用者に確認する価値がある（[research.md](./research.md) D11） |

**上記以外の逸脱は無い。**
