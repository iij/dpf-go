# タスク: ゾーン単位の排他のラベルをゾーンへ移す

**入力**: `/specs/009-zone-label-lock/` の設計文書

**前提**: [plan.md](./plan.md)、[spec.md](./spec.md)、[research.md](./research.md)、
[data-model.md](./data-model.md)、[contracts/](./contracts/)、[quickstart.md](./quickstart.md)

**テスト**: **含める。** 憲章 原則 II（テストを伴う実装。NON-NEGOTIABLE）が手書きコードへの
単体テストを必須としており、仕様も FR-016（単体テスト。ネットワーク不要）と FR-017（実 API で
の確認）で求めている。

**構成**: タスクは利用シナリオごとにまとめる。ただし本機能では**利用シナリオ 2 と 3 は
利用シナリオ 1 の実装から自動的に得られる結果**であり、単独で開発するものではない（仕様の
「この優先度の理由」）。そのためフェーズ 4 と 5 は、**期待値の反転と確認**が中心になる。

## 書式: `[ID] [P?] [シナリオ] 説明`

- **[P]**: 並行して進められる（別のファイルで、未完了のタスクに依存しない）
- **[シナリオ]**: どの利用シナリオに属するか（US1 / US2 / US3）
- 説明にはファイルのパスを含める

## パスの規約

本リポジトリは単一のライブラリである。手書きコードは `utils/` と `interfaces.go` に集まり、
単体テストは同じディレクトリの `*_test.go`、実 API に触れる確認は `internal/integration/` に
置く。**生成物（`api_*.go` / `model_*.go` など）は直接編集しない**（憲章 原則 I）。

## 依存関係と実行順序

### フェーズ間の依存

```text
フェーズ 1 (準備)
    ↓
フェーズ 2 (土台) ← ここまで完了しないと利用シナリオに着手できない
    ↓
フェーズ 3 (US1・MVP)
    ↓
フェーズ 4 (US2) ── フェーズ 3 の実装の結果を確認する
    ↓
フェーズ 5 (US3) ── 同じく確認
    ↓
フェーズ 6 (仕上げ)
```

### 利用シナリオ間の依存

**US2 と US3 は US1 に依存する。** 3 つは別々の機能ではなく、**同じ 1 つの変更（排他の状態の
置き場を移す）から出る 3 つの結果**である。US1 を実装すると US2 と US3 の性質は同時に満た
される。したがって US2・US3 のフェーズは「申告を外す」「期待値を反転する」「確認を足す」に
なる。

**この構成が仕様の優先度と矛盾しない理由**: 仕様の「この優先度の理由」が、US2 と US3 を
「US1 の置き場の変更から自動的に得られる結果」と明記している。独立して**開発**できることは
求めていない。独立して**検証**できることは満たしている（それぞれの関門を参照）。

### 各利用シナリオの内部

- テスト（T012〜T019 / T026〜T029 / T032〜T034）は実装より先に書いてよい。**先に書けば
  期待値の反転が意図どおりであることを、落ちるテストで確かめられる**
- US1 の実装は T020（取得）→ T021（延長）→ T022（解放）の順に進める。T023（確定の確認）は
  T020 の中で使うため先に用意してもよい

## 実装の進め方

### MVP の範囲

という本機能の動機が満たされる。US2 と US3 の性質も実際には同時に満たされるが、**その確認

- **T034 の後**: すべてのテストが通る。文書は追随していない

## 実行結果 (2026-09-29)

### 単体テストと品質ゲート

- `go test ./utils/... -race -count=1`: 通過
- `make check`: 7 ゲートすべて通過（`go.mod` に差分なし、生成物の編集なし）

### 実装で分かったこと

- **ホスト名に `-` が含まれる環境で既定の保持者のテストが落ちた。** 左から分解していた
  ためである。テスト側も**右から切り出す**形に直した。値の読み出しを右端から固定幅で行う
  という設計判断（[research.md](./research.md) D2）が、既定の保持者そのものにも必要だった
  ことの裏付けである
- **模擬サーバのラベル読み取りヘルパが二重ロックを起こした。** ハンドラと並行して読む
  テストは `s.mu` を保持したまま呼ぶため、ヘルパの側でロックを取ると詰まる。既存の
  `s.find` と同じくロックを取らない作法へ揃えた
- **`patchCount` / `waitPatchAbove` が未使用になり、`make check-lint` が検出した。** 延長が
  レコードの更新からゾーンのラベルの更新へ移ったためである。削除した
- **`discardSOAChanges`（統合テスト）が不要になった。** 排他が SOA の未反映の編集を作らなく
  なったため、後始末は `clearZoneLock`（ゾーンのラベルから排他を取り除く。**ゾーン反映は
  不要**）で足りる。削除し、`internal/integration/README.md` の記述も直した

### 期待値を反転したもの

### 実 API での確認 1 回目 (2026-09-29、利用者が実行)

**本命の前提が成立した。** レコードの一括更新とゾーン反映（`atomic_changes`）の後も排他が
保持されていた。SOA は作り直されている（`r2s1vb6qp4nw3t` → `r8qlny0au97sd6`）にもかかわらず
ゾーンのラベルは残り、別 owner の取得も拒否された。利用シナリオ 2 と FR-008 は成立する。

あわせて次が確認できた。

| 確認 | 証拠 |
|---|---|
| 排他がゾーンに未反映の編集を作らない | `[ロック後] 未反映件数=0`（v0.5.0 までは 1 件） |
| 排他が SOA を触らない | `[ロック後] SOA: state=0(反映済み) labels=map[]` |
| 利用者のラベルが失われない | `applier.test.dpf-go=keep-...` が Apply の後も残存 |
| 権威サーバへ影響しない | 公開されているレコードが排他の前後で 3 件のまま |
| 専用レコードが公開されない | `TestLockRecordPremises` 通過 |
| 延長が効く | 奪ってよい時刻が `1790659716` → `1790659783`（+67 秒、保持期間 60 秒） |

**3 件の失敗はいずれもテストの期待値の取り残しであった。** 実装の欠陥ではない。

1. **解放の確定を待っていなかった**（`TestLockFlow_AtomicChangesKeepsLock`）。ゾーンのラベルの
   更新は非同期であり、`Unlock` は確定を確認しない（[contracts/zone-label.md](./contracts/zone-label.md)
   第 4 節）。復帰の直後に読むと解放前の値が返る。**同じ競合を `TestZoneApplierApply` と
   `TestZoneApplierSkipApply` も抱えていた**（ログには「保持=true」と出ているのに、後続の
   読み取りがたまたま新しい値を得て通っていた）。3 箇所とも読み戻しで待つように直した
2. **未反映件数の期待値が 2 件のままだった**（`TestLockFlow_ZoneChanges`・
   `TestZoneMutexDoPerRecord`）。排他が SOA の未反映の編集を作らなくなったため 1 件が正しい

**この性質は利用者に見えるため、`Unlock` の godoc に明記した**（[research.md](./research.md)
D4 の実測）。

### 公開前のゾーンについて (2026-09-29)

T043 はスキップされたが、**T049 は不要と判断した。** 公開状態が決めるのは DNS への反映の

するため、黙って壊れることはない。統合テストは公開前のゾーンがあれば確かめる形で残す。
