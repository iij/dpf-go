### 判断の記録

- **「実装の詳細を含んでいない」について**: 本仕様は `KUBECONFIG`、
  `/var/run/secrets/kubernetes.io/serviceaccount/token`、
  `/var/run/secrets/kubernetes.io/serviceaccount/namespace`、`~/.kube/config`、
  `dpf-token`、`token` という具体的な字面を含む。これらは実装側の選択ではなく、
  利用者が要件として指定した値そのものである。字面を伏せると要件が一義でなくなるため、
  そのまま記載した。言語・SDK・型・関数名は記載していない。004 も既定のキー名 `token` を
  同じ扱いで記載している。
- **「技術者以外の関係者にも読める」について**: 本ライブラリの利用者は Kubernetes 上で
  動作する Go プログラムの開発者である。Secret・名前空間・資格情報は利用者の運用語彙で
  あり、これを避けると要件が表せない。004 と同じ読者を想定した。

**反復 1 で利用者へ確認した事項** (2026-09-18):

- 名前空間を指定しなかった場合の既定値について、初稿は「接続情報が示す既定の名前空間」と

  (FR-014)。`default` を補う案は採らない。合わせて成功基準に SC-009 を追加し、
  推測によって補われる名前空間が 0 件であることを条件とした。

### 検証記録 (改訂, 2026-09-18 — 計画フェーズ中の要件変更)

**変更の契機**: 計画フェーズの調査 (research.md D3) で、初稿の FR-020 が定めた探索順序
(`KUBECONFIG` → クラスタ内の資格情報 → `~/.kube/config`) が、Kubernetes の標準的な
クライアントの順序と食い違うことが判明した。標準は `KUBECONFIG` と `~/.kube/config` を
1 つの候補に畳み込み、その後にクラスタ内の資格情報へ落ちる。両者の間にクラスタ内の
資格情報が入る形は標準に存在しない。

**利用者の判断**: 「探索順序は client-go と合わせる」。初稿の列挙は「この 3 つを見る」
ことを示したもので、順序の指定ではないと解した。

**仕様への反映**:

| 変更 | 内容 |
|---|---|
| FR-020 | 候補を 3 つから 2 つへ。設定ファイル (`KUBECONFIG` が指すもの、無ければ `~/.kube/config`) を先に見て、得られなければクラスタ内の資格情報を用いる。独自の順序を定めない |
| FR-022 | 対象を「設定ファイルが存在するが解釈に失敗した場合」へ限定 |
| FR-023 | **新設**。設定ファイルが存在しない場合・使える接続情報が得られない場合は、候補が無いものとして次へ進む。失敗として扱わない |
| 旧 FR-023〜FR-035 | FR-024〜FR-036 へ繰り下げ |
| SC-008 | **新設**。8 通りの組み合わせすべてで、選ばれる接続先が標準的なクライアントの選択と一致する |
| 旧 SC-008〜SC-017 | SC-009〜SC-018 へ繰り下げ |
| 利用シナリオ 2 | 受け入れシナリオを 12 件から 14 件へ。順序、存在しないファイルの扱い、名前空間の非回り込みを追加 |
| 境界的な状況 | 順序の項を書き換え、存在しない設定ファイルの扱いと、名前空間を標準に合わせない理由を追加 |

**名前空間については標準に合わせないことを明記した**。標準的なクライアントは設定
ファイルの名前空間が空のときクラスタ内の名前空間へ回り込み、最後は `default` を補う。
本機能は選ばれた認証情報に紐づく値のみを用い、決まらなければエラーとする (FR-013・FR-014)。
接続先を取り違えても認証が失敗して気づけるが、名前空間を取り違えると別の Secret を
読んで成功しうるため、誤りの重さが違う。この判断は受け入れシナリオ 2-12 と
境界的な状況に記載した。

**再検証**: 全 16 項目が通過。要明確化の印は 0 件。機能要件 36 件すべてに対応する
受け入れシナリオがある (新設の FR-023 は利用シナリオ 2 の受け入れ 7、
FR-022 は同 6 が対応)。
