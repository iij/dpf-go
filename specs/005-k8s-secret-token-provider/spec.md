# 機能仕様: Kubernetes Secret からのトークン取得

**機能ブランチ**: `005-k8s-secret-token-provider`

**作成日**: 2026-09-18

**状態**: ドラフト

**憲章**: v2.0.1 の原則 II、原則 III、原則 V (本体への依存追加の禁止と optional な機能の隔離)、および「ライセンス」ブロックに整合

**入力**: 利用者による記述: "token取得方法に、k8s secretを追加します。namespace,resource_nameを指定し、data.tokenの中身をtokenとして扱います。namespaceが指定されてない場合は、認証に使用した情報のデフォルト値、resource_nameが指定されていない場合はdpf-tokenをデフォルトとして扱います。認証情報は、何も指定がない場合は、環境変数KUBECONFIG,/var/run/secrets/kubernetes.io/serviceaccount/token,~/.kube/configのどれかを選択し、何もない場合はエラーとします。"

**関連**: 004-misc-token-providers (シークレット管理サービスからのトークン取得)。本機能は 5 つ目の取得元として Kubernetes の Secret を追加する

## 利用シナリオと検証 *(必須)*

### 利用シナリオ 1 - Kubernetes の Secret に置いたトークンで API を呼べる (優先度: P1)

利用者は DPF-API のアクセストークンを Kubernetes の Secret に置いている。利用者は Kubernetes 向けの追加モジュールを取り込み、Secret の所属する名前空間と Secret の名前を指定して、トークンを取得する処理を得る。それをそのまま DPF-API のクライアント生成へ渡すと、API リクエストのたびに Secret からトークンが取得される。Secret を更新すれば、プログラムを再起動せずに反映される。

名前空間と Secret の名前は、多くの利用者にとって指定が不要である。名前空間を指定しなければ、接続に用いた情報が示す既定の名前空間が使われる。Secret の名前を指定しなければ `dpf-token` が使われる。

**この優先度の理由**: 本機能の存在理由そのものである。Kubernetes 上で動くプログラムにとって、Secret はアクセストークンの標準的な置き場である。すでに Secret に置いているトークンを本ライブラリから読めないと、利用者は Secret の内容を環境変数やファイルへ写す手順を自分で用意することになり、平文で残る箇所が増える。

**独立した検証**: Kubernetes の操作を差し替えた状態でトークンの取得処理を作り、期待するトークンが返ることを確認できる。名前空間と Secret の名前を省略したときに、既定値が問い合わせに使われることを確認できる。得られた処理が DPF-API のクライアント生成へそのまま渡せる形であることを確認できる。同じ処理を複数回評価したときに、そのたびに問い合わせが行われることを確認できる。

**受け入れシナリオ**:

1. **前提** Secret の `token` に値が格納されている、**操作** 名前空間と Secret の名前を指定して取得処理を作り、それを評価する、**結果** 格納されている値がトークンとして返る
2. **前提** Secret の値が符号化された形で保持されている、**操作** 取得処理を評価する、**結果** 復号された値がトークンとして返る。符号化された文字列がそのまま返ってはならない
3. **前提** 名前空間を指定していない、**操作** 取得処理を評価する、**結果** 接続に用いた情報が示す既定の名前空間が問い合わせに使われる
4. **前提** Secret の名前を指定していない、**操作** 取得処理を評価する、**結果** `dpf-token` が問い合わせに使われる
5. **前提** 取得処理を得た、**操作** それを DPF-API のクライアント生成へ渡す、**結果** 追加の変換なしに受け付けられる
6. **前提** 取得処理を得た、**操作** 複数回評価する、**結果** そのたびに問い合わせが行われ、更新後の Secret が反映される
7. **前提** 指定した Secret が存在しない、**操作** 取得処理を評価する、**結果** Secret が見つからないことを判別できるエラーが返る
8. **前提** Secret に `token` が含まれていない、**操作** 取得処理を評価する、**結果** キーが見つからないことを判別できるエラーが返る
9. **前提** `token` の値が空である、**操作** 取得処理を評価する、**結果** 空であることを判別できるエラーが返る。キーが見つからない場合と区別できる
10. **前提** Secret を読む権限が与えられていない、**操作** 取得処理を評価する、**結果** 権限が不足していることを判別できるエラーが返る
11. **前提** 問い合わせが上記以外の理由で失敗する (通信の断絶など)、**操作** 取得処理を評価する、**結果** 元の失敗の原因が判別できるエラーが返る
12. **前提** 何らかの理由でエラーが返る、**操作** そのエラーの内容を確認する、**結果** Secret の値そのものは含まれていない
13. **前提** トークンが `token` 以外のキーに格納されている、**操作** キー名をオプションで指定して評価する、**結果** そのキーの値がトークンとして返る
14. **前提** 名前空間、Secret の名前、キー名のオプションに空の値を渡した、**操作** 取得処理を作って評価する、**結果** その指定は無視され、それぞれの既定値が使われる
15. **前提** 呼び出し側が処理を打ち切る、**操作** 取得処理を評価する、**結果** 打ち切りに応じる

### 利用シナリオ 2 - 実行環境に応じて接続情報が自動で選ばれる (優先度: P2)

利用者は同じコードを、クラスタ内の Pod としても、手元の端末からも動かす。利用者が接続情報を何も指定しない場合、Kubernetes の標準的なツール群と同じ順序で接続情報が選ばれる。まず設定ファイル (環境変数が指すもの、無ければ利用者の既定の設定ファイル) を見て、そこから使える接続情報が得られなければ、クラスタ内で割り当てられた資格情報を使う。どれも見つからない場合は、取得処理を作る時点でエラーになる。

手元では設定ファイルが、設定ファイルを持たない Pod の中では割り当てられた資格情報が選ばれる。利用者が普段使っているコマンドと同じ設定で同じ接続先を向くことが、この順序の目的である。

利用者が接続情報を明示した場合は、自動の選択は行われない。

**この優先度の理由**: Kubernetes は実行場所によって接続情報の在り処が異なる。利用者に毎回の指定を強いると、同じコードをクラスタの内外で動かすために分岐を書くことになる。一方、接続情報が 1 つも無い状態を黙って通すと、失敗が API 呼び出しの時点まで遅れ、原因が分かりにくくなる。P1 に次ぐ優先度としたのは、これが取得の正しさではなく、取得に至るまでの経路の要件であるためである。

**独立した検証**: 環境変数の設定、利用者の設定ファイルの有無、割り当てられた資格情報の有無を組み合わせた状態を作り、どれが選ばれたかを確認できる。どれも無い状態で、取得処理を作る時点でエラーになることを確認できる。接続情報を明示した場合に、自動の選択が行われないことを確認できる。選ばれる接続先が、同じ環境で Kubernetes の標準的なツールが向く先と一致することを確認できる。

**受け入れシナリオ**:

1. **前提** 接続設定を指す環境変数が設定され、その設定から接続情報が得られる、**操作** 接続情報を指定せずに取得処理を作る、**結果** その環境変数が指す設定が使われる。利用者の既定の設定ファイルは読まれない
2. **前提** 環境変数は無く、利用者の既定の設定ファイルから接続情報が得られる、**操作** 接続情報を指定せずに取得処理を作る、**結果** その設定ファイルが使われる
3. **前提** 設定ファイルから使える接続情報が得られないが、クラスタ内で割り当てられた資格情報がある、**操作** 接続情報を指定せずに取得処理を作る、**結果** 割り当てられた資格情報が使われる
4. **前提** 設定ファイルから接続情報が得られ、かつクラスタ内で割り当てられた資格情報もある、**操作** 接続情報を指定せずに取得処理を作る、**結果** 設定ファイルが使われる
5. **前提** 設定ファイルも割り当てられた資格情報も無い、**操作** 取得処理を作る、**結果** 接続情報が見つからないことを判別できるエラーが、取得処理を作る時点で返る
6. **前提** 設定ファイルが存在するが内容が不正である、**操作** 取得処理を作る、**結果** その失敗を判別できるエラーが返る。割り当てられた資格情報があっても、そちらへ移ってはならない
7. **前提** 環境変数が存在しないファイルを指している、**操作** 取得処理を作る、**結果** その設定は無いものとして扱われ、次の候補へ進む
8. **前提** 利用者が接続情報を明示した、**操作** 取得処理を作る、**結果** 自動の選択は行われず、明示された接続情報が使われる
9. **前提** 設定ファイルが選ばれ、選択中の接続先に名前空間が書かれている、**操作** 名前空間を指定せずに評価する、**結果** そこに書かれた名前空間が使われる
10. **前提** 割り当てられた資格情報が選ばれた、**操作** 名前空間を指定せずに評価する、**結果** 同じ位置に置かれた名前空間の値が使われる
11. **前提** 設定ファイルが選ばれ、選択中の接続先に名前空間が書かれていない、**操作** 名前空間を指定せずに取得処理を作る、**結果** 名前空間を決められないことを判別できるエラーが、取得処理を作る時点で返る
12. **前提** 設定ファイルが選ばれ、選択中の接続先に名前空間が書かれておらず、かつ割り当てられた資格情報の名前空間の値が読める状態にある、**操作** 名前空間を指定せずに取得処理を作る、**結果** その値は使われず、名前空間を決められないことを判別できるエラーが返る。選ばれた認証情報と別の認証情報の名前空間を混ぜてはならない
13. **前提** 割り当てられた資格情報が選ばれたが、名前空間の値が読めない、**操作** 名前空間を指定せずに取得処理を作る、**結果** 名前空間を決められないことを判別できるエラーが、取得処理を作る時点で返る
14. **前提** 認証情報に名前空間の値が無い、**操作** 名前空間を明示して取得処理を作る、**結果** 明示された名前空間が使われ、エラーにならない

### 利用シナリオ 3 - 使わない利用者に依存を持ち込まない (優先度: P3)

利用者は Kubernetes を使っていない。DPF-API のクライアントを取り込んでも、Kubernetes の SDK は依存に現れない。Kubernetes 向けの追加モジュールを取り込んだ利用者にも、他のシークレット管理サービスの SDK は及ばない。

**この優先度の理由**: Kubernetes の SDK は依存が重い。本ライブラリはライブラリであり、依存は利用者のビルドと配布物へそのまま漏れる。既存の 4 つの追加モジュールと同じ分離を保たなければ、この機能の追加が、使わない利用者すべてに負担を課す。優先度を最後に置くのは、これが取得機能の正しさではなく、モジュールの分割という構造の要件であるためである。

**独立した検証**: 本体モジュールの依存の一覧に Kubernetes の SDK が現れないことを確認できる。本追加モジュールが独立して取得・ビルド・テストできることを確認できる。本追加モジュールの依存に他のシークレット管理サービスの SDK が現れないことを確認できる。

**受け入れシナリオ**:

1. **前提** 利用者が本体モジュールのみを取り込んだ、**操作** 依存の一覧を確認する、**結果** Kubernetes の SDK は現れない
2. **前提** 利用者が Kubernetes 向けの追加モジュールを取り込んだ、**操作** 依存の一覧を確認する、**結果** 他のシークレット管理サービスの SDK は現れない
3. **前提** 本追加モジュールを単独で取得した、**操作** その内容を確認する、**結果** ライセンスの全文が同梱されている
4. **前提** 本追加モジュールである、**操作** ビルドと単体テストを実行する、**結果** 独立して成功し、ネットワークアクセスも動作中のクラスタも必要としない
5. **前提** 本追加モジュールを追加した、**操作** ビルド・テスト・各検査を実行する、**結果** 対象の一覧を書き換えることなく、本モジュールが対象に含まれる
6. **前提** 本追加モジュールである、**操作** 公開された型・関数・エラー値と、パッケージの文書を確認する、**結果** いずれにも用途と使い方の記述があり、すべてのファイルの先頭にライセンス識別子が置かれている
7. **前提** 本追加モジュールである、**操作** その内部の実装を確認する、**結果** ログ出力も unsafe な機能の使用も無い
8. **前提** 本機能を追加した、**操作** 同じ変更の内容を確認する、**結果** 変更履歴と利用者向け文書が併せて更新されている

### 境界的な状況

- 既存の 4 つの取得元と作り方は揃うか？ → 揃える。トークンを返す処理を生成する手段を提供し、必須でない指定はオプションで表す。返るものは同じ形の取得処理であり、DPF-API のクライアント生成へそのまま渡せる。
- 既存の 4 つは認証を行わない (004 の FR-014) のに、本機能は接続情報を自分で選ぶ。矛盾しないか？ → 004 は「認証済みのクライアントを利用者から受け取る」と定めており、本機能でも利用者が接続情報またはクライアントを明示した場合はそれを使う。自動の選択は、利用者が何も指定しなかった場合に限られる。Kubernetes は他の 4 サービスと異なり、接続情報の在り処が標準化されており、実行環境から一意に導ける。この差が自動選択を成立させる。
- 候補が複数ある場合の順序はどうするか？ → Kubernetes の標準的なクライアントと同じ順序に合わせる。設定ファイル (環境変数 `KUBECONFIG` が指すもの、無ければ `~/.kube/config`) を先に見て、そこから使える接続情報が得られない場合にクラスタ内の資格情報を用いる。独自の順序は定めない。利用者が普段使っているコマンドと同じ接続先を向くことが、驚きの少ない挙動である。
- 設定ファイルが存在しない場合と、存在するが壊れている場合は同じ扱いか？ → 違う。存在しない場合はその候補が無いものとして次へ進む。存在するが解釈できない場合はエラーとし、クラスタ内の資格情報へ移らない。壊れた設定を黙って迂回すると、意図した接続先とは別の場所へ問い合わせることになり、どの権限で何を読んだのかが利用者に見えなくなる。
- 環境変数が存在しないファイルを指している場合はどうなるか？ → その設定は無いものとして扱い、次の候補へ進む。標準的なクライアントと同じ挙動である。
- 接続情報が 1 つも無い場合はいつ失敗するか？ → 取得処理を作る時点で失敗する。評価の時点まで遅らせない。
- 名前空間を指定しなかったとき、どこから取るか？ → 接続に用いた認証情報が持つ名前空間の値である。クラスタ内で割り当てられた資格情報を使う場合は、資格情報と同じ位置に置かれた名前空間の値 (`/var/run/secrets/kubernetes.io/serviceaccount/namespace`) を読む。設定ファイルを使う場合は、選択中の接続先に記された名前空間の値を読む。**選ばれた認証情報に紐づく値だけを用い、別の認証情報の値へ回り込まない。**
- 接続情報の選択は標準的なクライアントに合わせるのに、名前空間の決定は合わせないのか？ → 合わせない。標準的なクライアントは、設定ファイルに名前空間が書かれていない場合にクラスタ内の名前空間へ回り込み、最後は `default` を補う。本機能は回り込みも補完も行わず、決まらなければエラーとする (FR-014)。接続先の選択を揃えるのは利用者の予測に沿うためだが、名前空間を取り違えると読む対象そのものが変わる。誤りの重さが違うため、扱いを分ける。
- 認証情報から名前空間の値が得られない場合はどうなるか？ → 取得処理を作る時点でエラーとする。設定ファイルの選択中の接続先に名前空間が書かれていない場合、および名前空間の値を置いた位置が読めない場合が該当する。`default` などの推測をしてはならない。名前空間を誤ると、意図しない Secret を読むか、権限不足として失敗する。どちらも原因が利用者に見えにくい。利用者は名前空間を明示するか、認証情報側に記すことで解消できる。
- Secret の値は符号化された形で保持されるが、どう扱うか？ → 復号した値をトークンとして扱う。利用者に復号を要求してはならない。
- トークンを保持するキーの名前は変えられるか？ → 既定は `token` であり、必要な利用者はオプションで変更できる。既存の 4 つが取り出し方をオプションで表す (004 の FR-010) のに揃える。
- Secret が無い場合、キーが無い場合、値が空の場合、権限が無い場合は区別できるか？ → 区別できる。それぞれ別のエラーとして返す。原因ごとに利用者の対処が異なる (Secret の作成、キーの追加、値の投入、権限の付与) ためである。
- 単体テストのために動作中のクラスタが必要か？ → 不要。Kubernetes の操作は差し替えられる形で受け取る。
- トークンをどこかに保持するか？ → 本機能では保持しない。評価のたびに問い合わせる。保持したい場合は、DPF-API のクライアント側の有効期間の指定を用いる。
- 読み取り対象を Secret 以外へ広げるか？ → 広げない。本機能の範囲は Secret の読み取りに限る。

## 要件 *(必須)*

### 機能要件

**配置と分離**

- **FR-001**: 本機能は、本体とは別の独立したモジュールとして配置されなければならない。既存の追加モジュールと同じ位置づけとする
- **FR-002**: 本体モジュールの依存に、Kubernetes の SDK が現れてはならない
- **FR-003**: 本追加モジュールの依存に、他のシークレット管理サービスの SDK が現れてはならない
- **FR-004**: 本追加モジュールには、ライセンスの全文を同梱しなければならない。独立して取得した利用者にライセンスが届かない状態を作ってはならない
- **FR-005**: ビルド・テスト・各検査の対象は、リポジトリ内のモジュールの定義から導出されなければならない。本モジュールの追加にあたって、対象の一覧を書き換えてはならない

**取得処理の形**

- **FR-006**: 本機能は、トークンを返す処理を生成する手段を提供しなければならない。生成された処理は、DPF-API のクライアント生成が受け付ける形と一致しなければならない
- **FR-007**: 生成された処理は、評価のたびに問い合わせなければならない。本機能の内部でトークンを保持してはならない
- **FR-008**: 生成された処理は、呼び出し側の打ち切りに応じなければならない
- **FR-009**: Kubernetes の操作は、テスト時に差し替えられる形で受け取らなければならない。単体テストが動作中のクラスタへの接続を必要としてはならない
- **FR-010**: 任意の指定はオプションで表さなければならない。既定で足りる利用者に指定を要求してはならない
- **FR-011**: オプションに空の値が渡された場合は、その指定を無視し既定値を用いなければならない

**Secret の指定と読み取り**

- **FR-012**: Secret の所属する名前空間を指定できなければならない
- **FR-013**: 名前空間が指定されていない場合は、接続に用いた認証情報が持つ名前空間の値を用いなければならない。クラスタ内で割り当てられた資格情報 (`/var/run/secrets/kubernetes.io/serviceaccount/token`) を用いる場合は、同じ位置に置かれた名前空間の値 (`/var/run/secrets/kubernetes.io/serviceaccount/namespace`) を用いる。設定ファイル (`KUBECONFIG` が指すもの、または `~/.kube/config`) を用いる場合は、選択中の接続先に記された名前空間の値を用いる
- **FR-014**: 名前空間が指定されておらず、かつ接続に用いた認証情報から名前空間の値が得られない場合は、取得処理を作る時点でエラーを返さなければならない。名前空間を推測してはならない
- **FR-015**: Secret の名前を指定できなければならない
- **FR-016**: Secret の名前が指定されていない場合は、`dpf-token` を用いなければならない
- **FR-017**: Secret の中でトークンを保持するキーの既定は `token` でなければならない。利用者はオプションでキー名を変更できなければならない
- **FR-018**: Secret に保持された値が符号化されている場合は、復号した値をトークンとして扱わなければならない。利用者に復号を要求してはならない

**接続情報の選択**

- **FR-019**: 利用者は接続情報を明示できなければならない。明示された場合、自動の選択を行ってはならない
- **FR-020**: 接続情報が明示されていない場合は、Kubernetes の標準的なクライアントと同じ順序で選ばなければならない。すなわち (1) 設定ファイル — 環境変数 `KUBECONFIG` が設定されていればそれが指すもの、設定されていなければ利用者の既定の設定ファイル (`~/.kube/config`) — を先に見て、(2) そこから使える接続情報が得られない場合に、クラスタ内で割り当てられた資格情報 (`/var/run/secrets/kubernetes.io/serviceaccount/token`) を用いる。独自の順序を定めてはならない
- **FR-021**: いずれの候補も利用できない場合は、取得処理を作る時点でエラーを返さなければならない。評価の時点まで遅らせてはならない
- **FR-022**: 設定ファイルが存在するが解釈に失敗した場合は、その失敗を判別できるエラーを返さなければならない。クラスタ内の資格情報へ移ってはならない
- **FR-023**: 設定ファイルが存在しない場合、および設定ファイルから使える接続情報が得られない場合は、その候補が無いものとして扱い、次の候補へ進まなければならない。これを失敗として扱ってはならない

**エラーの区別**

- **FR-024**: 指定した Secret が存在しない場合は、Secret が見つからないことを判別できるエラーを返さなければならない
- **FR-025**: 指定したキーが Secret に存在しない場合は、キーが見つからないことを判別できるエラーを返さなければならない
- **FR-026**: 値が空である場合は、空であることを判別できるエラーを返さなければならない。キーが見つからない場合および Secret が見つからない場合と区別できなければならない
- **FR-027**: Secret を読む権限が不足している場合は、権限が不足していることを判別できるエラーを返さなければならない
- **FR-028**: 問い合わせが上記以外の理由で失敗した場合は、元の失敗の原因が判別できるエラーを返さなければならない
- **FR-029**: エラーに Secret の値そのものを含めてはならない

**共通**

- **FR-030**: 公開されたパッケージ・型・関数・エラー値には、godoc 形式のコメントを付与しなければならない
- **FR-031**: 本パッケージは用途・使い方・関連パッケージを記述した文書を持たなければならない
- **FR-032**: 公開挙動には単体テストを付与しなければならない。単体テストはネットワークアクセスを必要としてはならない
- **FR-033**: すべてのファイルの先頭にライセンス識別子を置かなければならない
- **FR-034**: `unsafe` パッケージおよび unsafe な機能を使用してはならない
- **FR-035**: 本モジュールの内部でログを出力してはならない
- **FR-036**: 利用者に見える挙動の追加であるため、変更履歴および利用者向け文書を同じ変更のなかで更新しなければならない

### 主要な実体

- **トークンの取得処理**: 評価のたびに Kubernetes へ問い合わせ、アクセストークンを返す処理。DPF-API のクライアントが受け付ける形と一致する
- **Secret の位置**: 対象の Secret を一意に指す情報。名前空間と Secret の名前からなる。いずれも省略でき、省略時は名前空間は接続に用いた認証情報が持つ名前空間の値、Secret の名前は `dpf-token` となる
- **取り出しの設定**: Secret の中のどのキーをトークンとして扱うかの指定。既定は `token`
- **接続情報**: Kubernetes へ問い合わせるための資格情報と接続先。利用者が明示するか、定められた順序で実行環境から選ばれる。名前空間の値を伴い、名前空間が指定されなかったときの導出元になる
- **追加モジュール**: Kubernetes からの取得に対応する独立したモジュール。自身の依存の定義とライセンスの全文を持ち、他のシークレット管理サービスの依存を含まない

## 前提

- 接続情報の順序は、Kubernetes の標準的なクライアントに合わせることを利用者との確認を経て決めた (2026-09-18)。初稿は利用者の記述に列挙された順 (`KUBECONFIG`、クラスタ内の資格情報、`~/.kube/config`) を優先順位として採用していたが、`KUBECONFIG` と `~/.kube/config` の間にクラスタ内の資格情報を挟む形は標準的なクライアントに存在せず、同じ環境で利用者のコマンドと本ライブラリが別の接続先を向きうる。列挙は「この 3 つを見る」ことを示したものであり、順序の指定ではないと解した
- 設定ファイルの扱いは、存在しない場合は候補が無いものとして次へ進み (FR-023)、存在して解釈できない場合はエラーとして止まる (FR-022)。この区別も標準的なクライアントの挙動に合わせた。存在しないファイルを指す環境変数で全体が止まるより、設定を持たない環境として扱う方が実務に合う
- 名前空間の決定は標準的なクライアントに合わせない。標準的なクライアントは設定ファイルに名前空間が無い場合にクラスタ内の名前空間へ回り込み、最後は `default` を補うが、本機能は選ばれた認証情報に紐づく値のみを用い、決まらなければエラーとする。接続先を取り違えても認証が失敗して気づけるが、名前空間を取り違えると別の Secret を読んで成功しうる。誤りの重さが違う
- 名前空間の既定値は、接続に用いた認証情報が持つ名前空間の値である。認証情報から値が得られない場合にエラーとすることは、利用者との確認を経て決めた (2026-09-18)。`default` を補う案は採らない。名前空間を推測すると、意図しない Secret を読むか権限不足で失敗し、いずれも原因が利用者に見えにくいためである
- トークンを保持するキーの既定は `token` とし、オプションで変更可能とした。利用者の記述は `data.token` のみを示しているが、既存の 4 つの取得元がいずれも取り出し方をオプションで表している (004 の FR-010・FR-017) ため、同じ形に揃えた
- 認証そのものは本機能の範囲外である。本機能が行うのは、標準化された場所に置かれた既存の接続情報の選択であり、新たな認証手続きの実装ではない。利用者が接続情報またはクライアントを明示した場合は、004 の FR-014 と同じく、それをそのまま用いる
- 読み取り対象は Secret に限る。ConfigMap やその他の資源、および Secret への書き込みは範囲外とする
- トークンの短期的な保持は本機能の範囲外である。DPF-API のクライアント側の有効期間の指定 (003-utils-highlevel-api) が担う
- 利用する Kubernetes の SDK は公式のものを前提とし、そのライセンスは憲章の許容リストの範囲内である。SDK の選定は本仕様では定めない
- Secret を読む権限 (RBAC) の付与は利用者の責務である。本機能は権限を要求する手段を提供せず、不足している場合にそれと分かるエラーを返すことまでを担う
- 本機能は既存の 4 つの取得元を変更しない。追加のみであり、既存の利用者に影響しない
