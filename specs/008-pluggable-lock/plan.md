# 実装計画: 排他の仕組みを差し替えられるようにする

**ブランチ**: `008-pluggable-lock` | **日付**: 2026-09-24 | **仕様**: [spec.md](./spec.md)

**入力**: 次の機能仕様 `/specs/008-pluggable-lock/spec.md`

**注記**: `ブランチ` は `.specify/feature.json` が示す機能ディレクトリ名である。実際の
git ブランチは `main`（`before_specify` フックが無いためブランチは作成していない）。
実装時に切る。

## 概要

006 と 007 が前提としている「排他」は、DPF-API のレコードを使う実装に固定されている。
利用者が etcd などの分散ロックを既に運用していても、それを使う道が無い。レコードを使う
方式には、SOA のラベルを 2 つ消費する、保持中はゾーンに未反映の編集が残る、取得のたびに
API を呼ぶ回数が増える、一括置き換えが排他を解くので特別な扱いが要る、といった制約がある。

排他を「取得・延長・解放ができるもの」として抽象化し、差し替えられるようにする。方針は
5 つある。

1. **抽象は 3 メソッドに絞る。** `Lock` / `Renew` / `Unlock` のみ。待機と保持者は含めない。
   ライブラリが必要とするものだけを実装者に求める（[research.md](./research.md) D1・D11）。
2. **`Renew` を「保持を確かめ、必要なら延ばす」と定義する。** 保持の維持を背景で行う仕組み
   （etcd のセッション）では「延ばす操作」が空になり、**排他を失ったことを検知できなく
   なる**。007 が定めた「奪われたら処理を打ち切る」が働かなくなるため、定義を変える（同 D3）。
3. **実装ごとの違いは任意のインターフェースで吸収する。** 「反映が排他を解くか」は
   `utils` の外からは実装できない非公開の形で（同 D4）、「延長の間隔」は外部の実装にも
   申告してほしいので公開の形で（同 D5）。必須メソッドを増やさない。
4. **契約は機械的に確かめられるようにする。** 006 で、排他の意味論の取り違えが静かに壊れる
   ことが分かっている。差し替えを許すとは、その取り違えを利用者が再現できるようにすると
   いうことである。`utils/lockertest` として確認の手段と参照実装を提供する（同 D8・D9）。
5. **抽象が実物に収まることを、設計の段階で確かめる。** 参照実装だけで設計すると実物に
   合わない抽象ができる。etcd の `concurrency` パッケージの**実物を読んで**当てはめた
   （同 D10）。結論は「収まる。ただし 2 点はアダプタで埋める」である。

標準ライブラリの `sync.Locker` は使えない。打ち切りもエラーも表現できないためである。
etcd 自身が提供する `sync.Locker` アダプタは、エラーを `panic` に変えている（同 D2）。

## 技術的な前提

**言語 / バージョン**: Go 1.27（`go.mod` は `go 1.27.0`）

**主要な依存**: 追加なし。本体の `go.mod` は変更しない。新設する `utils/lockertest` は
標準ライブラリの `testing` と `utils` のみに依存する

**保存先**: 該当なし。排他の状態は実装が持つ。ライブラリは抽象を通して扱うだけで、
どこに保存されるかを知らない

**テスト**: 単体テストは `go test ./... -race -count=1`（既存の `make test`）。契約の確認は
`utils/lockertest` を通して行い、ネットワークを必要としない。既定の実装の挙動が変わって
いないことは、既存の統合テスト（`make test-integration`）で確認する

**対象環境**: 本ライブラリを取り込む Go プログラム全般。差し替える側は、etcd・Consul・
Kubernetes の Lease など任意の仕組みを想定する

**プロジェクト種別**: Go ライブラリ（既存パッケージ `utils` への抽象の導入と、サブパッケージ
`utils/lockertest` の新設。新規モジュールなし）

**性能目標**: 抽象を挟むことによる追加の API 呼び出しは無い。既定の実装の呼び出し回数は
007 から変わらない（取得 8 回、一括置き換えは 12 回程度）

**制約**:
- 本体の `go.mod` に依存を追加しない（憲章 原則 V）。外部ミドルウェアの実装は `misc/` 配下の
  独立モジュールとし、本機能の範囲外とする
- ライブラリ内でログを出力しない。`unsafe` を使わない（同）
- `testing` を `utils` へ持ち込まない。確認の手段は別パッケージに置く
  （[research.md](./research.md) D8）
- 単体テストはネットワークを必要としない（憲章 原則 II）
- 既定の実装の挙動を変えない（FR-007）。利用者に見える変更は機械的な置き換えで済む範囲に
  留める
- 既定値は保守的に定め、変更手段を Option として公開する（憲章 原則 V）

**規模 / 範囲**: 要件 22 件（FR-001〜FR-022）／成功基準 7 件（SC-001〜SC-007）。
新規に公開するものは、インターフェース 2 件（`Locker` / `RenewIntervaler`）、関数 1 件
（`RunLocked`）、Option 型 2 件（`HoldOption` / `ApplierOption`）、Option 3 件
（`WithLocker` / `WithLockOptions` / 待機）、パッケージ 1 件（`utils/lockertest`）。
新規ファイルは 4 件、変更するファイルは 7 件（[research.md](./research.md) D12）

**要明確化**: なし。仕様に未解決のマーカーは無い。仕様が実装に委ねた選択（抽象の形、
既存の型との関係、既定の選ばせ方、確認手段の置き場）は [research.md](./research.md)
D1〜D11 で決定した。FR-021 が求めた実物への当てはめは D10 で完了している

**`utils/lockertest` が `testing` を import することについて**: 憲章 原則 V は「呼び出し側の
環境を侵さない」を求める。`testing` を import するパッケージは、リンクされると
コマンドラインフラグを登録する。これを避けるため、確認の手段を `utils` 本体ではなく
サブパッケージへ分けた。標準ライブラリが `net/http/httptest` を分けているのと同じ理由で
ある。利用者は自分のテストからのみ import する。

**任意のインターフェースを 2 つ設けることについて**: 憲章に直接の規範は無いが、抽象の
単純さに関わるため記録する。必須メソッドを 3 つに絞ったうえで、実装ごとの違いを 2 つの
任意インターフェースで吸収している。片方（反映が排他を解くか）は `utils` の外からは実装
できない非公開の形とし、利用者の判断を増やさない。もう片方（延長の間隔）は外部の実装に
こそ関係するため公開する。**「誰に関係があるか」で公開・非公開を分けている。**

**破壊的変更の一覧**（`CHANGELOG.md` に記載する内容）:

1. `NewZoneApplier` の可変長引数が、排他の Option（`Option`）から `ZoneApplier` の Option
   （`ApplierOption`）へ変わる。既存の呼び出しは `WithLockOptions` で包む機械的な置き換えで
   対応できる（[research.md](./research.md) D7）

`hold` と延長の仕組みを移す。`lock.go` は「レコードを使う排他の実装」に専念させる。両者を
1 ファイルに混ぜると、抽象の話とレコードの話が交ざって読めなくなる。

`utils/lockertest` をサブパッケージにするのは `testing` の持ち込みを避けるためである
（[research.md](./research.md) D8）。`utils` にサブパッケージができるのは初めてだが、
`.openapi-generator-ignore` の `utils/**` に含まれるため保護の追加は要らない。

## 複雑さの記録

> **憲章への適合確認で、正当化が必要な逸脱があった場合にのみ記入する**

憲章違反なし。ただし、単純さを損なう選択を 3 つ意図して行っているため記録する。

| 選択 | 必要な理由 | より単純な代替案を採らない理由 |
|---|---|---|
| 任意のインターフェースを 2 つ設ける | 実装ごとに違う 2 点（反映が排他を解くか、延長の間隔）を、必須メソッドを増やさずに吸収する必要がある | 必須メソッドにすると、無関係な実装にも実装を強いる。決め打ちにすると、レコードを使う排他か外部の排他のどちらかが壊れる |
| `Mutex.Do` を残したまま `RunLocked` を足す | `Mutex.Do` は v0.4.0（本日リリース）で公開したばかりであり、消すには早い | `Do` を消せば名前は 1 つになるが、リリース直後の破壊的変更に見合うものが無い。包みにすることで実装は 1 つに保てる |
| 確認の手段を別パッケージに置く | `testing` を `utils` へ持ち込むと、利用者のバイナリにテスト用のフラグが登録される | 同じパッケージに置けばファイルは減るが、すべての利用者に副作用が及ぶ。標準ライブラリも `httptest` を分けている |
