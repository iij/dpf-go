# 調査と決定: 排他の仕組みを差し替えられるようにする

**機能**: [spec.md](./spec.md) | **計画**: [plan.md](./plan.md) | **日付**: 2026-09-24

仕様に `[要明確化]` は無い。本ファイルは、仕様が実装に委ねた選択について、決定・根拠・
採らなかった案を記録する。D2 と D10 は実物の API を読んで確かめた事実に基づく。

## D1: 抽象は取得・延長・解放の 3 つに絞る

**決定**: 排他の抽象は次の 3 つのメソッドだけを持つ。

```go
type Locker interface {
	Lock(ctx context.Context) error
	Renew(ctx context.Context) error
	Unlock(ctx context.Context) error
}
```

**根拠**: ライブラリの操作（排他を保持したままの実行、ゾーン全体の一括置き換え）が必要と
するのはこの 3 つだけである（FR-002）。実装者に求めるものが少ないほど、正しい実装が
書きやすい。006 で分かったとおり排他の意味論は細かく、面が増えるほど取り違えが増える。

含めなかったもの。

- **取得できるまで待つ操作**: 取得の再試行で実現でき、実装ごとに書く必要がない。ライブラリ
  側で汎用に持つ（D11）。
- **保持者を返す操作**: ライブラリは使わない。診断のためのものであり、実装が独自に持てばよい。
- **保持期間を返す操作**: 保持期間という概念を持たない実装がある（D10 の etcd がそうである）。
  必要なのは延長の間隔であり、それは別の任意インターフェースで申告させる（D5）。

**採らなかった案**: 取得・解放だけにして延長を持たない（長い処理の途中で排他を失っても
検知できず、007 が定めた「奪われたら処理を打ち切る」が成立しない）。`utils.Mutex` の
公開メソッドをすべて含める（`LockWait` と `Owner` は実装者の負担になるだけである）。

## D2: 標準ライブラリの `sync.Locker` は使えない（実証）

**決定**: 独自の抽象を定義する。`sync.Locker` は使わない。

```go
type Locker interface {   // 標準ライブラリ
	Lock()
	Unlock()
}
```

**根拠**: 打ち切りもエラーも表現できない。ネットワーク越しの排他は取得に失敗しうるし、
待っている間に打ち切りたいこともある。この形では表せない。

**実証がある。** etcd の分散ロックは `sync.Locker` へのアダプタを提供しているが、その
実装はエラーを `panic` に変えている（`go.etcd.io/etcd/client/v3/concurrency/mutex.go`）。

```go
func (lm *lockerMutex) Lock() {
	client := lm.s.Client()
	if err := lm.Mutex.Lock(client.Ctx()); err != nil {
		panic(err)
	}
}
```

分散ロックを `sync.Locker` に収めようとすると `panic` するしかない、という具体例である。
ライブラリが利用者のプロセスを落とすことは憲章 原則 V（呼び出し側の環境を侵さない）にも
反する。

分散ロックを跨いで使える共通の抽象は、標準ライブラリにもエコシステムにも無い。etcd・
Consul・Redis・Kubernetes がそれぞれ独自の形を持っている。自分で定義するしかない。

**採らなかった案**: `sync.Locker` を埋め込んだ独自インターフェース（`panic` に頼る形を
引きずる）。`golang.org/x/sync/semaphore`（打ち切りとエラーは扱えるが、インターフェース
ではなく具象型であり、差し替えの土台にならない）。

## D3: 延長は「保持を確かめ、必要なら延ばす」

**決定**: `Renew` を「保持を確かめ、必要なら延ばす」操作として定義する。保持していないと
分かる場合は `ErrNotLockHolder` を返す。延ばす必要が無い実装でも、確かめる責任は負う。

**根拠**: 保持の維持を背景で行う仕組みがある（D10 の etcd がそうで、リースの更新は
セッションが自動で行う）。延長を「延ばす操作」と定義すると、そうした実装では `Renew` が
常に何もしないことになり、**保持を失ったことを検知する手段が無くなる**。007 が定めた
「排他を奪われたら処理へ渡した打ち切りを発火させる」（007 FR-004）が働かなくなる。

「確かめる」と定義すれば、etcd ではセッションが生きているかを見るだけで済み、レコードを
用いる排他では従来どおり書き込みで延ばす。どちらも同じ意味を持つ。

確かめる手段すら無い実装は常に成功を返してよいが、その場合に処理の途中で排他を失っても
検知できないことを文書に明記する（FR-010b）。

**採らなかった案**: 延長を任意のメソッドにする（実装しない実装が既定になり、検知できない
状態が普通になってしまう）。保持の喪失を伝える専用のチャネルを別に設ける（`Renew` の
戻り値で足りるものを増やす）。

## D4: 「反映が排他を解くか」は非公開の任意インターフェースで申告する

**決定**: ゾーン全体の一括置き換えが排他を解くかどうかは、非公開のメソッドを持つ任意の
インターフェースで申告させる。申告が無ければ「解かれない」とみなす。

```go
// utils パッケージの内部
type zoneApplyConsumer interface {
	consumedByZoneApply() bool
}
```

**根拠**: レコードを用いる排他だけが特殊である。排他のラベルは SOA の未反映の編集としてのみ
存在し、一括置き換えは未反映の編集を引き継がない（007 research.md D1、実測）。外部の
ミドルウェアを使う排他でこれが起こることはない。したがって既定は「解かれない」でよい。

**非公開のメソッドにするのは、`utils` の外からは実装できないようにするためである。**
公開すると、すべての実装者が「これは何を意味するのか」を考えることになる。申告が必要なのは
DPF-API のレコードを使う実装だけであり、それは `utils` の中にある。型で表現できる制約は
型で表現する。

**採らなかった案**: 公開の任意インターフェースにする（利用者に無用な判断を強いる）。
`Locker` の必須メソッドにする（すべての実装に無関係な負担を課す。D1 の最小性に反する）。
解放時の「保持者でない」を常に成功として扱う（本当に奪われた場合の信号を失う。007 D8 で
同じ判断をしている）。

## D5: 延長の間隔は公開の任意インターフェースで申告する

**決定**: 延長の間隔を自分で決められる実装のために、公開の任意インターフェースを設ける。
申告が無く、利用者の指定も無い場合は既定値を使う。

```go
type RenewIntervaler interface {
	RenewInterval() time.Duration
}
```

**根拠**: 007 では `Mutex` が保持期間の 1/3 を延長の間隔として導いていた。抽象を挟むと
保持期間が見えなくなるため、そのままでは利用者が保持期間を変えるたびに延長の間隔も指定し
直すことになる。実装に申告させれば、`Mutex` は従来どおり保持期間の 1/3 を返し、利用者は
何もしなくてよい。etcd の実装ならセッションの TTL から導ける。

こちらを公開にするのは、外部の実装にも申告してほしいためである。D4 とは逆の判断になるが、
理由も逆である。D4 は「外部の実装には関係が無い」、D5 は「外部の実装にこそ関係がある」。

**採らなかった案**: 延長の間隔を利用者の指定だけにする（保持期間との整合が崩れる）。
`Locker` の必須メソッドにする（保持期間の概念を持たない実装に無意味な実装を強いる）。

## D6: 汎用の実行は自由関数にし、`Mutex.Do` は薄い包みとして残す

**決定**: 排他を保持したままの実行を、`Locker` を受け取る自由関数として提供する。

```go
func RunLocked(ctx context.Context, l Locker, fn func(context.Context) error, opts ...HoldOption) error
```

`Mutex.Do` は残し、`RunLocked` の薄い包みとする。

**根拠**: 007 で `Mutex.Do` を公開したのは v0.4.0（2026-09-24 リリース）であり、消すには
早すぎる。一方、実装を 2 つ持つのは避けたい。`Do` を包みにすれば、動く実装は 1 つで済み、
既存の呼び出しもそのまま動く。

名前に `With` を使わないのは、この package では `With...` が Option の生成関数を意味して
いるためである（`WithOwner`、`WithTTL`、`WithRenewInterval` など）。`WithLock` という名前は
Option に見えてしまう。

**採らなかった案**: `Mutex.Do` を消して自由関数だけにする（リリース直後の破壊的変更であり、
得るものが名前の統一だけである）。`Locker` を包む型（`Holder` など）を新設する（保持する
状態が設定しか無く、型を作るほどではない）。`Do` を `Locker` のメソッドにする（実装者が
汎用の処理を書くことになる。D1 の最小性に反する）。

## D7: `ZoneApplier` は Option で排他を差し替える

**決定**: `NewZoneApplier` の可変長引数を、排他の Option から `ZoneApplier` の Option へ
変える。排他の差し替えと、既定の排他への設定の受け渡しを、それぞれ Option で行う。

```go
func NewZoneApplier(cr dpf.RecordsApi, cz dpf.ZonesApi, cj dpf.JobsApi, zoneID string,
	opts ...ApplierOption) *ZoneApplier

func WithLocker(l Locker) ApplierOption          // 排他を差し替える
func WithLockOptions(opts ...Option) ApplierOption // 既定の排他への設定
```

**根拠**: 現在の `NewZoneApplier` は可変長引数で排他（`Mutex`）の Option を受け取り、内部で
排他を生成している。ここへ「排他そのものを渡す」道を足すには、可変長引数の型を変えるしか
ない。Go では可変長引数を 2 つ並べられないためである。

既存の呼び出し `NewZoneApplier(a, b, c, id, utils.WithTTL(x))` は
`NewZoneApplier(a, b, c, id, utils.WithLockOptions(utils.WithTTL(x)))` へ変わる。破壊的変更
だが**機械的な置き換えで済む**（FR-007）。v0.4.0 のリリース当日であり、影響範囲は小さい。

排他を差し替えた場合、`WithLockOptions` は意味を持たない。両方指定された場合は差し替えを
優先し、その旨を godoc に書く。

**採らなかった案**: 別のコンストラクタを足す（`NewZoneApplier` と
`NewZoneApplierWithLocker` の 2 つになり、どちらを使うべきかの判断を利用者に強いる）。
排他を必須の引数にする（差し替えない利用者に排他の生成を強いる。利用シナリオ 2 に反する）。

## D8: 契約の確認手段は独立したパッケージに置く

**決定**: 契約の確認手段を `utils/lockertest` パッケージとして提供する。

```go
func Run(t *testing.T, newPair func(t *testing.T) (utils.Locker, utils.Locker))
```

**根拠**: 確認の手段は `testing` を import する。これを `utils` に置くと、`utils` を使う
すべての利用者のバイナリにテスト用のフラグが持ち込まれる。標準ライブラリが
`net/http/httptest` を別パッケージにしているのと同じ理由である。

同じゾーンに対する排他を 2 つ作る関数を受け取るのは、契約の中心が「一方が保持している間は
もう一方が取得できない」ことだからである。1 つでは競合を確かめられない。

**採らなかった案**: `utils` に直接置く（`testing` の持ち込み）。文書だけにする（006 で、
排他の意味論の取り違えが静かに壊れることが分かっている。機械的に確かめられるべきである）。

## D9: 参照実装はメモリ内のものとする

**決定**: 契約を満たす参照実装を `lockertest` に置く。プロセス内で完結し、外部の
ミドルウェアを必要としない。

**根拠**: 確認の手段には「契約を満たす実装」が要る。自分自身を確かめる対象にもなり、
利用者が自作の実装を書くときの手本にもなる。`utils.Mutex` は DPF-API を必要とするため、
この役には立たない。

**この実装は分散ロックの難しさを再現しない。** プロセス内の排他であり、ネットワークの
分断も保持期間の失効も起こらない。抽象が実物に収まるかは、これでは確かめられない。
そのために D10 を行う。

**採らなかった案**: 参照実装を置かない（確認の手段を自分で確かめられない）。`utils.Mutex`
を参照実装とする（ネットワークが要る。憲章 原則 II の「単体テストはネットワーク不要」に反する）。

## D10: etcd への当てはめ（FR-021、実物で確認）

**決定**: 抽象は etcd の分散ロックに収まる。ただし 2 点、アダプタ側で埋める必要がある。

**確認の方法**: `go.etcd.io/etcd/client/v3@v3.7.1` の `concurrency` パッケージの実物を
読んだ（モジュールキャッシュにあったもの）。推測ではない。

| 本機能の抽象 | etcd の対応 | 備考 |
|---|---|---|
| `Lock(ctx) error` | `Mutex.TryLock(ctx) error` | 保持されている場合は `concurrency.ErrLocked` を返す。これを `ErrStillLock` へ写す |
| `Renew(ctx) error` | `Session.Done()` を見る | リースの更新はセッションが背景で行う。閉じていれば `ErrNotLockHolder` を返す |
| `Unlock(ctx) error` | `Mutex.Unlock(ctx) error` | `ErrSessionExpired` / `ErrLockReleased` を `ErrNotLockHolder` へ写す |
| 延長の間隔の申告 | セッションの TTL から導く | `concurrency.WithTTL(n)` で指定した値を使う |

**アダプタ側で埋める点が 2 つある。**

1. **取得は `Lock` ではなく `TryLock` を使う。** `Mutex.Lock` は取得できるまで**待つ**。
   本機能の契約は「取得できなければただちに `ErrStillLock` を返す」であり、待つかどうかは
   呼び出し側が決める（D11）。`TryLock` は保持されていれば `ErrLocked` を返して戻るため、
   こちらが対応する。
2. **再入の禁止はアダプタが担保する。** 同じ `Mutex` に対する 2 回目の `TryLock` は、自分が
   保持していることを検出して**成功を返す**（`mutex.go` の
   `ownerKey[0].CreateRevision == m.myRev` の分岐）。本機能の契約は再入を禁じるため
   （006 FR-017 から継承）、アダプタが保持中かどうかを記録して `ErrStillLock` を返す。

**結論**: 抽象の 3 メソッドは etcd の形に無理なく収まる。収まらなかった点は無い。上記 2 点は
「etcd の既定の挙動が本機能の契約と違う」ものであり、アダプタで吸収できる範囲である。
D3 で延長を「確かめる」と定義し直したことが、ここで効いている。元の定義（延ばす操作）の
ままだと、etcd では `Renew` が空になり喪失を検知できなかった。

**採らなかった案**: etcd に合わせて「取得は待ってもよい」と契約を緩める（待つかどうかを
実装が決めることになり、利用者から見た振る舞いが実装ごとに変わる）。再入を許す契約にする
（006 で、再入を許す判定が同一ユーザ間の排他を無効にしていた。同じ穴を作ることになる）。

## D11: 待機と保持者は抽象に含めない

**決定**: 取得できるまで待つ操作は、`RunLocked` の Option（`WithLockWait`）として汎用に
実装する。保持者を返す操作は抽象に含めない。

**根拠**: 待機は「取得を繰り返す」だけで実現でき、実装ごとに書く理由が無い。既に
`Mutex.LockWait` があるが、これは `Mutex` 固有の便宜として残す。保持者はライブラリが
使わないため、必要な実装が独自に持てばよい（`Mutex.Owner` は残す）。

**採らなかった案**: `LockWait` を抽象に含める（すべての実装者に再試行の実装を求めることに
なる。しかも間隔の扱いを取り違えやすい）。
