# 機能仕様: 排他の仕組みを差し替えられるようにする

**機能ブランチ**: `008-pluggable-lock`

**作成日**: 2026-09-24

**状態**: ドラフト

**憲章**: v2.0.1 の原則 II (テストを伴う実装、統合テストの隔離)、原則 III (godoc と CHANGELOG の同時更新)、原則 V (ライブラリとしての規律、本体への依存追加の禁止、optional な機能は `misc/` 配下の独立モジュールへ) に整合

**入力**: 利用者による記述: "lockはレコードロック以外にもetcd等のミドルウェアによるlockもできるようにしたいので、interface化したいです"

**関連**: 006-zone-lock-redesign（レコードを用いたゾーン単位の排他）、007-zone-atomic-apply（排他を保持したままの実行と、ゾーン全体の一括置き換え）。本機能はこの 2 つが前提としている「排他」を、差し替え可能なものにする

## 利用シナリオと検証 *(必須)*

### 利用シナリオ 1 - 自分の環境に合った排他の仕組みを選べる (優先度: P1)

利用者はすでに分散ロックの仕組みを運用している。etcd、Consul、Kubernetes の Lease と
いったものである。ゾーンを編集するプログラムも、その仕組みで排他したい。

現在の排他は DPF-API のレコードを使って実現されており、差し替えられない。レコードを
使う方式には次の制約がある。

- SOA レコードのラベルを 2 つ消費する。利用者が自由に使えるラベルは 8 個までになる
- 排他を保持している間、ゾーンに未反映の編集が存在する。この状態では DNSSEC の有効化
  など一部の操作が行えない
- 取得のたびに専用レコードの作成と取り消しが発生し、API を呼ぶ回数が増える
- ゾーン全体の一括置き換えは排他を解いてしまうため、特別な扱いが必要になる

利用者が既に信頼している仕組みを使えれば、これらの制約はなくなる。本機能は、排他を
「取得・延長・解放ができるもの」として抽象化し、利用者が実装を差し替えられるようにする。

**この優先度の理由**: 本機能の目的そのものである。差し替えられること自体が価値であり、
これが無ければ利用者は自分で排他を書き、ライブラリの提供する「保持したままの実行」や
「ゾーン全体の一括置き換え」を諦めることになる。

**独立した検証**: 既定とは別の排他の実装を用意して渡し、ライブラリの操作（保持したままの
実行、ゾーン全体の一括置き換え）がそのまま動くことを確認できる。実装の中で取得・延長・
解放が呼ばれることを確認できる。

**受け入れシナリオ**:

1. **前提** 利用者が独自の排他の実装を用意した、**操作** ライブラリの操作へその実装を渡す、**結果** 取得・延長・解放がその実装に対して行われ、操作の呼び出し方は既定の場合と変わらない
2. **前提** 独自の実装を渡している、**操作** 排他を保持したまま処理を実行する、**結果** 実行中は自動で延長され、終了時に解放される
3. **前提** 独自の実装を渡している、**操作** ゾーン全体の一括置き換えを行う、**結果** 排他の下で実行され、正しく解放される
4. **前提** 独自の実装が「まだ保持されている」ことを表すエラーを返す、**操作** 排他を取得する、**結果** ライブラリはそれを取得できなかった場合として扱う
5. **前提** 独自の実装が「保持者でない」ことを表すエラーを返す、**操作** 延長が行われる、**結果** ライブラリはそれを排他を失った場合として扱い、処理へ渡した打ち切りを発火させる

---

### 利用シナリオ 2 - 差し替えない利用者は今までどおり使える (優先度: P2)

多くの利用者は分散ロックの仕組みを持っていない。その人たちにとって、レコードを使う排他は
「追加の運用なしで使える」という利点がある。差し替えの仕組みを入れることで、この人たちの
使い方が複雑になってはならない。

排他を指定しなければ、これまでどおりレコードを使う排他が使われる。既存の書き方を変える
必要がない。変更が必要な場合でも、機械的な置き換えで済む形にする。

**この優先度の理由**: 差し替えの仕組みは、使わない人にとっては複雑さでしかない。既定の
使い勝手を損なうなら、機能全体の価値が下がる。

**独立した検証**: 既存の利用例が、変更なし（または機械的な置き換えのみ）で動くことを
確認できる。排他を指定しない場合にレコードを使う排他が選ばれることを確認できる。

**受け入れシナリオ**:

1. **前提** 排他の実装を指定していない、**操作** ライブラリの操作を呼ぶ、**結果** レコードを使う排他が使われる
2. **前提** 006・007 で書かれた既存の利用例がある、**操作** 本機能の後に同じコードを動かす、**結果** 動作が変わらない。変更が必要な場合は、その内容が `CHANGELOG.md` に記載されている

---

### 利用シナリオ 3 - 自作の実装が契約を満たすか確かめられる (優先度: P3)

利用者が自分で実装を書くとき、「どう振る舞えば正しいのか」が分からなければ、静かに壊れた
排他ができあがる。006 で明らかになったとおり、排他の意味論は細かい。再入できないこと、
「まだ保持されている」と「保持者でない」を区別すること、延長が失敗したときの扱い、といった
点を取り違えると、排他として機能しなくなる。

契約を文書化するだけでなく、**実装が契約を満たすかを機械的に確かめる手段**を提供する。

**この優先度の理由**: 差し替えができても、間違った実装を作りやすいままでは危険である。
ただし契約の文書化だけでも最低限は成立するため、優先度は 1 つ下げる。

**独立した検証**: 契約を満たす実装と、わざと満たさない実装を用意し、確認の手段が前者を
通し後者を落とすことを確認できる。

**受け入れシナリオ**:

1. **前提** 利用者が排他の実装を書いた、**操作** 提供された確認の手段にその実装を渡す、**結果** 契約を満たしていれば成功し、満たしていなければどの約束に反しているかが分かる
2. **前提** 実装が再入を許してしまう、**操作** 確認の手段に渡す、**結果** 再入が許されていることが検出される

---

### 境界的な状況

- ゾーン全体の一括置き換えは、実装によって排他を解いたり解かなかったりする。どう扱うか？ → レコードを使う排他では反映が排他を解く（006・007 の実測）。外部の仕組みを使う排他では解かれない。**この違いを利用者に意識させてはならない。** どちらの実装でも、ゾーン全体の一括置き換えの呼び出し方と結果は同じでなければならない。
- 外部の仕組みを使う排他に替えると、何が失われるか？ → **別ユーザや管理画面からの編集を止める効果が失われる。** レコードを使う排他は、編集中のレコードを他ユーザが編集できないという DPF-API の性質によって、ライブラリを使っていない相手にも効く。外部の仕組みは、その仕組みを使うプログラム同士しか排他しない。この違いを文書に明記する。
- 保持期間という概念を持たない実装はどう扱うか？ → 延長は「保持を確かめ、必要なら延ばす」操作である。延ばす必要が無くても、**保持を失っていることが分かるなら「保持者でない」を返す**。確かめる手段も無い実装は常に成功を返してよいが、その場合は長い処理の途中で排他を失っても検知できない。この限界を文書に明記する。
- 排他の対象（どのゾーンに対する排他か）は誰が決めるか？ → 実装が決める。ライブラリは「この排他」を受け取るだけであり、それがどのゾーンに対応するかを知らない。**取り違えると、別のゾーンの排他の下でゾーンを編集してしまう。** 対応づけの責任が実装側にあることを文書に明記する。
- 既定の排他と外部の排他を同時に使いたい場合は？ → 2 つを順に取得する実装を利用者が書けばよい。ライブラリが組み合わせの仕組みを用意する必要はない。別ユーザからの編集も止めたい場合の選択肢として文書に記す。
- 実装が取得に成功したと返したが、実際には保持していない場合は？ → ライブラリは検出できない。実装の責任である。契約に明記する。

## 要件 *(必須)*

### 機能要件

**排他の抽象**

- **FR-001**: 排他を、取得・延長・解放ができるものとして抽象化しなければならない。ライブラリの操作（排他を保持したままの実行、ゾーン全体の一括置き換え）は、この抽象を通して排他を扱わなければならない
- **FR-002**: 抽象は、ライブラリの操作が必要とする最小限に留めなければならない。実装者の負担を増やす要素を含めてはならない
- **FR-003**: 「まだ保持されているため取得できなかった」ことと「保持者でない」ことを、実装が呼び出し側へ伝えられなければならない。ライブラリはこの 2 つを区別して扱う
- **FR-004**: 抽象の契約（再入できないこと、エラーの意味、延長の意味）を文書化しなければならない

**既定の実装**

- **FR-005**: 現在のレコードを用いた排他は、この抽象の実装として位置づけなければならない
- **FR-006**: 排他の実装を指定しない場合は、レコードを用いた排他が使われなければならない
- **FR-007**: 006・007 で定めた既存の挙動を変えてはならない。利用者に見える変更が生じる場合は、機械的な置き換えで対応できる範囲に留め、`CHANGELOG.md` に記載しなければならない

**実装による違いの吸収**

- **FR-008**: ゾーン全体の一括置き換えは、排他が反映によって解かれる実装でも解かれない実装でも、同じ呼び出し方で正しく動作しなければならない。呼び出し側にこの違いを意識させてはならない
- **FR-009**: 排他が反映によって解かれるかどうかは、実装が申告できなければならない。ライブラリはその申告に従って解放と延長の扱いを変える
- **FR-010**: 延長は「保持を確かめ、必要なら延ばす」操作として定義しなければならない。保持期間という概念を持たない実装でも、**保持を失っていることが分かる場合は「保持者でない」を返さなければならない**
- **FR-010b**: 保持しているかを確かめる手段を持たない実装は、延長で常に成功を返してよい。その場合、長い処理の途中で排他を失っても検知できないことを文書に明記しなければならない

**抽象の妥当性**

- **FR-021**: 抽象が、外部のミドルウェアを使う実装に無理なく収まることを、設計の段階で少なくとも 1 つの実物（etcd を想定）に当てはめて確認しなければならない。確認した内容と、収まらなかった点があればその扱いを記録しなければならない

**実装の検証**

- **FR-011**: 実装が契約を満たすかを機械的に確かめる手段を提供しなければならない
- **FR-012**: 確認の手段は、契約のどの約束に反しているかを示さなければならない
- **FR-013**: 確認の手段は、ネットワークや外部のミドルウェアを必要としない形でも使えなければならない

**文書**

- **FR-014**: 外部の仕組みを使う排他に替えた場合、別ユーザや管理画面からの編集を止める効果が失われることを明記しなければならない
- **FR-015**: 排他がどのゾーンに対応するかを決める責任が実装側にあることを明記しなければならない
- **FR-016**: レコードを用いた排他と外部の仕組みを使う排他の、それぞれの利点と制約を比較できる形で示さなければならない
- **FR-017**: 利用者に見える変更を `CHANGELOG.md` に記録しなければならない

**依存の隔離**

- **FR-018**: 本体が依存する外部パッケージを増やしてはならない。外部のミドルウェアを使う実装を提供する場合は、`misc/` 配下の独立したモジュールとして配置しなければならない（憲章 原則 V）

**検証**

- **FR-019**: 抽象と既定の実装の組み合わせを単体テストで確認しなければならない。ネットワークを必要としてはならない
- **FR-020**: 既定の実装が、本機能の前後で挙動を変えていないことを、既存の統合テストによって確認しなければならない

### 主要な実体

- **排他**: 取得・延長・解放ができるもの。特定のゾーンに対応づくが、その対応づけは実装が持つ
- **排他の契約**: 実装が守るべき約束。再入できないこと、2 種類のエラーの区別、延長の意味、反映によって解かれるかどうかの申告
- **確認の手段**: 実装が契約を満たすかを機械的に確かめるもの

## 成功基準 *(必須)*

### 測定可能な成果

- **SC-001**: 利用者は、排他の実装を差し替えても、排他を保持したままの実行とゾーン全体の一括置き換えの呼び出し方を変える必要がない
- **SC-002**: 排他の実装を指定しない利用者のコードは、本機能の前後で変更なしに動作する。変更が必要な場合、その範囲は機械的な置き換えで済み、`CHANGELOG.md` に記載されている
- **SC-003**: 利用者が自作の実装を書く場合、契約を満たしているかを自分で確かめられる。契約に反する実装が検出されずに通る事象が 0 件である
- **SC-004**: 本体が依存する外部パッケージが増える事象が 0 件である
- **SC-005**: 排他が反映によって解かれる実装と解かれない実装の違いによって、ゾーン全体の一括置き換えの結果が変わる事象が 0 件である
- **SC-006**: 外部の仕組みを使う排他を選んだ利用者が、別ユーザからの編集を止める効果が失われることを知らずに使う事象が 0 件である（文書に明記され、比較表から読み取れる）
- **SC-007**: 抽象が、外部のミドルウェアを使う実装に収まらないことが後から判明する事象が 0 件である。設計の段階で少なくとも 1 つの実物に当てはめて確認している

## 前提

- 本機能は 006-zone-lock-redesign の排他と、007-zone-atomic-apply の 2 つの操作を前提とする。それらの意味論（再入できない、延長は取得とは別の操作、取得・延長・解放がゾーン反映を伴わない）が、抽象の契約の土台になる
- レコードを用いた排他では、ゾーン全体の一括置き換えが排他を解く。2026-09-24 に実測で確認した（007 research.md D1）。外部の仕組みを使う排他ではこれは起こらない
- レコードを用いた排他は、編集中のレコードへの他ユーザからの編集を DPF-API が拒否することによって、ライブラリを使っていない相手にも効く。外部の仕組みを使う排他にはこの効果が無い
- 外部のミドルウェアに依存する実装は `misc/` 配下の独立したモジュールとして配置する。`misc/vault`・`misc/aws`・`misc/azure`・`misc/gcp`・`misc/k8s` がトークン取得で同じ形を採っており、その作法に倣う（憲章 原則 V）
- 抽象の名前、メソッドの形、既存の型との関係、既定の実装をどう選ばせるかは本仕様では定めない。実装計画で決める
- Go の標準ライブラリには、この用途に使えるロックの抽象が無い。標準にあるのは取得と解放だけを持つものであり、打ち切りもエラーも表現できないため、ネットワーク越しの排他には使えない。分散ロックを跨いで使える共通の抽象はエコシステムにも定着しておらず、自分で定義するしかない
- etcd の分散ロックは、取得と解放が打ち切りとエラーを扱い、**保持の維持はセッション（リース）の側で背景的に行われる**形だと理解している。この形では「延長」に相当する呼び出しが何もしないことになるため、FR-010 では延長を「保持を確かめ、必要なら延ばす」と定義した。この理解が実際の API と合っているかは FR-021 の確認で確かめる
- 既定値は保守的に定め、変更手段を Option として公開する（憲章 原則 V）
- **本機能の範囲は、抽象化・既定の実装の位置づけ・契約の確認手段・参照実装までとする。** etcd など具体的なミドルウェアを使う実装は別の機能として扱う。理由は 2 つある。(1) 契約の確認手段を作るには、契約を満たす実装と満たさない実装がどのみち必要であり、参照実装はその土台になる。(2) 外部ミドルウェアの実装は、依存の追加・ライセンスの確認・サーバを要する統合テストの基盤という、抽象の良し悪しとは別の作業を伴う
- 参照実装は、外部のミドルウェアを必要としない範囲で用意する。これは「分散ロックの難しさ」を再現するものではなく、**契約を機械的に確かめるための土台**である。この実装だけで設計すると実物に合わない抽象ができるため、FR-021 で実物への当てはめを求める
