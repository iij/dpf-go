## 利用シナリオと検証 *(必須)*

### 利用シナリオ 1 - 設定を書かずに API クライアントを得られる (優先度: P1)

利用者は環境変数にアクセストークンを置き、引数なしでクライアントを生成する。エンドポイントは本番が既定なので指定しない。生成したクライアント経由の呼び出しは、DPF-API のレート制限を超えないよう自動的に間隔が空き、同時実行数も抑えられる。レスポンスが得られずに失敗した呼び出しは自動で再試行される。トークンが外部でローテーションされても、クライアントを作り直す必要はない。設定の誤りは、最初の API 呼び出しではなくクライアント生成の時点で分かる。

**この優先度の理由**: 利用者が最初に触れる入口であり、他のすべてのシナリオがこのクライアントを前提とする。またレート制限・同時実行数・リトライ・トークンの取り扱いは、いずれも誤ると相手のサービスに負荷をかけるか、認証情報を意図しない相手へ送ってしまう。既定値が保守的でなければ、利用者は気づかずに危険な設定で動かす。

**独立した検証**: 環境変数のみを設定してクライアントを生成し、API を呼べることを確認できる。トークンを未設定にして生成が失敗することを確認できる。既定のレート制限を超える速度で呼び出しを並べ、実際の送出が既定値に収まることを確認できる。別ホストへのリダイレクトを返す試験用のサーバに対して、認証情報が送られないことを確認できる。

**受け入れシナリオ**:

1. **前提** アクセストークンが環境変数に設定されている、**操作** 引数なしでクライアントを生成する、**結果** 生成が成功し、本番のエンドポイントに対して API を呼べる
2. **前提** エンドポイントが環境変数に設定されている、**操作** 引数なしでクライアントを生成する、**結果** その環境変数のエンドポイントが使われる。オプションでの明示指定はこれより優先される
3. **前提** トークンがどの手段でも与えられていない、**操作** クライアントを生成する、**結果** 生成は失敗し、トークンが必要であることが判別できるエラーが返る
4. **前提** トークンを取得する処理が失敗する状態にある、**操作** クライアントを生成する、**結果** 生成は失敗し、元の失敗の原因が判別できるエラーが返る
5. **前提** 既定の設定である、**操作** 多数の呼び出しを一斉に開始する、**結果** 送出は 1 秒あたり 5 リクエスト (バースト 10) を超えず、同時実行数は 5 を超えない
6. **前提** レスポンスが得られずに失敗する呼び出しである、**操作** 処理の実行を依頼する、**結果** 既定で 3 回まで再試行される
7. **前提** HTTP レスポンスを伴う API エラーである、**操作** 処理の実行を依頼する、**結果** 再試行せず、ただちにそのエラーが返る
8. **前提** トークンの取得に失敗するエラーである、**操作** 処理の実行を依頼する、**結果** 再試行せず、ただちにそのエラーが返る
9. **前提** トークンを返す処理を利用者が与えている、**操作** 複数回 API を呼ぶ、**結果** 呼び出しのたびにその処理が評価され、最新のトークンが使われる
10. **前提** トークンの有効期間が指定されている、**操作** その期間内に複数回 API を呼ぶ、**結果** トークンを返す処理は再評価されない
11. **前提** API のエンドポイントとは別のホストへリダイレクトされる、**操作** API を呼ぶ、**結果** そのリクエストに認証情報は付与されない
12. **前提** クライアントを生成した、**操作** 送信されるリクエストのヘッダを確認する、**結果** 利用者エージェントに本モジュールの名称とバージョンが含まれている
13. **前提** 任意の操作を行う、**操作** ライブラリの出力を確認する、**結果** ライブラリ自身はログを出力しない

### 利用シナリオ 2 - 非同期 JOB の終了を待てる (優先度: P2)

利用者はゾーンへレコードを追加する。DPF-API の更新系はいずれも非同期であり、呼び出しはすぐに戻るが処理は継続している。利用者は返り値をそのまま渡して終了を待ち、成功したか失敗したかを 1 つのエラーで受け取る。失敗した場合は、DPF-API が返した失敗の種別と内容が分かる。

**この優先度の理由**: DPF-API の更新系はすべて非同期である。終了を待たずに次の操作へ進むと、直前の変更が反映されていない状態で判断することになり、ゾーンの内容が意図しない形になる。待ち合わせを利用者に書かせると、状態値の解釈と待ち方をそれぞれが実装することになり、失敗の見落としが起きる。

**独立した検証**: 進行中から成功へ、進行中から失敗へ遷移する試験用の API に対して、それぞれ正しく待ち合わせて結果を返すことを確認できる。呼び出しがエラーを返していた場合にそのまま返ることを確認できる。待ち時間に上限を設けた場合に、その上限で打ち切られることを確認できる。

**受け入れシナリオ**:

1. **前提** 非同期の更新 API を呼んだ、**操作** その返り値をそのまま渡して終了を待つ、**結果** JOB が成功で終了した時点の情報が返り、エラーは返らない
2. **前提** 非同期 JOB が失敗で終了する、**操作** 終了を待つ、**結果** 失敗の種別と内容を含むエラーが返り、終了時点の JOB の情報も返る
3. **前提** 元の呼び出し自体がエラーを返していた、**操作** 終了を待つ処理へその返り値を渡す、**結果** JOB の確認は行わず、そのエラーがそのまま返る
4. **前提** JOB がまだ進行中である、**操作** 終了を待つ、**結果** 一定の間隔で状態を確認し続ける
5. **前提** 待ち時間に上限を設けた、**操作** その上限を超えて JOB が終わらない、**結果** 上限で打ち切られ、その理由が分かるエラーが返る
6. **前提** 元の呼び出しの過程で内部的に打ち切りが起きていた、**操作** 終了を待つ、**結果** 最初の状態確認が打ち切りで即座に失敗することはない
7. **前提** 分散トレースが設定されている、**操作** 終了を待つ、**結果** 状態確認のスパンは元の呼び出しと同じトレースに属する
8. **前提** いずれの場合も、**操作** 返り値を確認する、**結果** 元の呼び出しの HTTP レスポンスがそのまま返される

### 利用シナリオ 3 - ドメイン名からゾーンとレコードを引ける (優先度: P3)

利用者は操作したいレコードのドメイン名しか知らない。どのゾーンに属するかは、契約しているゾーンの一覧との照合が必要である。利用者はドメイン名を渡すだけで、そのドメイン名を最も長く含むゾーンを得られる。ゾーン ID を知っていれば、名前と RRTYPE からレコードを直接引ける。末尾のドットの有無や大文字小文字の違いは、利用者が気にする必要がない。

**この優先度の理由**: DPF-API はゾーン ID を鍵として操作する一方、利用者が持っている情報はドメイン名かサービスコードである。この橋渡しがなければ、利用者は毎回ゾーンの一覧を取得して自分で照合することになる。その照合を文字列操作で書くと、末尾ドット・大文字小文字・エスケープ・ラベル長という DNS 名の規則を再実装することになり、最長一致が静かに誤る。

**独立した検証**: 親子関係にある複数のゾーンを含む一覧に対して、最長一致が選ばれることを確認できる。末尾のドットの有無、大文字小文字を変えた入力で同じ結果が返ることを確認できる。上位ゾーンのみを対象とする指定で、完全一致のゾーン自身が除外されることを確認できる。該当がない場合に、それを判別できるエラーが返ることを確認できる。

**受け入れシナリオ**:

1. **前提** ドメイン名を含むゾーンが複数 (親と子) 存在する、**操作** ドメイン名からゾーンを取得する、**結果** ドメイン名を最も長く含むゾーンが返る
2. **前提** ドメイン名と完全一致するゾーンが存在する、**操作** 上位ゾーンのみを対象として取得する、**結果** 完全一致のゾーン自身は除外され、その真の上位ゾーンが返る
3. **前提** 末尾のドットの有無、大文字小文字が異なる同じドメイン名である、**操作** ゾーンを取得する、**結果** いずれも同じゾーンが返る
4. **前提** 該当するゾーンが存在しない、**操作** ゾーンを取得する、**結果** ゾーンが見つからないことを判別できるエラーが返る
5. **前提** サービスコードを知っている、**操作** サービスコードからゾーンを取得する、**結果** そのサービスコードのゾーンが返る。存在しなければ、ゾーンが見つからないことを判別できるエラーが返る
6. **前提** ゾーン ID・レコード名・RRTYPE を知っている、**操作** レコードを取得する、**結果** 名前と RRTYPE が完全一致するレコードが返る
7. **前提** レコード名の部分一致で複数のレコードが候補になる、**操作** レコードを取得する、**結果** 完全一致するものだけが返り、部分一致のものは返らない
8. **前提** 該当するレコードが存在しない、**操作** レコードを取得する、**結果** レコードが見つからないことを判別できるエラーが返る
9. **前提** レコード名しか知らない、**操作** レコード名からゾーンとレコードを取得する、**結果** 対応するゾーンとレコードの双方が返る
10. **前提** ゾーンの一覧が 1 ページに収まらない、**操作** ゾーンを取得する、**結果** すべてのゾーンが照合の対象になる

### 利用シナリオ 4 - ゾーン単位で排他できる (優先度: P4)

複数のプログラムが同じゾーンを同時に編集すると、互いの変更を上書きしうる。利用者はゾーンを編集する前に排他を取得し、編集してゾーンへ反映し、その後に解放する。他のプログラムが保持している間は取得できないが、保持者が異常終了した場合でも、一定の時間が過ぎれば奪える。保持者が自分自身であれば、取り直せる。

**この優先度の理由**: 排他は他の 3 つと違って、正しく動かなかったときの被害が「取得できない」ではなく「二重に編集される」になる。他者のゾーンを壊す方向の失敗であり、影響が本ライブラリの外に出る。一方で、これを必要とするのは複数のプログラムから同じゾーンを操作する利用者に限られるため、優先度は基本操作の後に置く。

**独立した検証**: 同じゾーンに対して 2 つの排他を作り、一方が取得している間はもう一方が取得できないことを確認できる。奪ってよい時刻を過ぎた状態で、他者が取得できることを確認できる。保持者が自分自身の場合に取り直せることを確認できる。解放の後に再取得できることを確認できる。取得と解放でゾーンへの反映が起きないことを確認できる。

**受け入れシナリオ**:

1. **前提** 排他が取得されていないゾーンである、**操作** 排他を取得する、**結果** 取得に成功し、SOA レコードが編集予定の状態になる
2. **前提** 他者が排他を保持しており、奪ってよい時刻を過ぎていない、**操作** 排他を取得する、**結果** まだ保持されていることを判別できるエラーが返る
3. **前提** 他者が排他を保持しているが、奪ってよい時刻を過ぎている、**操作** 排他を取得する、**結果** 取得に成功する
4. **前提** 自分自身が保持者である、**操作** 排他を取得する、**結果** 奪ってよい時刻を過ぎていなくても取得に成功する
5. **前提** 排他を保持している、**操作** 解放する、**結果** 奪ってよい時刻が現在時刻になり、他者が取得できる状態になる
6. **前提** 他者が保持している、**操作** 取得できるまで待ち続ける処理を、間隔を指定して呼ぶ、**結果** その間隔で再試行し、取得できた時点で返る
7. **前提** 取得できるまで待ち続けている、**操作** まだ保持されている以外のエラーが発生する、**結果** 再試行せず、そのエラーを返して終了する
8. **前提** 取得できるまで待ち続けている、**操作** 呼び出し側が処理を打ち切る、**結果** 打ち切りの理由が分かるエラーが返る
9. **前提** 排他の取得または解放を行った、**操作** ゾーンの状態を確認する、**結果** ゾーンへの反映は行われていない
10. **前提** 排他を取得し、レコードを編集してゾーンへ反映した、**操作** 解放する、**結果** レコードは編集できる状態に戻り、再び排他を取得できる
11. **前提** 保持者の名前を指定していない、**操作** 排他を取得する、**結果** 実行ホストの名前から導いた既定の保持者名が使われる
12. **前提** 有効期間を指定していない、**操作** 排他を取得する、**結果** 既定の 15 分が使われる

### 利用シナリオ 5 - レスポンスから JOB の識別子を取れる (優先度: P5)

利用者は非同期 API を呼び、その識別子を自分のログや監査記録に残したい。利用者はレスポンスを渡すだけで識別子を得られ、そのレスポンスは後続の処理でそのまま読み直せる。

**この優先度の理由**: 記録のための補助であり、これがなくても API の操作自体は完結する。ただしレスポンスの本文を読み出す処理であるため、読み出したまま戻さないと呼び出し側の後続処理を壊す。他のシナリオが確立した後に足すのが安全である。

**独立した検証**: 識別子を含むレスポンス、含まないレスポンス、本文が解釈できないレスポンスのそれぞれに対する結果を確認できる。取得の後にレスポンスの本文が読み直せることを確認できる。

**受け入れシナリオ**:

1. **前提** 識別子を含むレスポンスである、**操作** 識別子を取得する、**結果** その識別子が返る
2. **前提** 識別子を取得した、**操作** 同じレスポンスの本文を読む、**結果** 本文は失われておらず読み直せる
3. **前提** 本文が解釈できない、本文がない、またはレスポンス自体がない、**操作** 識別子を取得する、**結果** 空の値が返り、処理は失敗しない

### 境界的な状況

- トークンはいつ取得されるか？ → API リクエストのたびに、利用者が与えた取得処理を評価する。外部でローテーションされたトークンを、クライアントを作り直さずに反映するためである。評価の頻度を抑えたい場合は有効期間を指定する。
- 設定の誤りはいつ分かるか？ → クライアント生成の時点で取得処理を 1 度実行して検証する。最初の API 呼び出しまで遅らせない。
- レート制限の待ちとトークンの取得はどちらが先か？ → レート制限と同時実行数の待ちを抜けた直後にトークンを取得する。順序が逆だと、待っている間に古くなったトークンを送ることになる。
- 利用者が独自の HTTP クライアントを渡した場合、タイムアウトの指定はどうなるか？ → 渡された HTTP クライアントの設定が優先される。タイムアウトの指定は無視される。
- 渡された HTTP クライアントは書き換えられるか？ → 書き換えない。複製してから、そのうえで制御を差し込む。
- 別ホストへリダイレクトされたときに認証情報はどうなるか？ → 付与しない。認証情報を意図しない相手へ送らないためである。
- 本モジュールのバージョンが取得できない場合はどうなるか？ → 不明であることを示す固定の値が使われる。クライアントの生成は失敗しない。
- 何を再試行の対象とするか？ → レスポンスが得られなかった失敗のみである。HTTP レスポンスを伴う API エラーは、繰り返しても結果が変わらないため対象としない。トークンの取得失敗も同様である。
- 非同期 JOB の待ち合わせで、元の呼び出しの打ち切り状態を引き継ぐと何が起きるか？ → 条件によっては、元の呼び出しから戻った時点で既に打ち切られていることがある。そのまま引き継ぐと最初の状態確認が即座に失敗する。このため、既に打ち切られている場合は打ち切りだけを切り離す。分散トレースの文脈は保つ必要があるため、文脈全体を捨てて作り直すことはしない。
- 待ち合わせに上限を設けたい場合はどうするか？ → 打ち切りを明示的に指定できる別の入口を使う。上記の切り離しが働く経路では、元の呼び出し側の打ち切りを伝播できないためである。
- ドメイン名の最長一致はどう判定するか？ → 文字列操作では行わない。正規化・包含関係・ラベル数の判定をいずれも miekg/dns の関数で行う。
- レコードの検索は API の絞り込みだけで足りるか？ → 足りない。名前の絞り込みは部分一致であるため、取得した候補に対して名前と RRTYPE の完全一致を利用者側で確認する。
- ゾーンの一覧が 1 ページに収まらない場合、照合から漏れないか？ → 漏れない。照合には全件取得を用いる。
- 排他はなぜ SOA レコードのラベルで実現できるのか？ → レコードは追加予定・編集予定の状態にある間、同名かつ同 RRTYPE のレコードを追加・編集できない。この性質を用い、SOA レコードのラベルへ保持者と奪ってよい時刻を書いて編集予定の状態にする。
- 排他の取得・解放でゾーンへの反映は起きるか？ → 起きない。取得した後にレコードを編集し、取得したレコードをそのままゾーンへ反映することを想定している。反映の後に解放すると、レコードは編集できる状態に戻り、再び取得できる。
- 保持者が異常終了して解放されなかった場合はどうなるか？ → 奪ってよい時刻が過ぎれば、他者が取得できる。
- 対象の SOA レコードが複数見つかった場合はどれを使うか？ → 反映済みのものを優先する。なければ最初に見つかったものを使う。

## 要件 *(必須)*

### 機能要件

**クライアントの生成**

- **FR-001**: エンドポイントは、オプションでの明示指定、環境変数、本番の既定値の順で決定されなければならない。明示指定を必須の引数としてはならない
- **FR-002**: アクセストークンは、文字列から取得する手段、ファイルから取得する手段、利用者が与える任意の取得処理、環境変数のいずれからも与えられなければならない
- **FR-003**: アクセストークンは、API リクエストのたびに取得処理を評価して得られなければならない。実行時点の最新のトークンが使われる
- **FR-004**: トークンの取得処理には有効期間を設定できなければならない。期間内は再評価してはならない
- **FR-005**: クライアントの生成時に取得処理を 1 度実行して検証し、トークンが空または取得に失敗した場合はエラーを返さなければならない。トークンが必要であることと、元の失敗の原因のいずれも、返されたエラーから判別できなければならない
- **FR-006**: 利用者エージェントには、本モジュールの名称とバージョンを含めなければならない。バージョンは実行時の構成情報から取得し、取得できない場合も生成を失敗させてはならない
- **FR-007**: 生成されたクライアントから、内包する API クライアントを取り出せなければならない

**リクエストの制御**

- **FR-008**: 送出するリクエストは、レート制限に従わなければならない。既定は 1 秒あたり 5 リクエスト、バースト 10 とする
- **FR-009**: 同時に実行するリクエストの数を制限しなければならない。既定は 5 とする
- **FR-010**: レスポンスを得られずに失敗したリクエストは再試行しなければならない。既定は 3 回とする
- **FR-011**: HTTP レスポンスを伴う API エラー、およびトークンの取得失敗は、再試行してはならない
- **FR-012**: HTTP クライアントのタイムアウトを設定しなければならない。既定は 30 秒とする
- **FR-013**: HTTP クライアント自体を差し替えられなければならない。差し替えた場合、タイムアウトの指定より差し替えたものの設定が優先される
- **FR-014**: 差し替えられた HTTP クライアントを書き換えてはならない
- **FR-015**: レート制限と同時実行数の制御は、再試行による再実行を含むすべてのリクエストに適用されなければならない
- **FR-016**: トークンの取得は、レート制限と同時実行数の待ちを抜けた後に行われなければならない
- **FR-017**: API のエンドポイントとは別のホストへのリクエストに、認証情報を付与してはならない
- **FR-018**: 既定値 (FR-008 から FR-012) はすべてオプションで変更できなければならない
- **FR-019**: ライブラリの内部でログを出力してはならない

**非同期 JOB の待ち合わせ**

- **FR-020**: システムは、非同期 API の呼び出しの返り値をそのまま受け取り、JOB が終了するまで待つ手段を提供しなければならない
- **FR-021**: 元の呼び出しがエラーを返していた場合、JOB の確認を行わず、そのエラーをそのまま返さなければならない
- **FR-022**: JOB が成功で終了した場合、終了時点の JOB の情報を返し、エラーを返してはならない
- **FR-023**: JOB が失敗で終了した場合、失敗の種別と内容を含むエラーを返さなければならない。終了時点の JOB の情報も返さなければならない
- **FR-024**: 元の呼び出しの HTTP レスポンスを、成功・失敗のいずれの場合も返さなければならない
- **FR-025**: JOB が進行中の場合、一定の間隔で状態を確認し続けなければならない
- **FR-026**: 状態確認に用いる文脈は、元の呼び出しの文脈を引き継がなければならない。ただし既に打ち切られている場合は、打ち切りのみを切り離さなければならない。分散トレースの文脈は保たれなければならない
- **FR-027**: 待ち時間に上限を設けられる別の入口を提供しなければならない

**ゾーンとレコードの検索**

- **FR-028**: システムは、ドメイン名から、そのドメイン名を最も長く含むゾーンを返さなければならない
- **FR-029**: 上位ゾーンのみを対象とする指定を提供し、その場合はドメイン名と完全一致するゾーン自身を除外しなければならない
- **FR-030**: ドメイン名の正規化・包含関係の判定・一致の長さの判定は、いずれも `miekg/dns` の関数で行わなければならない。文字列操作による自作の処理を用いてはならない
- **FR-031**: ドメイン名を受け取る公開された処理は、内部で正規化しなければならない。呼び出し側に正規化を要求してはならない
- **FR-032**: ドメイン名からゾーン ID を返す手段を提供しなければならない
- **FR-033**: サービスコードから、対応するゾーンおよびゾーン ID を返す手段を提供しなければならない
- **FR-034**: ゾーンが該当しない場合は、ゾーンが見つからないことを判別できるエラーを返さなければならない
- **FR-035**: ゾーン ID・レコード名・RRTYPE から、名前と RRTYPE が完全一致するレコードを返さなければならない。API の絞り込みが部分一致であるため、完全一致の確認を自ら行わなければならない
- **FR-036**: ゾーン名とレコード名から、またはレコード名のみから、対応するゾーンとレコードの双方を返す手段を提供しなければならない
- **FR-037**: レコードが該当しない場合は、レコードが見つからないことを判別できるエラーを返さなければならない
- **FR-038**: ゾーンおよびレコードの照合は、一覧の全件を対象としなければならない。1 ページ分に限ってはならない

**ゾーン単位の排他**

- **FR-039**: 排他は、対象ゾーンの SOA レコードのラベルへ、保持者と奪ってよい時刻を書き、編集予定の状態にすることで実現しなければならない
- **FR-040**: 保持者と奪ってよい時刻を格納するラベルの鍵は、他の用途と衝突しない固定の名前でなければならない
- **FR-041**: 奪ってよい時刻は、協定世界時の Unix 時刻で格納されなければならない
- **FR-042**: 取得の可否は次のとおり判定されなければならない。(a) 奪ってよい時刻のラベルが存在しない場合は取得できる、(b) 存在し、その時刻を過ぎている場合は取得できる、(c) 保持者が自分自身の場合は取得できる、(d) それ以外の場合は、まだ保持されていることを判別できるエラーを返す
- **FR-043**: 解放は、奪ってよい時刻を現在時刻にすることで行われなければならない
- **FR-044**: 取得および解放は、ゾーンへの反映を行ってはならない
- **FR-045**: 排他を表す型は、標準の排他機構と同じ形の取得・解放を備えなければならない
- **FR-046**: 取得できるまで再試行し続ける手段を提供しなければならない。再試行の間隔は呼び出し側が指定する。まだ保持されている以外のエラーが発生した場合は、再試行せずそのエラーを返して終了しなければならない。呼び出し側の打ち切りに応じなければならない
- **FR-047**: 有効期間の既定は 15 分でなければならない。オプションで変更できなければならない
- **FR-048**: 保持者の既定の名前は、実行ホストの名前のうちノード名の部分でなければならない。オプションで変更できなければならない。ホスト名を取得できない場合も動作しなければならない
- **FR-049**: 対象の SOA レコードが複数見つかった場合、反映済みのものを優先しなければならない

**JOB の識別子の取得**

- **FR-050**: システムは、HTTP レスポンスの本文から JOB の識別子を取得できなければならない
- **FR-051**: 識別子の取得は、レスポンスの本文を読み直せる状態に復元しなければならない。呼び出し側の後続処理を妨げてはならない
- **FR-052**: 本文が解釈できない、本文がない、またはレスポンス自体がない場合は、空の値を返さなければならない。処理を失敗させてはならない

**共通**

- **FR-053**: 公開されたパッケージ・型・関数・メソッド・エラー値には、godoc 形式のコメントを付与しなければならない
- **FR-054**: 手書きで追加・変更した公開挙動には単体テストを付与しなければならない。単体テストはネットワークアクセスを必要としてはならない
- **FR-055**: 検索と更新に用いる API は、テスト時に差し替えられる形で受け取らなければならない
- **FR-056**: 本体モジュールが依存する外部パッケージを増やしてはならない
- **FR-057**: `unsafe` パッケージおよび unsafe な機能を使用してはならない

### 主要な実体

- **クライアント**: DPF-API クライアントを内包し、リクエストの制御と再試行の設定を保持する。エンドポイント、トークンの取得手段と有効期間、レート制限、同時実行数、再試行回数、タイムアウト、利用者エージェントからなる
- **トークンの取得処理**: 実行時にアクセストークンを返す処理。文字列・ファイル・環境変数・利用者が与える任意の処理のいずれかで構成され、有効期間による短期の保持を伴う
- **非同期 JOB**: 更新系 API が返す処理の単位。識別子と、進行中・成功・失敗の状態を持ち、失敗時は種別と内容を持つ
- **ゾーン**: 契約に属する DNS ゾーン。識別子・ゾーン名・サービスコードを持ち、ゾーン名によってドメイン名との包含関係が定まる
- **レコード**: ゾーンに属する DNS レコード。識別子・名前・RRTYPE・状態・ラベルを持つ。名前と RRTYPE の組で一意に定まる
- **排他**: 対象ゾーンとその SOA レコードのラベルによって表される排他の状態。保持者と、奪ってよい時刻の 2 つのラベルからなる

## 前提

- 本機能は実装済みである。本仕様は、CLAUDE.md「追加処理作成タスク」の記述と現在の実装から起こした事後仕様であり、新規の作業を含まない。CLAUDE.md は本仕様への移行に伴って削除された
- CLAUDE.md は「追加処理作成タスク」の全体を `utils/` 以下に置くと記していたが、非同期 JOB の待ち合わせは生成された型のメソッドとして提供する必要があるため、本体パッケージに置かれている。それ以外 (ゾーン・レコードの検索、排他、クライアント、JOB の識別子の取得) は `utils/` 以下にある
- CLAUDE.md には「SyncWait 仕様」の節が同一の内容で 2 度記載されていた。重複であり、要件は 1 つである
- 待ち時間に上限を設けられる別の入口 (FR-027) は、CLAUDE.md に記載がない。元の呼び出しの打ち切り状態を引き継げない経路が存在するため、実装時に追加されたものである
- ゾーン単位の排他は、レコードが追加予定・編集予定の状態にある間は同名かつ同 RRTYPE のレコードを追加・編集できないという DPF-API の性質を前提とする。この性質が変わると排他は成立しない。**この前提は不正確であった。** 編集中のレコードへの編集の拒否は他ユーザに対してのみ働き、同一ユーザからの編集は拒否されない。そのため 1 つのアクセストークンを複数のプログラムから使う構成では排他が成立していなかった。この欠陥と、その修正のための方式は 006-zone-lock-redesign が扱う
- 排他は、取得の後にレコードを編集し、取得したレコードをそのままゾーンへ反映する使い方を前提とする。反映の後に解放することで、レコードは編集できる状態に戻り、再び取得できる
- 既定値 (レート制限 1 秒あたり 5 リクエスト・バースト 10、同時実行数 5、再試行 3 回、タイムアウト 30 秒、排他の有効期間 15 分) の変更は、破壊的変更として扱う (憲章 原則 V)
- 実 API に触れる挙動 (ゾーン反映、排他、非同期 JOB の待ち合わせ) の確認は、`integration` の区分で隔離された統合テストで行う。単体テストの対象には含めない (憲章 原則 II)
- 本仕様は、生成された API クライアント自体を含まない。それは 002-openapi-generation-pipeline が扱う。またシークレット管理サービスからトークンを取得する機能を含まない。それは 004-misc-token-providers が扱う
