# 統合テスト

実際の DPF-API と権威 DNS サーバを使うテスト。`integration` ビルドタグで隔離しており、
通常の `go test ./...` では実行されない。

```bash
make test-integration
```

## 環境変数

| 変数 | 要否 | 用途 |
|---|---|---|
| `DPF_TOKEN_RO` | 必須 | `dpf_read` スコープのトークン。未設定なら全テストがスキップされる |
| `DPF_TOKEN_RW` | 書き込み系で必須 | `dpf_write` スコープのトークン。未設定なら書き込み系のみスキップされる |
| `DPF_TEST_SERVICE_CODE` | 書き込み系で必須 | `sub.sub.dns-tool-test.jp.` のサービスコード |
| `DPF_API_ENDPOINT` | 任意 | 既定は本番エンドポイント |
| `DPF_TEST_DNS_TIMEOUT` | 任意 | 権威サーバへの反映確認の上限。既定 `10m`。`time.ParseDuration` 形式 |

`DPF_API_TOKEN` は設定しないこと。`utils.NewClient` の既定の TokenProvider が
参照するため、設定されているとトークンの取り違えに気づけなくなる。

ゾーン名はテストコード内の定数として持っている。DNS を引けば分かる情報である一方、
サービスコードは社内の識別子なので環境変数から受け取り、リポジトリには置かない。

## 前提となるゾーン構成

テスト契約に 3 階層の入れ子ゾーンがあることを前提とする。

| ゾーン | 用途 |
|---|---|
| `dns-tool-test.jp.` | longest match の検証、ネームサーバ申請（`/delegations`）の検証 |
| `sub.dns-tool-test.jp.` | longest match / `parent` 引数の検証（参照のみ） |
| `sub.sub.dns-tool-test.jp.` | **レコードの書き込み対象** |

## 安全のための仕組み

**書き込みは `sub.sub.dns-tool-test.jp.` にしか行わない。**
`utils.GetZoneFromZonename` は longest match であり完全一致ではないため、ゾーン名だけで
解決すると、対象ゾーンが契約から消えていた場合に黙って親ゾーンにフォールバックする。
そこで書き込み対象の特定には、

1. `DPF_TEST_SERVICE_CODE` からの解決（`ServiceCode` の完全一致）
2. 解決結果のゾーン名がコード上の定数と一致すること

の両方を要求している。片方でも食い違えば書き込み前に失敗する。

**このゾーンは統合テスト専用にすること。**
テスト開始時に未反映の編集が残っていた場合、前回の実行が中断されたものとみなして
`DeleteZoneChanges` で破棄してから開始する。他の用途と共用すると、作業中の編集が
失われる。

**ネームサーバ申請の前に委任先の動作を確認する。**
`POST /delegations` の前に、ゾーンの権威サーバ全台が実際に権威応答（`AA=1`）を
返すことを確認する。1 台でも確認できなければ申請を行わずに失敗する。

**反映前に未反映件数を確認する。**
`PatchZoneChanges` の直前に、未反映の件数が自分の作った分と一致することを確認する。
他者の作業中の編集を巻き込んで公開しないため。

**専用レコードを公開したまま残さない。**
`TestLockRecordPremises` は `_dpf-go-lock.sub.sub.dns-tool-test.jp.` の TXT レコードを
一度権威サーバへ公開し、削除予定にして入れ直したうえで最後に消す。ゾーン反映を 2 回行う。
テストが途中で失敗した場合も、後始末が state ごとに処理を分けて片付ける
（追加予定は取り消し、反映済みは削除して反映）。

## 用語について

本テストは権威サーバに**直接**問い合わせるため、リゾルバのキャッシュは介在しない。
待っているのは「ゾーン反映が全権威サーバに行き渡ること」であり、いわゆる DNS の
「伝播(propagation)」ではない。DNS にそのような伝播現象は存在せず、権威サーバが
新しい内容を返すか、リゾルバが TTL の間だけ古い内容をキャッシュしているかの
どちらかである。そのためコードとログでは一貫して「権威サーバへの反映」と表記する。

## API 負荷の制御

- プロセス全体で 1 本の `rate.Limiter` を共有し、**1.1 秒に 1 リクエスト**に制限する。
  `utils.Client` はクライアントごとにリミッタを持つため、RO / RW の 2 つを作ると
  レートが 2 倍になってしまう。これを避けるため、両方に同じ `http.RoundTripper` を
  `WithHTTPClient` で渡している。
- 最大同時実行数は 1。`t.Parallel()` は使わず、`-parallel 1` で実行する。
- 非同期 JOB は常に 1 つずつ。次の操作の前に必ず `SyncWait` で完了を待つ。
- 更新系クライアントはリトライを無効にしている。`Operation` は「レスポンスが
  得られなかったエラー」を再試行するため、POST 受理後の接続断でレコードが
  二重作成されうる。

## 所要時間

実測で全 18 テストが約 3 分 57 秒（2026-09-18）。内訳の大きいものは
`TestLockRecordPremises` が 66 秒（ゾーン反映 2 回を含む）、`TestZoneMutex` が 58 秒、
`TestRecordLifecycle` が 57 秒である。`TestZoneMutex` は
`specs/006-zone-lock-redesign` の実装により、排他の取得 1 回あたりの API 呼び出しが
増えたため以前より長い。ゾーン反映が権威サーバへ行き渡るのは速く、
レコード追加は 17ms、削除は 12 秒で確認できた（いずれも上限 10 分に対して）。

`DPF_TEST_DNS_TIMEOUT` の既定 10 分は「異常を検出するための天井」であり、
通常の所要時間ではない。反映にかかった実時間は毎回ログに出力されるので、
傾向が変わった場合は気づける。

上限を大きくする場合は `Makefile` の `-timeout 45m` も見直すこと
（上限を 20 分にすると、反映待ちが 2 回あるため最悪 46 分となり抵触する）。

## 実行が中断された場合

ゾーンに未反映の編集が残るが、次回の実行が開始時に `resetPendingChanges` で破棄するため
手動の復旧は不要。ロックは次の 3 つで回復する。

1. `t.Cleanup` の `discardSOAChanges` が SOA の未反映編集を破棄する。中断されない限り毎回走る
2. ロックの TTL（テストでは 2 分）の経過。中断で 1 が走らなかった場合
3. 一時レコード追加ロックの失効（既定 1 分）の経過。取得の途中で中断した場合

以前は owner を `dpf-go-ci` に固定し、`utils.Mutex` の「owner が自分自身ならロック可能」
という判定で短絡させて自己回復していた。`specs/006-zone-lock-redesign` でこの判定を
外したため（同一 owner を持つプログラム同士が互いを排他できなくなるため）、回復は上記に
置き換わった。owner の固定は、残っているラベルが CI 由来かどうかを見分けるために続けている。

同仕様の FR-028 が求める前提の確認のうち、レコードの状態に関する 2 つは
`TestLockRecordPremises` が担う。
